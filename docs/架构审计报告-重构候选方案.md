## 二、Top 技术债清单

### P0 —— 阻塞 V2.0 或已产生用户可见错误

#### P0-1 导航栏 4 个图标格式错配，实际渲染为空
`frontend/js/app.js` 的 `NAV_ITEMS` 混用了两种互不兼容的 icon 数据格式：

- `app.js:8-22`、`app.js:27-28`：值是**裸 path 的 `d` 属性字符串**，例如 `icon: 'M3 12l2-2m0 0l7-7...'`
- `app.js:23-26`：值是**完整 SVG 子元素标记**，例如
  `{ path: '/poc', icon: '<path d="M10 2v7.31"/><path d="M14 9.3V1.99"/>...' }`

而模板只有一种消费方式，`app.js:242-244`：
```html
<svg class="app-sidebar__nav-icon" ...>
  <path stroke-linecap="round" :d="item.icon"></path>
</svg>
```

即把 `'<path d="M10 2v7.31"/>...'` 整段字符串塞进 `<path d="...">`。这不是合法路径数据，**`/poc`、`/bid`、`/vuln`、`/incident` 四个入口的侧边栏图标必然渲染为空白**。

更关键的是，这 4 段字符串与 `frontend/js/utils/icons.js` 中的条目**逐字节相同**：

| NAV_ITEMS | icons.js 对应键 |
|---|---|
| `app.js:23` `/poc` | `icons.js:20` `flask` |
| `app.js:24` `/bid` | `icons.js:12` `clipboard` |
| `app.js:25` `/vuln` | `icons.js:23` `warning` |
| `app.js:26` `/incident` | `icons.js:21` `rocket` |

**影响**：4 个功能入口视觉缺失；同时违反团队 P0 规则"锁定一套 SVG 图标库、全项目统一不混用"——`icons.js` 已经是那套库（`app.js:316` 已把 `htdIcon` 注入全局），NAV_ITEMS 却绕开它复制粘贴。

#### P0-2 图表色板硬编码，暗色主题下配色失效
`frontend/css/global.css:45` 定义亮色 `--color-primary: #5B8DEF`，`global.css:187` 定义暗色 `--color-primary: #2F6BEE`。

`charts.js:42`、`charts.js:111` 的默认值写得是对的——`opts.color || 'var(--color-primary)'`，会跟随主题。**但每一个调用方都用硬编码 hex 覆盖了它**，于是主题适配被系统性架空：

| 位置 | 硬编码值 | 问题 |
|---|---|---|
| `charts.js:9` | `PALETTE[0] = '#5B8DEF'` | 写死亮色主色，暗色主题不变 |
| `HomePage.js:112,117` | `'#22D3EE'`、`'#34D399'` | 覆盖主题变量 |
| `FinancePage.js:340,347,365` | `'#34D399'`、`'#F87171'`、`'#5B8DEF'` | 同上 |
| `StudyPage.js:35` | `'#22D3EE'` | 同上 |
| `ProjectPage.js:446,447` | `'#34D399'`、`'#94A3B8'` | 同上 |

同时存在**三个互不相同的"主蓝"**，设计 token 已实质性断裂：
- `#5B8DEF` — `global.css:45` / `charts.js:9`
- `#3B82F6` — `app.js:33-34`（Logo）、`TimeBlockPage.js:152`
- `#3D6EFF` — `HtpSelect.js:252-253`

另外 `TimeBlockPage.js:153` 使用 `'#8B5CF6'`（紫色）作为 STUDY 类型功能色，既不在 `PALETTE` 内，也与团队"避开紫粉"的配色治理方向相悖；`TimeBlockPage.js:290,315` 还内联了 `background:#eef0f4`，暗色主题下会出现亮灰块。

**影响**：暗色/多外观（Liquid Glass、Notion Flat）是 V1.4 已交付能力，图表区域实际未跟随，属已交付功能的隐性回退。

#### P0-3 图表渲染机制与 V2.0 知识图谱验收标准不兼容
V2.0 明确要求（`V2.0.0-第二大脑与APP化.md:19`）"基于标签/引用关系绘制轻量图谱（d3-force/SVG手写）"，验收标准（同文档 `:52`）"知识图谱渲染 1k 节点流畅"。

当前机制（C3）为：`Vue.computed` 拼接 SVG 字符串 → `v-html` 注入。力导向图每帧需更新全部节点坐标，按现机制每帧要：① 重新拼接约 1k 个 `<circle>` + 边的字符串；② 浏览器全量重新解析 innerHTML；③ 丢弃并重建整棵子树。**这在 60fps 下不可能达标**，且 `v-html` 全量替换会使拖拽、hover 等交互态在每帧丢失。

此外 d3-force 是 npm 包，在 C1 约束下必须找到 UMD 构建产物、手工 vendor 到 `assets/lib/`、再追加第 44 个 `<script>` 标签。

**影响**：这是唯一一条"不改架构就做不出来"的债，是 V2.0 的真实技术前置条件。

#### P1-2 状态机三套实现并存，抽象已存在却未统一
`lib/stateMachine.js` 提供了 `createStateMachine` 通用工厂，但三个核心模块用了三种不同范式：

| 模块 | 是否用 createStateMachine | 迁移表来源 | 证据 |
|---|---|---|---|
| reading.status | 是 | **配置平台**（可配） | `reading.service.js:141-152` |
| project.phase | **否，手写校验** | 配置平台（可配） | `project.service.js:106-113` |
| todo.status | 是 | **常量枚举**（不可配） | `todo.service.js:125` |

`project.service.js:15` 显式 `import { createStateMachine }`，但全文件从未调用——**dead import + 重复实现**。它在 `:107-113` 手写了 `allowed.includes(toPhase)`，逻辑与 `stateMachine.js:17-21` 的 `isAllowed` 重复，且**缺少 `reading` 有的状态合法性前置校验**（`reading.service.js:144-146` 会拒绝未知 `toStatus`，project 不会）。

更严重的一致性漏洞：`todo.service.js:99-110` 的 `toggleStatus` **完全绕过状态机**，直接 `exists.status === 'completed' ? 'pending' : 'completed'`。这意味着一条处于 `delayed` 态的待办，走 `changeStatus`（`:116`）会受 `TODO_STATUS_TRANSITIONS` 约束，走 `toggleStatus`（`:99`）却能无校验直接跳到 `completed`。**同一实体、两条写路径、两套规则。**

规模失衡也很明显：`enums.js` 定义了 **8 张**迁移表（`:145,152,209,233,250,273,298,326`），配置平台只纳管 **2 个** scope（`fieldConfig.service.js:44-55` 仅 `reading.status`、`project.phase`）。其余 6 个（review、poc、bid、vuln、incident/emergency、todo）在 `bid.service.js:112`、`incident.service.js:145`、`poc.service.js:113`、`review.service.js:70,93`、`vuln.service.js:117`、`todo.service.js:125,151` 直接写死枚举。配置平台对用户的承诺（"状态机可配置"）只兑现了 1/4。

#### P1-3 三层重复回落，语义反而变模糊
`getStateMachineSync` 内部**已经**做了回落——`fieldConfig.service.js:140-142`：未配置时返回 `defaultConfig().stateMachines[scope]`，而 `defaultConfig()`（`:44-55`）本身就是用 `READING_STATUS_TRANSITIONS` / `PROJECT_PHASE_TRANSITIONS` 播种的。

调用方却又加了一层：
- `project.service.js:106` `const transitions = smConfig?.transitions || PROJECT_PHASE_TRANSITIONS;`
- `reading.service.js:142-143` `smConfig?.states || Object.values(READING_STATUS)` / `smConfig?.transitions || READING_STATUS_TRANSITIONS`

同一份默认值经由 3 条路径可达（缓存 → defaultConfig 播种 → 调用方 `||`）。**后果**：当用户在配置平台**故意**把某状态的后继清空为 `[]` 时，`[] || TRANSITIONS` 因空数组为真值不会回落，但 `undefined` 会——回落边界依赖 JS 真值语义而非显式契约，行为难以推理，也无法从代码判断"到底哪份配置在生效"。

#### P1-4 `config.customFields` 是端到端死配置
配置平台在 `fieldConfig.service.js:40-43` 定义了 `customFields: { reading: [], project: [] }`，并提供同步读取器 `getCustomFieldsSync`（`:132-136`）。

- **后端**：`getCustomFieldsSync` 在 `fieldConfig.service.js` 之外**零调用**。`reading.schema.js:19,30` 对 customFields 的校验是 `z.record(z.string(), z.any()).optional()`——接受任意键、任意值，完全不参照配置定义。
- **前端**：`ReadingPage.js:41` 消费了 `fc.dropdowns['reading.type']`，`:46` 消费了 `fc.stateMachines['reading.status'].states`，**但从未读取 `fc.customFields`**。`ReadingPage.js:154-159` 提供的是一个自由 key-value 编辑器，用户可任意造字段名。

**影响**：管理员在设置里定义的扩展字段结构对系统零约束力，配置平台在此项上是纯装饰。这也解释了为什么 `reading.customFields` 存进 DB 后没有任何一致性保障。

#### P1-5 隐式全局状态：可变模块级缓存 + 属性注入
- `fieldConfig.service.js:84-89` 的 `cache` 是模块级可变对象，`:92` 的 `loadingPromise` 是模块级可变变量。所有依赖配置的校验（`configSchema.js:29,44`）都同步读它，正确性依赖调用方**记得**先 `await ensureFieldConfigCache()`。而该函数**仅在 3 个模块**被调用（project / reading / todo service），一旦后续有第 4 个模块使用 `dropdownValue`，忘记预热就会静默按默认枚举校验，**拒绝用户新增的合法下拉项**——失败模式是静默的、且只在"用户改过配置"时才复现。
- `app.js:78` `backupService.prisma = prisma;` 从外部往 service 实例上打属性，形成隐式依赖：单看 `backup.service.js` 无法知道 `this.prisma` 从哪来，也无法保证赋值先于首次使用。
- `prisma.js:20` 在**模块加载瞬间**读取 `process.env.HTD_TEST_DB_URL` 并冻结为 `datasourceUrl`。任何在 import 之后才设置该变量的场景都会静默连到生产库。当前靠 `vitest.config.js:21` 的 `setupFiles` 抢在前面才成立，属于时序耦合。
- `prisma.js:48` 仅在 `NODE_ENV !== 'production'` 挂 `globalThis.__prisma`，意味着生产与开发的实例复用语义不同。

#### P1-6 测试隔离靠"串行执行"这一个约定兜底
`test-setup.js:15-20` 把模板库复制到**固定共享路径** `os.tmpdir()/htd-workbench-test/workbench.test.db`，且作为 `setupFiles`（`vitest.config.js:21`）**在每个测试文件前都重新复制一次**。

这套设计只有在 `vitest.config.js:15` `fileParallelism: false` 时才安全。一旦有人为提速开启并行，多个 worker 会同时 `copyFileSync` 覆盖同一个 db 文件，造成跨文件互相清库——**表现为随机失败，极难定位**。隔离性来自约定而非构造。

同时 37 个测试文件各自重复 `new PrismaClient({ datasourceUrl: process.env.HTD_TEST_DB_URL, log: ['error'] })`（如 `bid.test.js:6`、`finance.test.js:6`、`meeting.test.js:6`…），既是 37 份重复代码，也意味着 37 个独立连接。

  - `:39` 数据与部署 → `'shujuheyushu'`（应为 `shujuyubushu`）
  - `:35` 游戏娱乐 → `'youxuyule'`（应为 `youxiyule`）
- 每新增一个命令需手工补 `id/label/type/path/typeLabel/iconSvg/pinyinKeys` 七个字段。

#### P2-5 打包目标 Node 版本跨平台不一致
`backend/package.json`：
- `build:win` → `pkg --targets node24-win-x64`
- `build:mac` → `pkg --targets node22-macos-x64`

技术栈基线为 Node 24 LTS，macOS 产物却固定在 Node 22，跨平台可能出现运行时行为差异，且 mac 脚本缺少 `build:template`、`build:entry` 两步（win 有），mac 产物是否包含模板库存疑。

#### P2-6 `index.html` 加载顺序是隐式契约
`index.html` 43 个 `<script>` 的相对顺序承载了未被任何机制校验的依赖关系：`vue-demi`（`:23`）必须先于 `pinia`（`:24`）；`theme-manager.js` 必须先于 `app.js`（`:94` 注释明确写着"置于 app.js 前，防 FOUC"）；所有 `utils/` 必须先于 `modules/`。任何顺序调整都可能引入运行时 `undefined`，且无自动化防护。

### 值得肯定的现状（不要在重构中破坏）

审计中有两条原本被怀疑、但实测为健康的项，应明确保留：

1. **响应封装完全一致**。`grep` 统计：`res.success` 188 处、`res.fail` 2 处、**绕过封装的 `res.json` 0 处**。`middleware/response.js:14-34` 的 `{code,msg,data}` 契约被 100% 遵守。前端可安全依赖统一解包。
2. **Tauri 迁移的路径耦合面极小**。绝对路径仅 `app.config.js:15` 一处；`process.pkg` 分支仅 `app.config.js:49,52` 两处；`app.config.js:16-28` 的 `resolveDataRoot()` 已经支持 `HTD_DATA_ROOT` 环境变量覆盖。这意味着**改 1 个文件即可完成数据目录的跨平台化**。

此外 `base.repository.js`（244 行）统一软删除/分页、`lib/fieldSelector.js` 的 `?fields` 裁剪、`middleware/origin-guard.js` 的本地 CSRF 防御、`bootstrap.js` 的启动自检与备份轮转，都是质量不错的横切设施。

## 三、三个重构候选方向

### 方向 A：保持无构建，仅模块化 + 注册点自动化（`meta.js`）

**做什么**
1. 每个前端模块新增 `frontend/js/modules/<name>/meta.js`，声明单一数据源：
   ```js
   window.htdRegistry.register({
     key: 'reading', path: '/reading', title: '阅读资料',
     icon: 'book',                    // 强制引用 icons.js 的键，不再内联 path
     component: () => ReadingPage,
     commands: [{ label: '新建阅读资料', type: 'nav' }],
   });
   ```
2. `router.js`、`NAV_ITEMS`、`pageComponents`、命令面板 `COMMANDS` 全部改为**从 registry 派生**，消灭 P1-1 的 5 处漂移。
3. 修 P0-1（NAV_ITEMS 统一走 `htdIcon(key)`）、P0-2（图表色改 CSS 变量或从 `getComputedStyle` 读 token）、P2-2、P2-3、P2-4。
4. 后端：`app.js` 改为扫描 `modules/*/\*.router.js` 约定式挂载；把 `project.phase` 状态机改为调用 `createStateMachine`；`todo.toggleStatus` 收敛到 `changeStatus`；把 8 张迁移表统一纳入配置平台或明确标注"不可配"。
5. 测试：抽 `test/helpers/prisma.js` 消除 37 份重复；`test-setup.js` 改为**按文件名 hash 生成独立 db 路径**，解除对 `fileParallelism: false` 的依赖。

**不做什么**
- 不引入 Vite/Webpack、不引入 TS、不动 `index.html` 的 script 机制、不碰 Tauri。
- 不重写 `charts.js` 渲染机制。

**风险**
- `registry` 本身仍需在 `index.html` 手工加一个 `<script>`，**C1 未被解除**：新增模块仍要改 `index.html`（从 5 处降到 2 处，非 1 处）。
- **不解决 P0-3**。V2.0 知识图谱依旧无法达标，等于把最难的问题推给下一阶段。
- 全局命名空间污染依旧（`window.HtpXxx`、`window.htdCharts`…），无法静态检查拼写错误。

**收益**
- 成本最低，可在不中断迭代的情况下增量完成；改动集中在注册层，回归面小。
- 立即消除已发生的用户可见缺陷（4 个空图标、11 个模块 Ctrl+K 不可达、"新建备忘"失效、暗色图表配色）。

**与 V2.0 的关系**
- 属于**必要但不充分**的前置整理。Tauri 壳（V2.0 的 APP 化）可以在 A 之上独立推进，因为 Tauri 只依赖 HTTP 契约；但知识图谱（V2.0 的第二大脑核心）无法在 A 上交付。

---

### 方向 B：前端引入 Vite 构建化

**做什么**
1. 引入 Vite + ESM。`assets/lib/*.js` 三个 global build 换成 `npm i vue pinia`；43 个 `<script>` 收敛为单一 `<script type="module" src="/src/main.js">`。
2. 页面组件按 `import`/`import()` 组织，用 `import.meta.glob('./modules/*/meta.js', { eager: true })` **在构建期自动收集注册表**——从根上消灭 P1-1（新增模块 0 处手工注册）。
3. 引入 `d3-force`（走 npm，不再找 UMD），把图谱与图表从"字符串 + `v-html`"改为**真实 Vue 组件 + 响应式 SVG 节点**（或 Canvas），解决 P0-3。
4. 拆分 `dataStore.js`（855 行）为按模块的 store 文件；拆 `ProjectPage.js`（885 行）。
5. 建立 design token 单一来源（CSS 变量 + JS 侧 token 导出），彻底修 P0-2 的三套主蓝。
6. 产物 `dist/` 替换 `pkg` assets 中的 `../frontend/**/*`。

**不做什么**
- 不动后端分层与 Prisma；不引入 SSR；不强制全量 TS（可先 `checkJs` 渐进）。
- 不在本阶段做 Tauri 壳。

**风险**
- **离线/本地优先的取舍**：当前"改个 JS 刷新即生效"的零门槛调试消失，需 `npm run dev`/`build`。对单人本地优先工具，这是真实体验损失。
- 构建产物与 `pkg` 的集成需重新验证：`pkg` 的 `assets` 需指向 `dist/`，且 `app.config.js:49-51` 的 `frontendDir` 解析逻辑要跟着调整。
- 迁移期风险最高：21 个页面组件全部要从"全局变量隐式可见"改为"显式 import"。当前组件间依赖靠全局暴露（`window.HtpCommandPalette` 等），改 ESM 时会暴露大量此前被隐式解决的循环/顺序依赖。
- 需要一次性投入，期间难以并行做业务迭代。

**收益**
- 唯一能真正满足 V2.0"1k 节点流畅"的方向（P0-3 的根治方案）。
- 解除 C1，npm 生态全面可用（d3-force、markdown-it、图谱布局库…），V2.0 的"Markdown Vault 化 + 双向链接 + 引用图谱"三项都需要它。
- 获得 tree-shaking、代码分割（21 个页面按需加载）、HMR、以及**构建期报错**替代运行时 `undefined`。

**与 V2.0 的关系**
- 是"第二大脑"（知识图谱 + Markdown Vault）的**硬前置**。与 Tauri 正交——Tauri 只关心有没有能加载的前端产物，`dist/` 反而比 43 个散文件更适合分发。

---

### 方向 C：面向 Tauri 端到端重构（sidecar 化 + 资源分发 + 构建化前端）

**做什么**
1. **sidecar 化 `server.js`**：抽出 `startServer({ openBrowser, port })`，把 `server.js:75-77` 的无条件 `openBrowser(url)` 改为环境开关（`HTD_SIDECAR=1` 时禁用）。当前实现下，Tauri 启动 Node sidecar 会**在 Tauri 窗口之外再弹一个系统浏览器**。
2. 重新设计单实例语义：`server.js:46-52` 的 `probeInstance` + `process.exit(0)`（为 C4 的 SQLite 单写而存在）在 sidecar 模式下含义完全不同——Tauri 主进程负责生命周期，sidecar 不应自行 `exit(0)`，否则 Tauri 会认为子进程异常退出。需改为"就绪握约 + stdout 端口上报"。
3. **数据目录跨平台化**：改 `app.config.js:15`，由 Tauri 通过 `HTD_DATA_ROOT` 注入 `appDataDir()`（Windows `%APPDATA%`、macOS `~/Library/Application Support`），保留 `D:\荒天帝工作台` 作为 V1.x 老用户的迁移兜底。
4. **资源分发决策**：当前 `package.json` 的 `pkg.assets` 把 `../frontend/**/*` 打进 pkg 虚拟文件系统，由 Express 静态托管。Tauri 下有两条路——(a) 前端资源仍由 sidecar 托管，Tauri WebView 指向 `http://127.0.0.1:17388`（改动最小，符合 V2.0 文档 `:9` "前端仍走 http://localhost:17388/api/*"）；(b) 前端资源交给 Tauri 打包、只有 `/api/*` 走 sidecar（启动更快、离线更稳）。**建议 (a)**，因为它保证"业务代码 0 改动"这一 V2.0 前提。
5. 包含方向 B 的全部构建化工作（Tauri 生态默认假设有构建产物）。
6. 保留 pkg 产物线（V2.0 文档 `:12` 要求 V1.x 老用户仍可用 .exe），即**双产物线并行维护**。

**不做什么**
- 不把业务逻辑迁进 Rust；不改 HTTP 契约（这是"业务代码 0 改动"的保证）；不引入 Tauri 原生插件替代现有 Node 能力。

**风险**
- **范围最大、并行度最差**：同时动构建体系、进程模型、路径体系、分发方式，任一环出问题都难以二分定位。
- 双产物线（pkg exe + Tauri app）的构建矩阵与测试成本翻倍，且 P2-5 已显示现有跨平台脚本就不整齐（mac 缺 `build:template`/`build:entry`，Node 版本还不一致）。
- 引入 Rust 工具链依赖，本地"离线优先"的构建环境要求显著提高。
- SQLite 单写约束（C4）在"Tauri 壳 + sidecar + 用户可能仍双击老 exe"的组合下更易被违反，需要更强的跨进程互斥（文件锁而非当前的 HTTP 探测）。

**收益**
- 一次性达成 V2.0 的 APP 化 + 第二大脑两大目标，无中间态返工。
- 真正的桌面应用体验（系统托盘、原生菜单、无浏览器地址栏、自动更新）。

**与 V2.0 的关系**
- 就是 V2.0 本身的完整实现路径。

## 四、给总监的架构建议

### 结论：**A → B → C 三阶段推进，且 A 必须先做、C 必须最后做。**

不建议直接上 C。理由基于本次审计的具体发现：C 的最大风险不是 Tauri 本身，而是**在一堆已知缺陷上叠加三个维度的变更**。目前存在 4 个空图标（P0-1）、11 个模块 Ctrl+K 不可达（P1-1）、图表暗色主题失效（P0-2）、状态机双写路径（P1-2）、端到端死配置（P1-4）。若在 C 阶段一起动，任何回归都会陷入"是 Tauri 的问题、是 Vite 的问题、还是原有缺陷"的三重归因困境。

同时，**A 的低成本被一个关键事实放大**：Tauri 迁移的路径耦合面极小（绝对路径仅 `app.config.js:15` 一处，`process.pkg` 仅 2 处，且 `HTD_DATA_ROOT` 覆盖机制已就位）。这意味着**推迟 C 的代价很低**——C 不会因为等待而变得更难。反过来，B 的必要性是刚性的：V2.0 自己的验收标准（1k 节点流畅）在现有 `v-html` 字符串渲染机制上不可能达标，这不是优化问题而是机制问题。

### 阶段划分

**阶段 1（方向 A，建议 1 个迭代内完成）—— 止血 + 建立单一数据源**

优先级内排序：
1. 修 P0-1、P0-2、P2-4 的空操作 handler 与拼音错字——**用户可见缺陷，独立可验证，无架构依赖**。
2. 建 `htdRegistry` + 各模块 `meta.js`，把 router/NAV_ITEMS/pageComponents/COMMANDS 四处收敛为派生，补齐命令面板缺失的 10 个模块。
3. 后端 `app.js` 约定式路由挂载；`project.phase` 改用 `createStateMachine`；`todo.toggleStatus` 收敛进 `changeStatus`。
4. 对 `config.customFields` 做**明确决策**：要么后端 `reading.schema.js` 接入 `getCustomFieldsSync` 做校验、前端 `ReadingPage` 按定义渲染；要么从配置平台移除。不要留着当装饰。
5. 测试隔离改为按文件独立 db 路径，解除对 `fileParallelism: false` 的隐式依赖，顺带打开并行提速。

**出口判据**：新增一个模块只需改 `meta.js` + `index.html` 两处；`grep` 不到重复的 icon path 字面量；`npm test` 在 `fileParallelism: true` 下全绿。

**阶段 2（方向 B）—— 构建化，为第二大脑铺路**

关键是**顺序**：先把阶段 1 建立的 `meta.js` 注册表切到 `import.meta.glob`，此时注册表已是单一数据源，切换是机械的、低风险的。若跳过阶段 1 直接做 B，等于在 5 处漂移的注册点上同时做 ESM 迁移。

阶段 2 内部建议再分两步：先完成 Vite + ESM + store/页面拆分并保证功能等价（不加新功能），再替换图表渲染机制并引入 d3-force。**图表机制替换应有明确的性能门槛测试**（1k 节点力导向 ≥ 30fps 作为中间目标，60fps 作为验收目标），这个数字要在做知识图谱业务功能**之前**验证，避免机制选错后返工。

**出口判据**：`dist/` 产物可被现有 pkg 流程消费；1k 节点图谱 demo 达到帧率门槛；新增模块 0 处手工注册。

**阶段 3（方向 C）—— Tauri 壳**

此时前端已有 `dist/`、注册表已自动化、路径已收敛，C 退化为一个**边界清晰的集成任务**：sidecar 生命周期 + 数据目录注入 + 双产物线。建议采用前述方案 (a)（前端仍由 sidecar 托管，WebView 指向 `127.0.0.1:17388`），以兑现"业务代码 0 改动"。

进入阶段 3 前需先解决两个前置项：`server.js:75-77` 的浏览器弹出开关、`server.js:46-52` 单实例语义改造（HTTP 探测 → 文件锁 + stdout 端口握约），并统一 P2-5 的跨平台 Node 版本与构建步骤。

### 一条需要总监决策的取舍

方向 B 会牺牲当前"改 JS 刷新即生效"的零门槛调试体验，这对一个**本地优先、单人使用**的工具是真实损失。它的正当性完全建立在 V2.0 的知识图谱与 Markdown Vault 目标上。

**因此建议总监先确认：V2.0 的"知识图谱 1k 节点"是硬需求还是可协商需求。**
- 若可降级为"标签树 + 引用列表 + ≤150 节点的静态关系图"，则方向 A 足够，B/C 可无限期推迟，项目维持零构建的极简优势。
- 若为硬需求，则 B 无可替代，应尽早启动以避免在旧机制上继续堆积图表代码（`charts.js` 已有 `lineChart` 零消费的沉没成本，`P2-2`）。

这个判断会直接决定阶段 2 是否存在，是本报告中唯一无法由代码证据单独裁定、必须由产品目标裁定的问题。
