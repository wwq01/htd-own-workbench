## 1. 无构建架构现状与真实瓶颈

### 1.1 现状：43 个有序 `<script>` 拼装（约束 C1）

入口 `frontend/index.html` 用 43 个 `<script>` 标签把 Vue/Pinia/store/utils/components/modules 按严格顺序拼装（`index.html:22-97`）。其中 21 个页面模块脚本必须排在 `app.js`（`:97`）之前，否则 `pageComponents['meeting']` 等全局变量尚未定义 → 白屏（`docs/模块挂载点规范.md:51` 已记录此顺序陷阱）。这是隐式契约，无自动化防护（P2-6）。

运行时依赖三个本地 global build：`vue.global.prod.js` / `vue-demi.iife.js` / `pinia.iife.prod.js`（`index.html:22-24`）。Vue 走「含运行时模板编译器的 global build」，所以**模板里禁用可选链**（注释 `HomePage.js:3-4` 明确说明）。

### 1.2 组件间通信与状态组织

**通信高度依赖 `window` 全局命名空间**，无任何模块化封装：

| 机制 | 证据 | 风险 |
|---|---|---|
| 业务 API 全局 | `api.js:138` `window.htdApi = {...}`；各模块直接 `htdApi.get(...)` 无 import | 全局污染，无 Tree-shaking |
| 图标全局 | `icons.js:46` `window.htdIcon`；`app.js:321` 注入 `globalProperties.htdIcon` | 两套并存（见 §3） |
| Store 全局 | `dataStore.js:855` `window.useDataStore`；`appStore.js:118`、`uiStore.js:52` | 任意模块可越级读写 |
| 事件总线 | `app.js:142` `window.eventBus.emit('ui:flush-all')` | 魔法字符串事件，无类型、无追踪 |
| 路由↔壳桥接 | `router.js:110-117` 写 `window.__htdApp`；`app.js:177-187` 定义该桥接对象 | **双向紧耦合**：路由直接改壳的内部 ref，初始化顺序强依赖（`app.js:190` 先挂桥接再 `initRouter`） |

`uiStore` 的保存三态机是干净设计（`uiStore.js:18-37` 用 `_savingDepth` 计数处理并发写），但 `api.js:60-66` 通过 `window.useUiStore()` 在请求生命周期内反向驱动它——跨层耦合靠全局拿 store，而非依赖注入。

### 1.3 V2.0 下的真实瓶颈（按严重度）

1. **npm 生态被锁死（C1 直接后果）**：知识图谱要 `d3-force`，D3 现代版本是 ESM、无干净 UMD；即便手 vendor，也无法把力导向仿真与 Vue 响应式优雅结合于无构建环境（`docs/架构审计报告-重构候选方案.md:117`）。
2. **全量加载、无代码分割**：21 个页面模块首屏全加载（`index.html:70-91`），用户只想看今日计划却下载了 16 个模块。无 Tree-shaking，无按需 import。
3. **图表机制与 1k 节点验收硬性不兼容（P0-3）**：当前图表 = 拼 SVG 字符串 → `v-html` 全量注入（`HomePage.js:94-355`）。每帧重算全量字符串 + `innerHTML` 替换，**60fps 力导向图不可达**（详见 §4、§5）。
4. **无类型安全（静默逻辑错误温床）**：API 请求/响应、store 字段全靠约定；`刷新即生效` 的代价是运行时才暴露 `undefined` 字段（失效模式 #2 高发）。
5. **全局命名空间污染**：每个模块都是 `window.XxxPage`，碰撞与越权风险随模块数线性增长。
6. **模板表达力被运行时编译器约束**：可选链禁用，状态机/聚合数据的防御性取值只能靠 setup 里包一层函数（`HomePage.js:23-30`），样板代码膨胀。

> 结论：无构建「改 JS 刷新即生效」的零门槛调试是真实收益，但它在 D1=硬需求下已不可保留。S2 的正当性完全成立。

### 2.1 当前注册点（新增一个模块要改 5 处）

| # | 文件 | 位置（行号） | 作用 | 当前条目数 |
|---|---|---|---|---|
| ① | `router.js` | `initRouter()` 内 `registerRoute(...)` `:125-145` | hash 路由表 | 21 条 |
| ② | `index.html` | 业务页面区 `<script>` `:70-91` | 加载页面组件定义（须先于 `app.js`） | 21 个脚本 |

| ③b | `app.js` | `pageComponents` 对象 `:65-87` | `module key → 组件` 映射 | 21 条 |

| ⑤ | `HtpCommandPalette.js` | `COMMANDS` `:30-50` | Ctrl/Cmd+K 命令 | **仅 10 个导航覆盖**（缺 10 模块，P1-1） |

### 2.2 meta.js 单一数据源设计（分两阶段落地）

**目标**：S1 阶段把新增模块降到「写 meta.js + 加 1 个 index.html 脚本」两处；S2 阶段降到 0 处手工注册。

#### 2.2.1 每个模块声明 `meta.js`（字段清单）

```js
// frontend/js/modules/meeting/meta.js  （示意，非业务代码）
window.__htdModuleMetas = window.__htdModuleMetas || [];
window.__htdModuleMetas.push({
  key: 'meeting',                 // 必填，唯一；== router module == pageComponents key
  name: '会议纪要',               // 必填，导航/标题
  group: 'work',                  // 'work'|'life'|'knowledge'，侧边栏分组 + 首页栏
  icon: 'presentation',           // 必填：引用 icons.js 的 htdIcon key（禁裸 path / emoji，修 P0-1、P2-3）
  route: '/meeting',              // 必填，hash 路由
  view: () => MeetingPage,        // 组件引用（无构建期用全局变量；S2 改 import）
  capabilities: { hasDetail: false, hasReview: false },   // 驱动能力 Tab
  homeSummaryCard: {              // null=首页不出现；否则挂模块即出卡
    column: 'work', order: 4, render: 'recentMeeting',
  },
  commands: [                     // 并入命令面板，修复缺 10 模块问题
    { id: 'nav-meeting', label: '会议纪要', type: 'nav', path: '/meeting',
      typeLabel: '跳转', pinyinKeys: ['huiyi', 'hy', 'huiyijilu'] },
  ],
});
```

**字段约定要点**：
- `icon` 改为 **htdIcon key 字符串**（如 `'presentation'`），由壳统一 `htdIcon(meta.icon)` 渲染，彻底消除 NAV_ITEMS 内联 path 与命令面板私有 ICON 三套并存（P0-1/P2-3）。
- `commands` 随 meta 声明，由聚合器合并进命令面板 `COMMANDS`，从根上补齐 10 个缺失模块。

#### 2.2.2 S1（无构建）：手动聚合器派生四处注册

新建 `frontend/js/registry.js`，在所有 meta.js 之后、`app.js` 之前加载：

```js
// registry.js（示意）
(function () {
  const metas = window.__htdModuleMetas || [];
  const pageComponents = {};
  const NAV_ITEMS = [];
  const COMMANDS = [];
  metas.forEach((m) => {
    pageComponents[m.key] = m.view();                       // 派生 ③b
    NAV_ITEMS.push({ path: m.route, label: m.name, icon: m.icon }); // 派生 ③a（壳按 key 渲染 htdIcon）
    (m.commands || []).forEach((c) => COMMANDS.push(c));     // 派生 ⑤
    // ① 路由由 app.js 在 initRouter 时遍历 metas.registerRoute(m.route,{title:m.name,module:m.key})
  });
  window.__htdRegistry = { metas, pageComponents, NAV_ITEMS, COMMANDS };
})();
```

此时 `app.js` / `router.js` / `HtpCommandPalette.js` 改为**消费 `window.__htdRegistry`** 而非各自硬编码数组。新增模块 = 写 `MeetingPage.js` + 写 `meta.js` + 在 `index.html` 加 2 个 `<script>`（`MeetingPage.js` 与 `meta.js`）。即 **2 处**（符合 S1 出口判据，`docs/架构审计报告-重构候选方案.md:365`）。

#### 2.2.3 S2（Vite）：`import.meta.glob` 自动收集 → 0 处手工注册

```js
// src/registry.ts（示意，S2 阶段）
const metaModules = import.meta.glob('./modules/*/meta.ts', { eager: true });
const metas = Object.values(metaModules).map((m) => m.default);
// router / nav / pageComponents / COMMANDS 全部由 metas 派生，新增模块只需建目录+meta.ts
```

`index.html` 收敛为单个 `<script type="module" src="/src/main.ts">`（43 脚本消失）。

## 4. 图表层（charts.js）：可维护性与配色硬编码

### 4.1 现状

`utils/charts.js` 手写 SVG，全部函数返回字符串，调用方 `v-html` 注入（`charts.js:7-228`）。导出 `barChart / donutChart / lineChart / stackedBarChart / timelineChart / legend`。

### 4.2 问题证据

1. **主色板硬编码**：`charts.js:9` `PALETTE[0] = '#5B8DEF'`，其余 9 色 likewise 硬编码。
2. **各 Page 用 hex 覆盖 `var(--color-primary)` 致暗色/多外观失效（P0-2）**：
   - `FinancePage.js:340` `#34D399`、`:347` `#F87171`、`:365` `#5B8DEF`
   - `ProjectPage.js:446` `#34D399`、`:447` `#94A3B8`
   - `HomePage.js:112` `#22D3EE`、`:117` `#34D399`；`StudyPage.js:35` `#22D3EE`
   - `TimeBlockPage.js:152-155` `#3B82F6/#8B5CF6/#10B981/#64748B`；`:291` `#3B82F6/#ef4444`
3. **三套主蓝不统一**：`#5B8DEF`（`global.css:45`、`charts.js:9`、`FinancePage:365`、`app.js` logo 区附近）、`#3B82F6`（`app.js:33-34`、`global.css:60/67/76`、`TimeBlockPage:152`）、`#3D6EFF`（`HtpSelect.js:252-253`）。同一「品牌蓝」三处取值 → 视觉不一致。
4. **暗/亮主题令牌已存在却被图表绕过**：`frontend/themes/liquid-glass.theme.json:15` 暗色 `accent:#5B8DEF`、亮色 `#2F6BEE`（`notion-flat.theme.json:15` 同样）；`global.css:45` 亦定义 `--color-primary:#5B8DEF`。charts.js **从不读取这些令牌**，亮色主题下图表色仍是写死的暗色蓝。
5. **`lineChart` 已实现未挂载（P2-2 沉没成本）**：`charts.js:92-124` 完整实现，但全仓仅 `timelineChart` 被消费（`ProjectPage.js:439`），`lineChart` 零调用。
6. **机制债（P0-3）**：字符串 + `v-html` 全量重渲染，无法做力导向增量更新，1k 节点验收不可达。

### 4.3 统一方案

**短期（S1，无构建，修 P0-2）**：
- 图表颜色全部改为读 **CSS 变量**，建立 `--chart-1 … --chart-N` 系列（语义类别：成功/危险/信息/系列1~N），由 `theme-manager` 按外观注入（与 `themes/*.json` 的 `colorPalette` 对齐）。`charts.js` 的 `colorAt(i)` 改为返回 `var(--chart-{i+1})`；页面**不再传 hex**，只传语义 key（`'success' | 'danger' | 'series-3'`）。
- 收敛三套主蓝为单一令牌：以 `themes/*.json` 的 `accent` 为准，`global.css --color-primary`、`app.js` logo、`HtpSelect.js` 勾选 SVG 全部引用 `var(--color-primary)`，删除 `#3B82F6`/`#3D6EFF` 字面量。
- 删除未消费的 `lineChart`（或迁入统一组件待 S2 用）。

**中期（S2，修 P0-3）**：
- 图表从「字符串 + `v-html`」改为**真实 Vue 组件 + 响应式 SVG 节点**（或 Canvas），颜色绑 CSS 变量，节点用 `v-for` 渲染，可增量更新。
- 知识图谱引入 `d3-force`，布局计算与渲染解耦（sim 跑在 `requestAnimationFrame`，只更新 transform），配性能门槛测试：1k 节点 ≥30fps（中间）/60fps（验收）。

## 5. Vite 构建化可行性评估（关键）

> 前提：D1 已裁定硬需求 → S2 必做（`docs/产品迭代/V2.0-重构方向.md:182`）。以下评估按「方向 B」落地。

### 5.1 分阶段路径（先 S1 后 S2，顺序不可颠倒）

**Pre：S1（无构建，见 §2.2.2）** —— 先把 5 处注册点收敛为 `meta.js` 单一数据源。**必须在 S2 之前**，否则等于在「5 处漂移的注册点」上同时做 ESM 迁移，归因困难（`docs/架构审计报告-重构候选方案.md:369`）。

**S2 第 1 步：Vite + ESM 启动，功能等价（不加新功能）**
- `npm i vue pinia` 替代 3 个 global build；`index.html` 收敛为 `<script type="module" src="/src/main.ts">`。
- 页面模块从 `const X={...}; window.X=X` 改为 `export default`；`meta.js` 改 `export default`。
- `import.meta.glob('./modules/*/meta.ts', { eager:true })` 自动收集注册表（§2.2.3），router/nav/组件/命令面板全部派生。
- **是否引入 .vue SFC**：建议 S2 第 1 步**保留 JS 组件对象 + template 字符串**（机械平移、低风险、1:1 等价），SFC 作为后续可选打磨；两者 Vite 都支持。若用预编译模板，可选链约束自然消失（改用 `vue` 而非 runtime-only build）。
- dev server 配代理 `/api/v1` → 后端 `127.0.0.1:port`；产物 `base` 设为 `/`（pkg sidecar 静态托管 dist）。

**S2 第 2 步：图表/图谱机制替换**
- 图表改真实 Vue 组件（§4.3）；引入 `d3-force` 做知识图谱；先写**性能门槛 demo**（1k 节点）验证帧率，再做业务。

### 5.2 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| pkg/Tauri 资源分发变化 | 43 散文件 → 单 bundle `dist/`；pkg 须改为打包 `dist/` + `assets/` | 更新 `pkg` 的 `files` 包含 `dist`；`base:'/'` 让后端静态托管根可用 |
| 全局版 API 差异 | 无 `Vue.createApp` 全局，改 `import { createApp } from 'vue'`；Pinia 改 `import { createPinia }` | 代码量小，集中在 `main.ts`（原 `app.js`） |
| 运行时编译器移除 | 当前模板字符串依赖 global build 含编译器；Vite 默认预编译 | 用 `vue` 完整版或 `.vue` 文件；可选链等语法放开 |
| 构建产物体积 | 引入 d3-force(~50KB) + Vue/Pinia | Tree-shaking + **路由级代码分割**（`import()` meta.view）使首屏只载当前页，21 页不再全量 |
| 绝对路径/资源 | 字体、主题 JSON 引用路径在打包后需正确解析 | Vite `assetsInclude` + `publicDir` 托管 `themes/`、`fonts/` |
| TS 迁移成本 | 全量 TS 化工作大 | **渐进式**：先 Vite(JS)，再为 api 契约/store 补 TS，不强制一步到位 |

### 5.3 收益

- **Tree-shaking + 代码分割**：首屏体积下降，21 页按需加载。

## 6. 状态管理审计

### 6.1 现状

3 个 Pinia store：
- `app`（`appStore.js`）：导航/主题/版本/数据计数/settings。主题应用干净地委托 `theme-manager`（`appStore.js:50-64`）。
- `ui`（`uiStore.js`）：保存三态机，设计整洁（§1.2 已肯定）。
- `data`（`dataStore.js`）：**神 store**，855 行承载全部 16 模块 CRUD + `homeSummary` + `fieldConfig` + `statistics`。

### 6.2 问题

1. **`dataStore` 单体过大（P2-1）**：855 行、数十个 action 混于一文件；无模块切片，增删模块必改此文件（与 §2.1④ 耦合）。
2. **跨模块数据流动靠全局拿 store**：`dataStore.refreshAll()` 内部 `useAppStore().refreshDataCount()`（`dataStore.js:109-114`）——跨 store 调用通过全局 `useAppStore()` 而非注入。
3. **`fieldConfig` 隐式全局缓存（P1-5）**：模块级可变 `cache` + `loadingPromise`，正确性依赖调用方「记得先 await」；仅 3 模块调用。
4. **首页硬编码（§6.1⑥）**：`HomePage.js:20` 直接 `dataStore.homeSummary` 并深读 `home.work.todayProgress` / `home.life.financeMonth` 等固定路径，强耦合后端聚合形状，非 meta 驱动；新增模块首页卡需改模板（§2.1⑥）。

### 6.3 重构方向（Vite 化时）

- 将 `dataStore` 按业务域拆分为 `useProjectStore` / `useFinanceStore` / … 或保留单 store 但用**注册式 actions map**（模块 meta 声明自己 action）。
- 跨模块流（刷新全局计数、首页聚合）抽为 composable，显式传参而非全局 `useXStore()`。
- 首页三栏改为读 `meta.homeSummaryCard` 声明 → 渲染器分发，消除 `HomePage.js` 硬编码（呼应 §2.2.1）。
