# V2-2 · 异地备份方案（可选，默认关闭）

> 状态：**已交付（2026-09-13）**。backend 527/527、lint 46/46 全绿。
> 依赖：V2-3 加密（可选，用于上传前加密）；不依赖任何外部 npm 包。

---

## 1. 要解决什么

本地备份与数据库落在**同一块磁盘**上。磁盘故障、机器丢失、误格式化发生时，
「数据库 + 全部本地备份」会同时消失。

| 手段 | 保护的属性 | 能防 | 不能防 |
|---|---|---|---|
| 访问令牌 / Origin 校验（S4） | 访问控制 | 未授权访问 | 物理拿到磁盘 |
| 数据库加密（V2-3） | **机密性** | 磁盘被拿走后读不出数据 | 数据被毁、磁盘损坏 |
| **异地备份（本文）** | **可用性** | 本机数据全毁 | 机密性（需配合加密） |

**结论：加密与异地备份互补，不可互相替代。** 只做加密而不同步异地，
一次磁盘故障就同时失去数据与全部备份；只做异地而不加密，
等于把明文个人数据推到别人的服务器上。

## 2. 设计原则

| 原则 | 落地方式 | 为什么 |
|---|---|---|
| **默认完全关闭** | 未配置 `HTD_REMOTE_BACKUP_TARGET` 时零网络请求、零行为变化 | 纯本机用户与既有 524 个测试完全不受影响 |
| **错误配置必须暴露** | `isEnabled()` 只看「是否配置了 target」；target 填了不受支持的值（如 `s3`）会**报错**而非静默跳过 | 静默跳过会让用户误以为备份在跑实则没有——比报错危险得多 |
| **只上传，不下载** | 无下载 / 无远端恢复接口 | 恢复是高危操作，不应建立在网络可用性上；恢复走本地备份 |
| **只管理自己的文件** | 清理只匹配 `workbench_daily-*`；手动备份与其它文件一律不碰 | 远端目录可能与他人共用（NAS / 网盘） |
| **先成功后记状态** | 上传成功才写「今日已同步」 | 任何失败都不会让远端处于比之前更差的状态 |
| **失败不外泄** | `maybeSyncFireAndForget()` 捕获一切异常，只写状态与日志 | 网络抖动绝不能拖慢业务写入请求 |
| **状态不含凭据** | `getStatus()` 只回显 target / dir / keep / encrypted | 状态会经 API 暴露给前端 |

### 硬约束（改动此模块时请一并遵守）

1. **上传前校验 SQLite 魔数头**。损坏的本地备份若被推上远端并覆盖好备份，
   结果是「本地坏了 + 远端也坏了」——这是本服务最危险的失败模式，故直接拒绝上传。
2. **启用加密后必须上传密文**（见 §3）。
3. 任何网络 / 配置异常都不得抛出到业务主流程。

## 3. 与 V2-3 加密的协同（重要）

启用加密后，备份复制的是**运行期明文库**（`data/workbench.db`）。
若直接上传，等于把明文推到云端，V2-3 的保护在数据离开本机的瞬间失效。

**处置**：`server.js` 在解锁数据库后把主密码注入异地备份服务
（`remoteBackupService.setPassphrase(...)`）。一旦注入：

- 上传前先用同一主密码加密为临时 `.enc`（复用 `lib/crypto.js` 信封格式，每次随机 salt）
- 远端文件名带 `.enc` 后缀（如 `workbench_daily-20260913_010000.db.enc`）
- 临时文件用完即删，不在磁盘留第二份
- `getStatus().encrypted === true`，可据此确认「异地是密文」

未启用加密时行为不变（上传明文 `.db`，与本地备份一致）。

> ⚠️ **已知缺口（未修，需后续工单）**：
> 启用加密后，**本地** `backups/` 下的每日备份仍是明文副本
> （备份服务复制的是运行期明文库）。它们受磁盘/文件系统权限保护，
> 但与「磁盘只留密文」的目标不一致。修复需把主密码线程进 `backup.service`，
> 并调整备份命名与恢复流程，影响面较大，故单独立项。
> **当前风险可控**：异地副本是密文，本地明文备份未离开本机。

## 4. 配置

不配置即关闭。配置写在 `deploy/server.env`（模板见 `deploy/server.env.example`）。

### 目标一：本机另一块盘 / 网络共享（推荐先用它跑通）

```
HTD_REMOTE_BACKUP_TARGET=local
HTD_REMOTE_BACKUP_PATH=E:\htd-offsite      # 或 \\NAS\backup
```

### 目标二：WebDAV（坚果云 / 群晖 / Nextcloud / ownCloud）

```
HTD_REMOTE_BACKUP_TARGET=webdav
HTD_REMOTE_BACKUP_URL=https://dav.jianguoyun.com/dav/
HTD_REMOTE_BACKUP_USER=your-account
HTD_REMOTE_BACKUP_PASS=your-app-password   # 建议用应用专用密码
```

### 通用项

| 变量 | 默认 | 说明 |
|---|---|---|
| `HTD_REMOTE_BACKUP_DIR` | `htd-backups` | 远端子目录，本应用只在其中活动 |
| `HTD_REMOTE_BACKUP_KEEP` | `30` | 远端保留份数（仅清理每日备份） |

> S3 **暂未实现**。若误填 `s3` 会明确报「不支持的异地备份目标」，不会静默跳过。

## 5. 触发时机与保留策略

- **触发**：每日自动备份成功后异步触发（fire-and-forget），每天最多一次
  （状态记录在 `<dataRoot>/remote-backup-state.json`）。
- **保留**：清理时只删 `workbench_daily-*.db[.enc]`，按文件名排序
  （daily 命名含 `YYYYMMDD_HHmmss`，字典序即时间序；远端 mtime 未必可靠）。
  手动备份永久保留，与本地策略一致。

## 6. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/system/backups/remote` | 状态（enabled/target/dir/keep/encrypted/lastUploaded…），不含凭据 |
| POST | `/api/v1/system/backups/remote/check` | 连通性自检（列举远端目录） |
| POST | `/api/v1/system/backups/remote/sync` | 立即同步一次（忽略当日节流） |

## 7. 验证记录（2026-09-13）

单测 14 例（`remote-backup.test.js`），其中 webdav 适配器跑**真实 HTTP mock 服务器**
（PUT / PROPFIND / DELETE）而非 stub：

| 场景 | 结果 |
|---|---|
| 未配置 target：不发任何网络请求 | 通过（注入会抛错的 fetchImpl） |
| target 填 `s3` | 报「不支持的异地备份目标」，不静默跳过 |
| 上传最新备份（local） | 远端文件名与本地一致 |
| 本地备份损坏 | 拒绝上传，远端不产生文件 |
| 清理 | 只删 daily，手动备份与他人文件保留 |
| 每日节流 | 第二次调用返回 `already-synced-today` |
| webdav 上传 / 列举 / 删除 | 通过（真实 HTTP） |
| webdav 5xx | 报错且状态置 error |
| fire-and-forget 失败 | 不抛出，只记状态 |
| **注入主密码后上传密文** | 远端无明文、内容不含 SQLite 魔数、可解密回原库 |
| 加密临时文件清理 | 上传后磁盘无残留 |
| 状态接口不含凭据 | url / user / pass 均不出现在返回中 |

## 8. 已知限制

1. **本地备份仍是明文**（见 §3 缺口）——需单独立项修复。
2. 上传为一次性读取整个文件到内存（未做流式）。个人库量级（数十 MB）无压力，
   若库增长到 GB 级需改为流式上传。
3. 远端无内容校验（不回读比对）。依赖「上传成功即完整」的 HTTP 语义；
   如需更强保证，可增加 `Content-Length` 校验或定期 `check()`。
4. 不支持断点续传与增量备份——每日全量，简单可靠优先。
