# 后端系统化设计（后端工程总纲）

> **本文档定位**：荒天帝工作台后端工程的"宪法"——定义后端的哲学、分层架构、数据契约、接口规范、业务基线、工程质量标准和版本演进规则。
> **不绑定任何具体版本或功能**。无论是 V1.2、V2.0 还是未来某个版本，无论是做备份升级还是做 Agent 协作，后端开发都必须先遵守本总纲，再做具体实现。
>
> **后端特性**：桌面单机后端（pkg 单文件 exe + SQLite 嵌入 + 无鉴权 + 绑定 127.0.0.1），不是传统服务端。所有设计选择都从这个特性推导，详见 § 1.0 项目定位。
>
> **文档关系**：
> - **本文件**：后端总纲（怎么思考后端 / 必须遵守的基线 / 版本无关）
> - [前端系统化设计.md](./前端系统化设计.md)：前端宪法（前端哲学/7层架构/设计系统/交互基线）
> - [产品迭代演进计划.md](./产品迭代演进计划.md)：版本规划（每个版本做什么 / 版本特有）
> - 视觉规范见对应版本文件（如 v1.1 的 [v1.1 - 视觉-LiquidGlass.md](../v1.1 - 视觉-LiquidGlass.md)）

### 0.1 给新 AI 的阅读顺序

```

第5步：§ 9 实操指南     → 拿到版本任务后怎么用本总纲（3分钟）
然后：去读 [产品迭代演进计划.md](./产品迭代演进计划.md) 看当前版本具体做什么
```

### 0.2 本文档不是什么

- ❌ 不是 V1.2（或任何版本）的 todo list——那在演进计划里
- ❌ 不是 API 文档——接口契约是稳定的，具体参数由代码自文档化
- ❌ 不是 Prisma schema 文档——schema 定义在代码里，这里只定义规范
- ❌ 不是一成不变的——随着版本演进可以修订，但修订必须走 § 8.5 的修订流程

### 0.3 核心心智模型

**先奠基，再盖楼**。

任何后端工作（新功能、新模块、重构、优化）都从这三个问题开始：

1. **它属于哪一层？**（L1-L6）
2. **它是否遵守了该层的基线？**
3. **它的数据契约是否稳定？**

只有回答完这三个问题，才能开始写代码。

## 1. 后端哲学（永远不变的基调）

> 这一节定义后端的"世界观"。所有技术选型、架构设计、接口设计，都从这些原则推导出来。

### 1.0 项目定位（哲学推导的根基）

**这是桌面单机后端，不是传统服务端**。以下特性决定了后端的所有设计选择：

| 特性 | 本项目 | 传统服务端 |
| --- | --- | --- |
| 部署形态 | pkg 打包单文件 exe，用户双击运行 | Docker / 服务器部署 |
| 数据库 | SQLite 单文件嵌入 | MySQL / PostgreSQL 服务 |
| 鉴权 | 无（本机即权限边界） | JWT / OAuth / Session |
| 监听 | `127.0.0.1:port`，不暴露局域网 | `0.0.0.0:port`，公网可达 |
| 并发模型 | 单进程 + SQLite 单写者 | 多进程 / 多实例 |
| 配置 | 文件 + 启动参数 | 环境变量 + 配置中心 |
| 升级 | 用户替换 exe，启动自迁移 | 滚动发布 / 蓝绿部署 |

**推导**：不要引入 helmet / CSRF / rate limiting / JWT / Redis / 微服务——这些是服务端方案，单机用不上。当前实际版本/功能/模块清单见 [记录 - 版本更新.md](../记录 - 版本更新.md) 和 [记录 - 开发进度.md](../记录 - 开发进度.md)。

### 1.1 核心设计原则

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| **本地优先** | 数据 100% 本地，备份/迁移/销毁完全可控 | 数据隐式上传到云端，用户不知情 |
| **离线可用** | 所有必做功能断网可用，网络不是前置条件 | 断网后核心功能全部报错不可用 |
| **数据自主** | 用户随时能迁移/销毁数据，不隐式上传 | 数据存在私有格式里用户无法导出 |
| **数据完整性** | 任何操作不破坏数据一致性，事务兜底 | 跨表更新部分成功导致脏数据 |
| **契约稳定** | API 响应格式/错误码/字段命名不随版本随意变更 | 同一个接口在 V1.2 和 V1.3 字段名变了 |
| **幂等设计** | 同一操作执行一次和多次效果相同 | 重复点击导致创建多条重复记录 |
| **失败可恢复** | 任何失败不丢数据，有兜底：备份/回滚/重试 | 备份中断后数据库损坏无法回退 |
| **可观测性** | 任何操作有日志，任何错误可追溯，任何状态可查询 | 出了问题却查不到任何日志线索 |
| **最小权限** | 绑定 127.0.0.1，不暴露不必要的端口/接口/字段 | 服务监听 0.0.0.0 暴露到局域网 |
| **性能即体验** | API P95 < 200ms，DB 查询 < 50ms，启动 < 3s | 列表接口响应 2 秒，启动卡 10 秒 |

### 1.2 可靠感的来源

可靠不是"不报错"，而是**所有"用户能感觉到但说不清"的稳定性细节都做对了**：

- **错误码可读**：前端按 code 查用户文案，不是堆技术栈信息
- **日志有上下文**：每条日志带模块名/操作/关键参数
- **接口契约稳定**：加字段不删字段，改类型走版本化
- **迁移有回滚**：schema 变更必须可逆，有备份兜底
- **慢查询有兜底**：分页上限 100，全量查询有缓存或拒绝
- **事务不漏**：跨表操作必须包在 `$transaction` 里
- **软删除不丢**：`deletedAt` 而非 `DELETE`，可恢复
- **启动有自检**：目录/DB/备份/端口/前端资源全检查

### 1.3 技术选型原则

- **少即是多**：能不引入新依赖就不用；能用现有库解决就不加新库
- **可替换性**：所有外部依赖通过 Repository 层隔离，ORM 可替换、日志库可替换
- **渐进式**：不一次性引入完整框架（如不直接上 NestJS），按需演进
- **构建最小化**：pkg 打包保持单文件 exe，启动自包含，不依赖外部运行时
- **依赖审计**：任何新依赖必须评估：包大小、维护状态、安全记录、是否真的需要

### 1.4 后端禁忌清单（不能做什么·集中清单）

> 这一节把分散在各处的"不能做"集中起来，让新 AI 一眼看到红线。任何版本都不允许突破。

**部署与监听**：
- ❌ 不监听 `0.0.0.0`，必须绑定 `127.0.0.1`（不暴露到局域网）
- ❌ 不引入需要外部服务的部署形态（Docker / k8s / 微服务 / 云函数）
- ❌ 不引入 Redis / Memcached 等外部缓存服务（保持单机无外部依赖）
- ❌ 不引入 PostgreSQL / MySQL（数据自主性要求 SQLite 单文件）

**鉴权与安全**：
- ❌ 不引入 JWT / OAuth / Session 鉴权（单机定位，本机即权限边界）
- ❌ 不引入 helmet / CSRF 防护 / rate limiting（单机无外部流量）
- ❌ 不在日志中打印敏感字段值（凭据明文、加密密钥、内部标志位）
- ❌ 不在任何接口返回密码字段，即使存在也不返回
- ❌ 不裸接收外部输入，必须过 Zod 校验

**数据访问**：
- ❌ Service 不直接调 Prisma，必须经 Repository（数据访问统一出口）
- ❌ Controller 不写业务逻辑，业务规则集中在 Service
- ❌ 不物理 `DELETE` 业务数据，软删除设置 `deletedAt`
- ❌ 跨表写操作不包在 `$transaction` 里（破坏数据完整性）
- ❌ 事务内不做文件读写、网络请求等慢操作（避免长事务）

**错误处理**：
- ❌ 不直接 `console.log`，必须用统一 logger
- ❌ 不裸 `throw new Error()`，必须用 `throw new BusinessError(code, msg)`
- ❌ 不返回非 `{code, msg, data}` 格式的响应
- ❌ 不返回未在 `toPublic()` 白名单的敏感字段

**契约与兼容**：
- ❌ 不删除已发布的 API 字段（加不删原则，废弃走 § 8.4 流程）
- ❌ 不改已发布字段的类型（类型变更走版本化升 v2）
- ❌ 不直接改数据库结构（必须走迁移流程，可逆 + 备份）
- ❌ 不占用已用的错误码段位

**依赖与构建**：
- ❌ 不引入 helmet / CSRF / JWT / Redis 等服务端方案（见 § 1.0 项目定位）
- ❌ 不一次性引入完整框架（如 NestJS），按需演进
- ❌ 不引入无法打包进 pkg 单文件 exe 的依赖（破坏交付形态）
- ❌ 不绕过 ESLint 提交代码（不允许 error）

## 2. 后端分层架构（6 层金字塔）

> 后端从地基到交付分为 6 层。**上层依赖下层，下层不感知上层**。
> 新功能开发从底层往上层做：先确认 L1-L3 满足，再做 L4-L5，最后做 L6。

```
         ┌─────────────┐
         │ L6 集成交付  │  ← 用户拿到的可执行文件
         ├─────────────┤
         │ L5 接口契约  │  ← 前端能调用的 API
         ├─────────────┤
         │ L4 领域服务  │  ← 业务逻辑的所在
         ├─────────────┤
         │ L3 数据持久  │  ← 数据怎么存、怎么迁移
         ├─────────────┤
         │ L2 基础设施  │  ← 日志/配置/错误处理/启动流程
         ├─────────────┤
         │ L1 工程规范  │  ← 代码怎么写、质量怎么保证
         └─────────────┘
```

### 2.1 L1 · 工程规范层

**职责**：定义代码怎么写、质量怎么保证、团队怎么协作。这一层是"开发体验"和"代码一致性"的基础。

**核心内容**：
- 代码规范（ESLint/命名约定/文件结构约定）
- Git 工作流（分支策略/commit 规范/PR 流程）
- 目录结构约定（每模块 6 文件结构）
- 测试策略（单元/集成/E2E 的测试金字塔）
- 构建与打包规范
- 文档要求（新模块必须写什么）

**基线要求**（任何版本都必须满足）：
- 所有代码通过 Lint，无 error，warning 逐条确认
- 新模块必须遵循 6 文件结构（router/controller/service/repository/schema/test）
- 提交信息符合 `type: description` 格式
- 新文件放在正确的目录，不乱放

**演进规则**：L1 随版本演进不断完善规范，但**不允许已确立的规范被回退**。

---

### 2.2 L2 · 基础设施层

**职责**：提供后端运行的"水电煤"——日志、配置、错误处理、中间件、启动流程，让业务代码写得简洁可靠。

**核心内容**：
- 日志系统（Winston，分级日志，带上下文，文件轮转）
- 配置管理（环境变量/默认值/启动参数）
- 错误处理（BusinessError 类 + errorHandler 中间件）
- 通用中间件（CORS/body-parser/请求日志/超时）
- 启动流程（目录自检/DB 连接/备份/端口顺延/前端资源检查/自动开浏览器）
- 优雅关闭（信号捕获/连接清理/进程退出）
- 通用工具函数（日期格式化/ID 生成/路径校验/加密等）

**基线要求**：
- 所有日志通过统一 logger，禁止直接 `console.log`
- 所有业务错误通过 `throw new BusinessError(code, msg)`，禁止裸 throw
- 启动时必须完成全部自检项，任何一项失败都有明确处理
- 进程退出前清理数据库连接、刷新日志

**演进规则**：基础设施**持续积累、可复用、与业务解耦**。新业务发现重复模式时，抽到 L2。

---

### 2.3 L3 · 数据持久层

**职责**：定义数据怎么存、怎么迁移、怎么访问。这一层是"数据完整性"和"性能"的根基。

**核心内容**：
- Prisma ORM（schema 定义/客户端实例化/连接管理）
- Schema 规范（model 命名/通用字段/索引/JSON 字段）
- 迁移策略（模板库 + 启动复制；V1.2+ 评估 Prisma Migrate）
- BaseRepository（通用 CRUD/软删除过滤/分页/排序/批量操作）
- 软删除机制（`deletedAt` 全局生效，BaseRepository 默认过滤）
- 备份恢复（启动自动备份/手动备份/保留策略/恢复前安全备份/完整性校验）

**基线要求**：
- 所有数据访问通过 Repository，禁止 Service 直接调 Prisma
- 所有 model 必须有 `id(cuid)/createdAt/updatedAt/deletedAt` 通用字段
- 所有写操作前自动备份，迁移必须可逆
- 软删除全局生效，查询默认排除已删除记录

**演进规则**：L3 是数据契约的根基，**变更必须走迁移流程，不允许直接改库结构**。schema 变更必须可回滚。

---

### 2.4 L4 · 领域服务层

**职责**：承载业务逻辑，是"领域知识"的所在。校验输入、编排事务、跨模块调用都在这一层。

**核心内容**：
- Service 类（每模块一个，单例导出 `export default new XxxService()`）
- 业务逻辑（领域规则/状态机/计算/转换）
- Zod 校验（输入校验在 `*.schema.js` 定义，Service 层 `.parse()` 调用）
- 事务边界（跨表操作 `$transaction`，Service 方法即事务边界）
- 跨模块调用（Service 之间可互引用，但避免循环依赖）
- DTO 转换（`toPublic()` 白名单导出，敏感字段不返回）

**基线要求**：
- 所有业务规则集中在 Service，Controller 不写业务逻辑
- 所有输入通过 Zod 校验，禁止裸接收未校验数据
- 跨表写操作必须包在 `$transaction` 里
- 所有领域对象提供 `toPublic()` 方法，敏感字段不外泄

**演进规则**：L4 随业务复杂度增长而增强。简单版本可以先简化实现，但**Service 即事务边界、输入必校验的思路必须从第一天就遵守**。

---

### 2.5 L5 · 接口契约层

**职责**：定义前端能调用的 API，是前后端协作的"合同"。响应格式、错误码、分页、版本化都在这一层。

**核心内容**：
- RESTful 路由（复数名词/标准 CRUD/自定义动作/统计路由）
- 统一响应格式（`{code, msg, data}` + `res.success/res.fail`）
- 错误码体系（0/1xxx/2xxx/3xxx/4xxx 分段编码）
- 分页规范（`{list, total, page, pageSize, totalPages}`，默认 page=1, pageSize=20, max=100）
- API 版本化（`/v1` 前缀，字段兼容：加不删）
- Controller 层（薄层，只做参数提取/调 Service/格式化响应）

**基线要求**：
- 所有接口返回统一 `{code, msg, data}` 格式
- 所有错误通过 errorHandler 中间件统一处理，返回明确 code
- 所有列表接口支持分页，pageSize 上限 100
- 路由按模块注册，统一挂载到 `/api/v1` 前缀下

**演进规则**：L5 是前后端契约，**接口契约一旦发布就不能随意破坏**。字段加不删，类型变更走版本化，废弃走 § 8.4 流程。

---

### 2.6 L6 · 集成交付层

**职责**：定义后端怎么打包、怎么部署、怎么被用户使用。这一层是"交付物"。

**核心内容**：
- 打包构建（pkg 打包为单文件 exe，esbuild 打包入口）
- 模板库机制（DB 模板/配置模板，启动时复制，非 Prisma Migrate）
- 进程管理（单进程/端口顺延/单实例锁）
- 可观测性（日志文件/启动自检报告/健康检查）
- 安全边界（绑定 127.0.0.1/最小端口暴露/无鉴权单机定位）
- 桌面集成（自动开浏览器/系统托盘/优雅关闭）

**基线要求**：
- 打包产物为单文件 exe，双击即可运行，无需安装运行时
- 启动自检覆盖：目录/DB 文件/备份/端口/前端资源
- 端口被占时自动顺延，不直接报错退出
- 优雅关闭：捕获 SIGINT/SIGTERM，清理连接后退出

**演进规则**：V1.x 保持 pkg 单文件 exe + SQLite 嵌入式定位；V2.0 评估 Tauri 集成与跨平台分发。**桌面单机定位是基线，不引入需要外部服务的部署形态**。

---

### 2.7 层间依赖规则

```
L6 集成  ──依赖──→ L5 接口 ──依赖──→ L4 领域 ──依赖──→ L3 数据
                                                      │
                                                      ▼
                    L4-L5 消费，不感知 ──→ L2 基建 ──依赖──→ L1 规范
```

- **上层依赖下层**：L6 可以引用 L5-L1 的所有东西，L1 不能引用任何上层
- **同层可互引用**：同一层内的模块可以互相依赖（如 Service 之间可互调，Repository 之间可组合查询）
- **跨层不跳级**：Controller 不直接调 Prisma（必须经 Service→Repository）；Service 不直接管打包（那是 L6）
- **数据契约贯穿所有层**：Schema（L3）→ DTO（L4）→ 响应格式（L5），契约从底到顶一致，`toPublic` 在 L4 转换、L5 透出

## 3. 数据契约系统

> 数据契约是后端的"语言"，确保数据从存储到接口的每一层表达一致：Schema（L3）→ DTO（L4）→ 响应格式（L5）。

### 3.1 Schema 规范

**Prisma model 命名**：
- model 名用 PascalCase（如 `Project`、`ReviewItem`）
- 表名用 snake_case 并通过 `@@map` 显式映射（如 `@@map("review_items")`）
- 字段名用 camelCase（如 `createdAt`），列名通过 `@map` 映射为 snake_case（如 `@map("created_at")`）

**通用字段**（所有业务 model 必须包含）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String @id @default(cuid())` | 主键，cuid 生成，不暴露自增序号 |
| `createdAt` | `DateTime @default(now())` | 创建时间 |
| `updatedAt` | `DateTime @updatedAt` | 更新时间，Prisma 自动维护 |
| `deletedAt` | `DateTime?` | 软删除标记，null 表示未删除 |
| `sortOrder` | `Int @default(0)` | 排序权重（如需排序的 model） |

**索引规范**：
- 常用查询字段必加索引（如 `userId`、`projectId`、`status`）
- 软删除过滤字段组合索引（如 `@@index([projectId, deletedAt])`）
- 外键字段必加索引
- 唯一约束用 `@unique`（如 `(projectId, name)` 联合唯一用 `@@unique`）

**JSON 字段约定**：
- SQLite 不支持原生 JSON 类型，用 `String` 存储
- Service 层负责 `JSON.parse()` 读取、`JSON.stringify()` 写入
- 读取时 try-catch，损坏数据降级为默认值，不抛错阻断

### 3.2 迁移策略

**当前策略（V1.x）：模板库 + 启动复制**

```
模板库（templates/）           实际 DB（data/）
┌──────────────┐  启动时检测   ┌──────────────┐
│ template.db  │ ──缺失则复制→ │ app.db       │
│ schema 定义  │              │ 用户数据     │
└──────────────┘              └──────────────┘
```

- schema 变更通过修改模板库 + 启动复制逻辑实现
- 已存在的 DB 通过启动时的 schema 升级脚本增量修改
- 迁移前必须自动备份当前 DB

**V1.2+ 评估：Prisma Migrate**
- 评估引入 `prisma migrate` 管理迁移历史
- 评估 `migrations/` 目录记录每次 schema 变更
- 评估迁移可回滚的标准化流程

**迁移硬规则**：

1. **迁移必须可逆**：每个 schema 变更必须有对应的回滚方案
2. **迁移前自动备份**：任何 schema 变更前，自动备份当前 DB 到 `backups/`
3. **迁移有完整性校验**：迁移后校验数据完整性，失败则回滚 + 恢复备份
4. **迁移不打断启动**：迁移失败时降级为只读模式或提示用户，不直接崩溃

### 3.3 DTO 命名规范

**toPublic 白名单导出**：
- 每个领域对象（model 实体）必须有 `toPublic()` 方法
- `toPublic()` 只返回前端需要的字段，敏感字段（如密码、内部状态）不返回
- 转换在 Service 层完成，Controller 直接透传

**字段命名约定**：

| 层 | 命名风格 | 例子 |
| --- | --- | --- |
| Prisma model | PascalCase | `Project` |
| 数据库表/列 | snake_case | `review_items`、`created_at` |
| API 响应字段 | camelCase | `createdAt`、`projectId` |
| Zod schema 字段 | camelCase | `pageSize`、`sortOrder` |

**敏感字段不返回**：
- 凭据明文、加密密钥、内部标志位不进入 `toPublic()`
- 用户密码字段即使存在也不在任何接口返回
- 日志中不打印敏感字段值

### 3.4 错误码体系

**分段编码**（实际定义见 [errorCodes.js](../../backend/src/common/constants/errorCodes.js)）：

| 段位 | 含义 | 实际编码 |
| --- | --- | --- |
| `0` | 成功 | `0` SUCCESS |
| `1xxx` | 通用错误 | `1000` 未知错误 / `1001` 参数错误 / `1002` 资源不存在 / `1003` 无权限 / `1004` 服务器错误 / `1005` 请求频繁 |
| `2xxx` | 数据库错误 | `2000` 数据库错误 / `2001` 数据不存在 / `2002` 数据已存在 / `2003` 数据约束冲突 |
| `3xxx` | 业务错误 | `3000` 业务处理失败 / `3001` 数据无效 / `3002` 数据已过期 / `3003` 数据已锁定 |
| `4xxx` | 文件错误 | `4000` 文件操作失败 / `4001` 文件过大 / `4002` 格式不支持 / `4003` 文件不存在 |

> ⚠️ **新增错误码必须**：① 在 `errorCodes.js` 的 `ErrorCodes` 和 `ErrorMessages` 同步登记 ② 不占用已用段位 ③ 同步前端 i18n 文案表

**BusinessError 类**：
- 所有业务错误通过 `throw new BusinessError(code, msg, data?)` 抛出
- `data` 可选，携带补充信息（如校验失败的字段列表）
- errorHandler 中间件统一捕获，转换为 `{code, msg, data}` 响应

**errorHandler 中间件**：
- 捕获 `BusinessError` → 按 code/msg 返回
- 捕获 Prisma 错误 → 映射到 2xxx 段
- 捕获未知错误 → 返回 `1000` 通用错误 + 记录完整堆栈到日志
- 所有错误都记日志，带请求上下文（method/url/params）

**前端 i18n 映射**：
- 前端按 code 查 i18n 文案表，展示用户可读文案
- 后端只返回 code + 技术性 msg，不返回面向用户的中文长文案
- 新增错误码必须同步前端 i18n 表

### 3.5 API 版本化

**当前策略**：
- 所有接口挂载在 `/api/v1` 前缀下
- 大版本升级时引入 `/api/v2`，旧版本至少保留一个版本周期

**版本升级策略**：
- 破坏性变更（删字段/改类型/改语义）才升大版本
- 兼容性变更（加字段/加接口）不升版本
- 升版本时新旧版本可并存，通过路由前缀区分

**字段兼容规则**：
- **加不删**：可以新增响应字段，不能删除已发布字段
- **改类型走版本化**：字段类型变更必须升版本，旧版本保持原类型
- **废弃流程**：废弃字段走 § 8.4 流程（标记 → 提供替代 → 保留 → 移除）

**废弃流程**：
1. 标记 `@deprecated`，响应中仍返回但文档标注废弃
2. 提供替代字段或接口
3. 至少保留一个完整版本周期
4. 在版本更新记录中说明
5. 下个大版本移除

## 4. 接口设计基线

> 接口是前后端的合同。本节定义接口怎么设计才稳定、一致、可预测——前端可以信赖的"契约"。

### 4.1 RESTful 约定

**路由命名**：
- 复数名词：`/api/v1/projects`、`/api/v1/credentials`
- 标准 CRUD：
  - `GET    /projects`        列表
  - `GET    /projects/:id`    详情
  - `POST   /projects`        创建
  - `PUT    /projects/:id`    更新
  - `DELETE /projects/:id`    删除（软删除）
- 自定义动作用 `POST /:id/action`：`POST /projects/:id/archive`
- 统计类路由放 `/:id` 之前避免冲突：`GET /projects/stats`（不能被 `/:id` 匹配）

**路由组织**：
- 每模块一个 router（`xxx.router.js`），统一挂载到 `/api/v1`
- 路由只做参数提取和调 Controller，不写业务逻辑
- 中间件按需挂载（认证/限流/日志），不在路由里写

### 4.2 统一响应格式

**响应结构**：

```json
{
  "code": 0,
  "msg": "success",
  "data": { /* 业务数据 */ }
}
```

- `code`：0 表示成功，非 0 表示错误（见 § 3.4 错误码体系）
- `msg`：技术性消息（前端可忽略，用 i18n 文案展示给用户）
- `data`：业务数据，成功时为实际数据，失败时为 `null` 或错误补充信息

**辅助方法**：
- `res.success(data, msg?)` → `{code: 0, msg, data}`
- `res.fail(code, msg, data?)` → `{code, msg, data}`

**分页格式**：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "pageSize": 20,
    "totalPages": 5
  }
}
```

**分页默认值**：

| 参数 | 默认值 | 上限 |
| --- | --- | --- |
| `page` | 1 | - |
| `pageSize` | 20 | 100 |
| `max` | - | 100（硬上限，超过截断） |

### 4.3 输入校验

**Zod schema 定义**：
- 所有输入校验 schema 在 `xxx.schema.js` 文件定义
- Service 层调用 `schema.parse(input)` 进行校验
- 校验失败抛出 ZodError，errorHandler 映射为 `1001` 参数校验失败

**通用 schema 复用**：

| 通用 schema | 用途 | 约束 |
| --- | --- | --- |
| `idSchema` | 主键校验 | 非空字符串 |
| `paginationSchema` | 分页参数 | page≥1, pageSize 1-100 |
| `dateStringSchema` | 日期字符串 | ISO 格式校验 |
| `sortOrderSchema` | 排序参数 | field + order(asc/desc) |

**校验硬规则**：

1. 所有外部输入必须过 Zod 校验，禁止裸接收
2. schema 与 Prisma model 字段对应，但可更严格（如密码长度）
3. 校验在 Service 层入口完成，Controller 不重复校验
4. 复用通用 schema，不每模块重写分页/ID 校验

### 4.4 批量操作

**批量路由约定**：
- 批量创建/更新/删除统一用 `POST /batch-action`
- 请求体携带操作类型和目标列表
- 事务保证原子性：全成功或全回滚

**批量删除示例**：
- `POST /api/v1/projects/batch-action`
- body: `{ "action": "delete", "ids": ["1", "2", "3"] }`
- 响应：`{ "code": 0, "data": { "affected": 3 } }`

**批量操作硬规则**：

1. 批量操作必须包在 `$transaction` 里，原子性保证
2. 批量上限 100 条，超过拒绝并提示分批
3. 返回实际影响数量，不返回每条详情（避免响应过大）
4. 软删除的批量删除同样设置 `deletedAt`，不物理删除

## 5. 业务交互基线

> 本节定义后端业务操作的稳定性基线——事务、并发、软删除、导入导出、备份恢复。

### 5.1 事务边界

**事务硬规则**：

1. **跨表操作必须 `$transaction`**：涉及多表写入的操作必须包在事务里
2. **Service 方法即事务边界**：一个 Service 方法要么全成功要么全回滚
3. **嵌套调用由最外层控制事务**：内层 Service 调用不自己开事务，由最外层 Service 统一管理
4. **事务内不调用外部 IO**：事务里不做文件读写、网络请求等慢操作，避免长事务

**事务示例**：
```
Service.createProject() {
  $transaction {
    Repository.createProject()        // 写 projects 表
    Repository.initDefaultReviews()   // 写 reviews 表
    Repository.createProjectConfig()  // 写 configs 表
  }
  // 任一失败则全部回滚
}
```

### 5.2 并发控制

**SQLite 单写者特性**：
- SQLite 同一时刻只允许一个写操作，写操作会加锁
- 长写操作会阻塞其他写，需控制事务粒度
- 读操作不阻塞（WAL 模式下读写并行）

**长任务处理**：
- 长任务（备份/导入/导出）不阻塞主线程，异步执行
- 主线程立即返回任务 ID，前端轮询查询进度
- 进度查询用轮询退避：800ms → 1600ms → 3200ms → 4800ms 封顶

**并发硬规则**：

1. 长任务异步化，主接口不阻塞
2. 任务状态可查询（pending/running/done/failed）
3. 同类任务串行执行（如同时只跑一个备份），避免资源竞争
4. 任务可取消（如用户主动中止导入）

### 5.3 软删除策略

**软删除全局生效**：
- 所有业务 model 有 `deletedAt` 字段
- 删除操作设置 `deletedAt = now()`，不物理 `DELETE`
- BaseRepository 查询默认过滤 `deletedAt IS NULL`

**关联删除**：
- 一对多关系：父删除时子记录级联软删除（Cascade 或手动遍历）
- 手动级联必须包在事务里
- 关联表的软删除要考虑引用完整性（如项目删除，关联的复盘也要删除）

**回收站功能**：
- 基于软删除实现回收站
- 回收站查询 `deletedAt IS NOT NULL` 的记录
- 支持恢复（`deletedAt = null`）和彻底删除（物理 `DELETE`）
- 彻底删除前二次确认

**软删除硬规则**：

1. 所有业务 model 必须支持软删除
2. 普通查询默认排除已删除记录，需显式参数才查回收站
3. 唯一约束要考虑软删除（如名称重复校验时排除已删除记录）
4. 彻底删除是显式操作，不自动触发

### 5.4 数据导入导出

**导出规范**：
- 导出全表 JSON，包含所有字段（含 `id`、`createdAt` 等）
- 导出文件为 JSON 格式，带版本号和时间戳
- 大表导出异步执行，返回任务 ID

**导入规范**：
- 支持三种模式：
  - `skip`：已存在的跳过
  - `overwrite`：已存在的覆盖
  - `full`：清空后全量导入
- 导入前校验数据格式，损坏数据拒绝并报告
- 导入在事务里执行，失败回滚

**清空规范**：
- 按业务域 scope 分组（如 projects / reviews / credentials 分别清空）
- 清空是软删除（设置 deletedAt），不是物理删除
- 清空前自动备份

**路径穿越防护**：
- 所有文件路径操作校验 `..` 和绝对路径
- 导入导出文件路径限制在 `data/` 目录内
- 正则校验：`/^[\w\-/]+\.(json|db)$/`，拒绝非法字符

### 5.5 备份恢复

**备份策略**：

| 触发方式 | 时机 | 保留 |
| --- | --- | --- |
| 启动自动备份 | 每次启动 | 最近 3 份 |
| 手动备份 | 用户触发 | 用户管理 |
| 迁移前备份 | schema 变更前 | 最近 1 份 |
| 恢复前安全备份 | 恢复操作前 | 最近 1 份 |

**恢复硬规则**：

1. 恢复前必须先做安全备份（防止恢复错数据无法回退）
2. 恢复前校验备份文件完整性，损坏文件拒绝恢复
3. 恢复时关闭其他写操作，避免冲突
4. 恢复后自检数据一致性

**完整性校验**：
- 备份文件大小、表数量、记录数校验
- JSON 结构校验（导入文件）
- SQLite 文件头校验（DB 文件）
- 损坏文件拒绝操作，不静默降级

## 6. 数据流与一致性基线

> 本节定义后端数据怎么流动、怎么保持一致——请求流、响应流、错误流、事件通知、缓存策略。

### 6.1 数据流分层

**请求流**（从前端到数据库）：

```
HTTP 请求
   │
   ▼
Router（路由匹配/参数提取）
   │
   ▼
Controller（薄层：调 Service/格式化响应）
   │
   ▼
Service（业务逻辑/Zod 校验/事务边界/DTO 转换）
   │
   ▼
Repository（数据访问/软删除过滤/分页）
   │
   ▼
BaseRepository（通用 CRUD/查询构造）
   │
   ▼
Prisma（ORM → SQLite）
```

**响应流**（从数据库到前端）：

```
Prisma（返回原始记录）
   │
   ▼
BaseRepository（透传）
   │
   ▼
Repository（过滤/分页封装）
   │
   ▼
Service（toPublic 白名单转换）
   │
   ▼
Controller（res.success 包装）
   │
   ▼
HTTP 响应 {code, msg, data}
```

**错误流**：

```
任意层 throw
   │
   ▼
errorHandler 中间件
   │
   ├─ BusinessError → 按 code/msg 返回
   ├─ PrismaError   → 映射 2xxx 段
   └─ 未知错误       → 1000 通用错误 + 完整堆栈入日志
   │
   ▼
HTTP 响应 {code, msg, data: null}
```

### 6.2 事件与通知

**当前状态**：
- 当前无 SSE/WebSocket，前端通过轮询查询状态
- 长任务（备份/导入/导出）通过轮询任务状态接口获取进度

**V1.2+ 引入 Observable 事件总线**：
- 评估引入事件总线，解耦事件生产者和消费者
- Service 层发布事件，Controller 层通过 SSE 推送前端
- 事件类型化，前端订阅 typed 事件

**实时推送场景**：

| 场景 | 触发 | 推送内容 |
| --- | --- | --- |
| 备份进度 | 备份任务执行中 | 进度百分比/状态 |
| Vault 变更 | 知识库增删改 | 变更类型/目标 ID |
| Agent 任务状态 | AI 任务执行 | 状态流转/结果 |

**跨 Tab 同步**：
- 前端通过 BroadcastChannel 中继事件
- 后端推送一次，前端主 Tab 接收后广播给其他 Tab
- 避免后端为每个 Tab 维护连接

### 6.3 缓存策略

**当前状态**：
- 当前无缓存层，所有查询直接走 DB
- SQLite 本地查询足够快（< 50ms），暂不需要缓存

**V1.5+ 评估**：
- 高频读低频写的数据可加内存缓存（如配置项、字典数据）
- 缓存失效策略：写入时清除（cache-aside）
- 不引入 Redis 等外部缓存，保持单机无外部依赖

**缓存硬规则**（引入后必须遵守）：

1. 缓存只用于读优化，不作为数据源（DB 是唯一数据源）
2. 写操作必须使相关缓存失效
3. 缓存可丢失（重启后重建），不依赖缓存持久化
4. 不引入外部缓存服务（Redis/Memcached），保持单机定位

## 7. 工程质量基线

> 本节定义后端代码质量、测试、性能、安全的标准——发布前必须通过 § 8.2 版本必检清单。

### 7.1 代码规范

- **ES Modules**：统一使用 ESM（`import/export`），不混用 CommonJS
- **文件命名**：
  - 模块文件：`xxx.router.js` / `xxx.controller.js` / `xxx.service.js` / `xxx.repository.js` / `xxx.schema.js` / `xxx.test.js`
  - 工具函数：`camelCase.js`（如 `formatDate.js`）
  - 常量：`UPPER_SNAKE_CASE`（如 `MAX_PAGE_SIZE`）
- **函数命名**：camelCase（如 `getProjectById`、`createReview`）
- **类命名**：PascalCase（如 `ProjectService`、`BusinessError`）
- **单例导出**：Service/Repository 统一 `export default new XxxService()`
- **commit 规范**：`type: description`（如 `feat: 新增复盘模块` / `fix: 修复备份完整性校验`）

### 7.2 测试金字塔

```
        ┌──────────────┐
        │  E2E 测试     │  ← HTTP API 全链路（少而精）
        ├──────────────┤
        │  集成测试     │  ← Service + 真实 DB（核心覆盖）
        ├──────────────┤
        │  单元测试     │  ← 纯函数/schema 校验（全覆盖）
        └──────────────┘
```

- **单元测试**（Vitest）：纯函数、Zod schema 校验、工具函数，目标全覆盖
- **集成测试**（Vitest + 真实 DB）：Service + Repository + Prisma，真实 DB 操作
- **E2E 测试**（Vitest + supertest）：HTTP API 全链路，从路由到 DB 再到响应

**当前测试策略**：
- 真实 DB 集成测试，非 mock
- 测试数据用 `TEST_` 前缀隔离，测试后清理
- 串行执行（SQLite 单写者，避免并发冲突）

**目标**：
- 补充单元测试层，纯逻辑脱离 DB 测试
- 集成测试覆盖核心业务流程
- E2E 测试覆盖关键 API 端点

## 8. 版本演进规则（三条线并行）

> 后端版本迭代不是只有"加功能"一条线，而是三条线并行。

### 8.1 三条迭代线

后端版本迭代不是只有"加功能"一条线，而是三条线并行：

```
┌─────────────────────────────────────────────────────────────┐
│  功能迭代线（Feature Line）                                   │
│  做什么功能（新模块/新接口/新业务能力...）                      │
│  主要影响层：L4-L5（领域服务 + 接口契约）                       │
│  规划位置：产品迭代演进计划.md                                │
├─────────────────────────────────────────────────────────────┤
│  架构迭代线（Architecture Line）                              │
│  数据模型重构/中间件升级/架构风格演进（模板库→Migrate/          │
│  无 SSE→事件总线/无缓存→内存缓存）                             │
│  主要影响层：L1-L3（工程规范 + 基建 + 数据持久）               │
│  规划位置：本总纲 § 2-3 + 演进计划                            │
├─────────────────────────────────────────────────────────────┤
│  基建迭代线（Infra Line）                                     │
│  可观测性/CI/CD/安全加固（日志增强/测试补充/Origin 校验/       │
│  加密存储）                                                   │
│  主要影响层：L1-L2（工程规范 + 基础设施）                      │
│  规划位置：本总纲 § 7 + 演进计划                              │
└─────────────────────────────────────────────────────────────┘
```

**三条线的关系**：
- 功能线驱动产品能力增长
- 架构线驱动数据模型和架构风格演进
- 基建线驱动可观测性、安全性和工程质量
- **每条线都必须遵守本总纲的基线**，不允许因为赶功能就降低 L1-L3 的质量
- **数据契约（L3-L5）的变更必须三条线协同评估**，避免破坏向后兼容

### 8.2 版本必检清单

任何版本发布前，后端必须通过以下检查（**版本无关，所有版本适用**）：

#### 功能检查
- [ ] 接口契约测试通过（请求/响应格式符合 § 4.2）
- [ ] 幂等性验证（重复调用不产生副作用）
- [ ] 错误码全覆盖（所有失败路径有明确 code）
- [ ] Zod 校验全字段（所有输入过 schema）
- [ ] 软删除生效（删除后查询不返回，回收站可查）
- [ ] 跨模块联动测试（如项目删除联动复盘删除）
- [ ] 数据导入导出兼容（旧导出文件能导入新版本）

#### 数据检查
- [ ] Migration 可逆（有回滚方案）
- [ ] 数据兼容旧版本（新代码能读旧数据）
- [ ] 备份验证通过（备份可恢复）
- [ ] 索引性能检查（慢查询有索引支撑）
- [ ] JSON 字段 parse/stringify 安全（损坏数据不崩溃）
- [ ] toPublic 白名单未泄漏敏感字段

#### 工程检查
- [ ] Lint 零 error
- [ ] 测试覆盖达标（核心流程有集成测试）
- [ ] 无 `console.log`（用 logger 替代）
- [ ] 无硬编码路径（用配置/常量替代）
- [ ] commit 规范符合（`type: description`）
- [ ] 新模块 6 文件结构完整（router/controller/service/repository/schema/test）

#### 性能与安全检查
- [ ] API P95 达标（< 200ms）
- [ ] 慢查询排查（无全表扫描）
- [ ] 内存无泄漏（长时间运行稳定）
- [ ] Origin 校验生效（V1.2+，非本地请求拒绝）
- [ ] 路径穿越防护（文件操作校验 `..` 和绝对路径）

### 8.3 向后兼容规则

- **数据兼容**：新版本必须能读取旧版本的数据（迁移脚本 + 备份兜底）
- **接口兼容**：已发布接口的字段加不删，类型变更走版本化
- **配置兼容**：配置文件带版本号，升级时自动迁移，旧配置在新版本有效
- **错误码兼容**：已发布的错误码语义不变，新增错误码不占用已用段位

### 8.4 废弃与迁移策略

当需要废弃某个 API/字段/规范时：

1. **标记废弃**：代码中加 `@deprecated` JSDoc 注释，日志 warning
2. **提供替代**：必须在废弃的同时提供新方式
3. **保留至少一个版本**：废弃的 API/字段至少保留一个完整版本周期
4. **文档记录**：本总纲和版本更新记录同步说明
5. **迁移指南**：在版本更新记录中说明如何迁移到新方式

### 8.5 本总纲的修订流程

本总纲不是一成不变的。修订流程：

1. 发现本总纲有不足/需要新增原则
2. 在 [产品迭代演进计划.md](./产品迭代演进计划.md) 的"决策记录"中记录修订提案
3. 与用户确认后更新本总纲
4. 在本文件附录 B 记录变更内容
5. 如果修订影响已实现代码，在下一版本中统一修正

### 9.1 新版本后端思考流程

```

        ① L1 工程规范：是否需要新的 Lint 规则/测试/6 文件结构？
        ② L2 基础设施：是否需要新的中间件/工具函数/启动检查？
        ③ L3 数据模型：是否需要新的 Prisma model/迁移/索引？

        → 开发过程中和发布前逐项检查

Step 6：如果发现新功能需要新的基础设施/数据模型/规范，
        先补 L1-L3，再做 L4-L6（先奠基，再盖楼）
```

### 9.2 新接口/新功能开发 Checklist

每个新接口/新功能开发前，问自己这些问题：

- [ ] 数据模型设计：需要新 model 吗？通用字段齐全吗？
- [ ] Schema 定义：Prisma model 命名/@@map/索引规范吗？
- [ ] 迁移策略：schema 变更怎么迁移？可逆吗？备份了吗？
- [ ] Service 逻辑：业务规则集中吗？跨模块调用清晰吗？
- [ ] Zod 校验：所有输入过 schema 了吗？复用通用 schema 了吗？
- [ ] 事务边界：跨表操作包在 `$transaction` 里了吗？
- [ ] 错误码：失败路径有明确 code 吗？同步前端 i18n 了吗？
- [ ] 响应格式：符合 `{code, msg, data}` 吗？分页格式对吗？
- [ ] 软删除：删除是软删除吗？查询默认过滤了吗？
- [ ] 分页：列表接口支持分页吗？pageSize 上限 100 吗？

- [ ] toPublic 白名单：敏感字段不返回吗？

### 9.3 新模块添加流程

1. 在 `src/modules/` 下创建模块目录（如 `reviews/`）

9. 编写 `reviews.test.js`（真实 DB 集成测试，TEST_ 前缀隔离）

## 附录 A · 术语表

| 术语 | 含义 |
| --- | --- |
| **BaseRepository** | 通用数据访问基类，封装 CRUD/软删除过滤/分页/排序，所有 Repository 继承它 |
| **BusinessError** | 业务错误类，携带错误码和消息，由 errorHandler 中间件统一捕获转换为响应 |
| **软删除** | 通过 `deletedAt` 字段标记删除，不物理 `DELETE`，可恢复，BaseRepository 默认过滤 |
| **toPublic** | 领域对象的白名单导出方法，只返回前端需要的字段，敏感字段不外泄 |
| **Zod** | TypeScript 优先的 schema 校验库，在后端用于输入校验，schema 定义在 `*.schema.js` |
| **Prisma** | 类型安全的 ORM，后端数据持久层核心，通过 schema 定义 model 生成类型化客户端 |
| **模板库机制** | DB 模板/配置模板随包发布，启动时复制到用户目录，非 Prisma Migrate 的迁移方式 |
| **端口顺延** | 默认端口被占时自动 +1 寻找可用端口，不直接报错退出 |
| **优雅关闭** | 捕获 SIGINT/SIGTERM 信号，清理数据库连接、刷新日志后退出进程 |
| **Observable 事件总线** | 发布-订阅模式的事件系统，V1.2+ 评估引入，解耦事件生产者和消费者 |
| **幂等键** | 保证同一操作执行一次和多次效果相同的机制，避免重复操作产生副作用 |
| **事务边界** | 数据库事务的范围，后端以 Service 方法为事务边界，跨表操作包在 `$transaction` 里 |
| **DTO** | Data Transfer Object 数据传输对象，后端通过 toPublic 转换为 API 响应格式 |
| **Schema 迁移** | 数据库结构变更的管理，当前用模板库 + 启动复制，V1.2+ 评估 Prisma Migrate |
| **pkg 打包** | 将 Node.js 应用打包为单文件可执行文件的工具，后端交付为桌面单文件 exe |
