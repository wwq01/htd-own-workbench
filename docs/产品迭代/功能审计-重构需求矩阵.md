## 0. 审计范围与方法论说明

### 0.1 产品定位与类型判定
本产品是**本地优先（local-first）的个人生产力 / 第二大脑工作台**，作者自用、纯本地无云、单 exe 分发。它不属于通用 SaaS / 电商 / 社区平台，而是"个人知识工作操作系统"。因此本审计**不套用通用行业竞品矩阵**，而是以"作者真实工作流"为锚点做功能盘点与缺口比对——这比外部竞品对标更有价值（作者的工作流即产品的"用户故事"）。

### 0.2 已读真实代码清单（实测依据）
- 方向文档：`V2.0-重构方向.md`、`架构审计报告-重构候选方案.md`、`产品迭代演进计划.md`、`V2.0.0-第二大脑与APP化.md`
- 前端入口/导航：`app.js`、`router.js`、`store/dataStore.js`、`components/HtpCommandPalette.js`、`utils/icons.js`、`utils/charts.js`

## 2. 核心用户旅程 / 工作流地图

> 标注：🔴 断点（流程断裂需手工补）、🟡 手工环节（可自动化未自动化）、🟠 跨模块摩擦（数据不互通）。

### 旅程 ① 多售前项目 日报 → 周报
`Project（每日备忘失焦自动存 ProjectPage.js:234-246）` → `Review（周复盘/项目复盘双模板 ReviewPage.js）` → `Vault（reviewSubmit/reviewPrecipitate ReviewPage.js:159-170 → autoCreateFromReview）`
- 🟡 **周报需手动汇总**：项目每日备忘是自由文本，周报无自动聚合"本周各项目进展"。
- 🔴 **沉淀无回链**：Vault 自动草稿（vault.service.js:70-82）无双向链接指回来源复盘/项目，复用靠全文搜索。
- 🟠 阅读资料无法挂靠项目，情报与项目脱节。

### 旅程 ② 技术投标 RFP 逐条应答
`Bid（投标号归档 BidPage.js）` → （人工拆 RFP）→ `撰写应答文档（外部）`
- 🔴 **Bid 无 RFP 条目级结构**：仅存 bidNo（search.service.js:23），无法"逐条应答、逐条挂证据（POC/漏洞）"。
- 🟡 应答文档在系统外产出，证据引用靠手动复制 Poc/Bid/Vuln 内容。
- **这是 V2.0 最明确的"新建能力"缺口**（当前 0 支持）。

### 旅程 ③ 公众号 PR 文章产出
`Reading（收藏+笔记 ReadingPage.js）` → `Vault（convertToVault 一键转化）` → `撰写`
- 🔴 **Vault 纯文本渲染**：转化后 Markdown 不强渲染（VaultPage.js:366），排版丢失。
- 🔴 **单向复制、无 Quote 双轨**：V2.0 §9.1 要求的"笔记↔原文双向跳转（anchor）"当前为 0。
- 🟡 文章成稿在系统外，无"客户端预览模式"兜底（V2.0 §9.1 设计但未实现）。

### 旅程 ④ 威胁情报 → 规则生成 → 发布链路
`Vuln / Poc / Bid / Incident（安全四模块）` → `情报整理` → `规则/报告产出`
- 🟠 **四模块状态机各自硬编码且不一致**：Poc 6 态、Vuln/Incident/Bid 各自定义（PocPage/BidPage/VulnPage/IncidentPage 前端硬写），后端亦硬编码（poc.service.js:113 等）。
- 🔴 **Vuln 资产分组存 localStorage**（VulnPage.js:6-51），多设备/重装即丢，与"本地优先单库"原则冲突。
- 🟡 无"情报→规则→发布"的串联流程，四模块是孤岛。

### 旅程 ⑤ 第二大脑 阅读 → 沉淀 → 复用
`Reading` → `Vault` → `搜索/图谱复用`
- 🔴 **Vault 无双向链接 / 标签树 / 图谱**（vault.service.js 全文件）：标签仅 JSON 字符串 + contains 子串匹配（vault.service.js:25），无归一化/层级。
- 🟡 **搜索覆盖不全**：后端 `/search` 仅 15/27 模块（search.service.js:11-27，缺 memo/dev-*/study-*/entertainment/milestone/task/finance-contract）；命令面板仅 10 模块（P1-1）。
- 🟡 **首页"智能推荐"弱**：`POST /home-recommend → autoRecommendVault` 是规则桩（system.router.js:42），非语义/图谱推荐。

**旅程总判**：5 条旅程在"采集/存储"段基本通顺，但在"聚合/关联/复用"段普遍断裂——根因是 **Vault 是扁平仓库而非知识网络**，且模块间仅靠"复制粘贴 + 全文搜索"耦合。这正是 V2.0 §9.1 知识图谱要解决的。

## 4. 信息架构与导航问题

### 4.1 侧边栏：扁平 21 项，无分组元数据
`app.js:7-29` 的 `NAV_ITEMS` 是**扁平列表，无 group 字段**。而首页却以"工作/生活/知识"三栏**硬编码**分组（HomePage.js:132-349）。两套组织逻辑不一致，且**分组元数据未单源化**——新增模块时需同时改 NAV_ITEMS（导航）和 HomePage（首页分组），易漂移。

### 4.2 命令面板覆盖度不足（P1-1，确认）
`HtpCommandPalette.js:30-50` 的 `COMMANDS` 仅含 10 个导航入口（home/todo/project/develop/ent/study/review/secret/data/settings）+ new-* + 外观/备份。**缺失 10 个模块**：meeting / habit / time-block / finance / vault / poc / bid / vuln / incident / reading。用户无法用 Ctrl/Cmd+K 直达这些高频模块。

### 4.3 多注册点漂移（P1-1 根因，扩展为 6 处）
新增一个模块需同步改动 **6 个独立注册点**，且其中 3 处是部分/漂移的：

| # | 注册点 | 位置 | 项数 | 问题 |
|---|---|---|---|---|
| 1 | index.html `<script>` | 43 个有序脚本（C1 无构建约束） | 43 | 顺序敏感，错序即崩 |
| 2 | router.js registerRoute | router.js:125-145 | 21 | 手动逐条 |
| 3 | app.js NAV_ITEMS | app.js:7-29 | 21 | 扁平无 group |
| 4 | app.js pageComponents | app.js:65-87 | 21 | 手动映射 |
| 5 | HtpCommandPalette COMMANDS | HtpCommandPalette.js:30-50 | **10** | 缺 10 模块 |
| 6 | search.service.js MODULE_CONFIGS | search.service.js:11-27 | **15** | 缺 10 模块（memo/dev-*/study-*/entertainment 等） |

## 5. 交互冗余与一致性

### 5.1 表单输入：组件化不一致（🔴 主要割裂点）
实测计数（前端 modules 目录）：
- **用 `<htp-input>`/`<htp-textarea>` 组件**：Finance(9) / Meeting(9) / Project(9) / Reading(8) / Vault(6) / Vuln(6) / Secret(6) / Poc(5) / Habit(5) / Todo(3) / TimeBlock(2) / Bid(4) / Incident(4) —— 共 12 模块。
- **用原生 `<input class="htp-input">`/`<textarea class="htp-textarea">`**：Develop(14) / Study(15) / Review(11) / Data(10) / Secret(6) / Entertainment(4) / Settings(3) —— 共 7 模块。

即约 37% 的模块仍走原生 input 路径，绕过 HtpInput/HtpTextarea 组件可能提供的校验态/聚焦态/禁用态统一处理。**Review、Study、Develop、Data 等"老模块"与新模块体验割裂**。

### 5.2 弹窗：已统一（✅）
`<htp-modal>` 在全部 18 个含弹窗的模块中一致使用（Bid/Entertainment/Habit/Data/Develop/Finance/Incident/Meeting/Poc/Project/Reading/Secret/Review/Study/TimeBlock/Todo/Vault/Vuln）。弹窗交互**无一致性问题**。

### 5.3 图表：机制统一但配色硬编码（⚠️ P0-2）
机制上统一走 `charts.js`（barChart/donutChart/lineChart/stackedBarChart/timelineChart）。**但颜色硬编码**：
- charts.js 工具本身**主题感知**（默认 `opts.color || 'var(--color-primary)'`，charts.js:42,111），调用方若不传色即跟随主题。
- **问题在调用方**：HomePage(#22D3EE/#34D399)、StudyPage(#22D3EE)、FinancePage(#34D399/#F87171/#5B8DEF)、ProjectPage(#34D399/#94A3B8)、TimeBlockPage(#3B82F6/#8B5CF6/#10B981/#64748B/#eef0f4×2) 共 **14 处硬编码 hex**，暗色主题下失效。
- `lineChart`（charts.js:92-124）**定义但零消费**（P2-2 死代码）。

### 5.4 状态机：三套实现 + 双写路径（⚠️ P1-2）
- 前端各模块硬写状态机常量（PocPage/BidPage/VulnPage/IncidentPage/ReadingPage/ProjectPage）。
- 后端部分模块用硬编码常量（poc.service.js:113 的 `POC_STATUS_TRANSITIONS`），部分用配置平台（reading.service.js:141 `getStateMachineSync('reading.status')`、project.phase）。
- **配置平台仅治理 2 个 scope**（fieldConfig.service.js:44-55：reading.status、project.phase），其余 6+ 状态机（todo/poc/bid/vuln/incident/review）前后端均硬编码。
- todo `toggleStatus`（todo.service.js:99-110）**完全绕过状态机**，直接翻转 pending↔completed。

### 5.5 标签组件：统一但含红线违规（⚠️）
`HtpTag` 组件统一，但**设计系统仍定义并使用了紫色**：
- HtpTag.js:3,10 支持 `purple` 类型；:28 将 `'POC演示'→purple`。
- ReviewPage.js:278 用 `type="purple"`；TimeBlockPage.js:153 硬编码 `#8B5CF6`（紫）。
→ 违反项目红线"禁止紫色→粉色渐变方案"（紫色作功能色）。

### 5.6 图标：两套系统 + 残留 emoji（⚠️ P2-3 + 红线残留）
- **导航图标**：`NAV_ITEMS` 裸 `d` 串（17 项）+ 完整 `<path>` 子元素串（4 项，app.js:23-26），由 `navIconInner`（app.js:122-124）渲染——**同一文件两种格式并存**。
- **页面图标**：`HTD_ICONS` 27 个 Lucide 风 SVG（icons.js:6-32），经 `htdIcon` 注入，EntertainmentPage 等正确使用。
- **残留 emoji（违反 P0-1 红线精神）**：HabitPage.js:227 默认书钉 emoji、DevelopPage.js:400 剪切板 emoji、HabitPage.js:322 表单字段明示"图标（emoji）"。全前端仅 2 处字面 emoji，但证明 emoji 禁令**未彻底执行**。

## 7. 结论与取舍建议

### 7.1 功能现状一句话总结
V1.5 是一个"**采集强、关联弱、可视化半成品**"的本地工作台：21 模块覆盖了作者工作/生活/知识三线，但模块间仅靠复制+全文搜索耦合，**Vault 是扁平仓库而非知识网络**，V2.0 五大新能力后端**全为零骨架**。

### 7.2 审计对架构报告的修正（重申）
- ❌ P0-1"4 图标空白"：实测 21 图标全渲染，仅格式不统一 → 降级为一致性问题。
- ❌ P2-4"命令面板空 handler/拼音错字"：实测 handler 与拼音均正常 → 该条撤销。
- ✅ P0-2/P0-3/P1-1/P1-2/P1-4/P2-2/P2-3 全部实测确认成立，并在本报告给出精确证据与范围。

### 7.3 三处红线违规（须 M0 立即治理）
1. **emoji 残留**：HabitPage.js:227（书钉）、DevelopPage.js:400（剪切板）、HabitPage.js:322（表单明示 emoji）。
2. **紫色违规**：HtpTag.js:3,10,28（purple 类型）、ReviewPage.js:278（type="purple"）、TimeBlockPage.js:153（#8B5CF6）。
3. **暗色失效**：5 模块 14 处硬编码 hex（P0-2）。

### 7.4 核心取舍
- **S2 不可跳过**：知识图谱"1k 节点流畅"验收（V2.0.0 §9.6）与当前 SVG 字符串 + v-html 机制（P0-3）不兼容，Vite 构建化是硬前置，D1 已裁定。
- **M0 与 S1 可立即并行启动**：M0 是零架构风险的红线/主题止血；S1 的 meta.js 注册表是后续所有模块新增的"单行接入"基础，越早做边际收益越高。
- **V2.0 新能力（Agent/云/加密）排期末尾但主密码加密应提前**：三者后端零骨架、RICE 最低；但主密码加密属安全属性，建议在 Tauri 首发前落地，避免"APP 化后仍是明文"。
- **Vault 深化是 V2.0 价值中枢**：它同时是第二大脑（旅程⑤）、PR 产出（旅程③）、复盘沉淀（旅程①）的汇点，应优先于 Agent/云获得图谱与双向链接能力。

### 7.5 给主理人（大湾区靓仔）的下一步建议
1. 先批 M0 四项的实现工单（主题变量化 / emoji 清除 / 紫色退役 / 命令面板补模块）。
2. 启动 S1 的 meta.js 注册表设计（消费方：router / NAV_ITEMS / pageComponents / commandPalette / search MODULE_CONFIGS / index.html script 顺序）。
3. S2 立项前先确认 Vite 迁移对"43 个有序 script + 无可选链"约束（C1）的兼容方案——这是 S2 的最大技术风险点，建议单独做可行性 spike。
