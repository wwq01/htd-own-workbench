# 前端系统化设计（前端工程总纲）

> **本文档定位**：荒天帝工作台前端工程的"宪法"——定义前端的哲学、分层、设计系统、交互基线、工程质量标准和版本演进规则。
> **不绑定任何具体版本或功能**。无论是 V1.2、V2.0 还是未来某个版本，无论是做命令面板还是做知识图谱，前端开发都必须先遵守本总纲，再做具体实现。
>
> **文档关系**：
> - **本文件**：前端总纲（怎么思考前端 / 必须遵守的基线 / 版本无关）
> - [产品迭代演进计划.md](./产品迭代演进计划.md)：版本规划（每个版本做什么 / 版本特有）
> - 视觉规范见对应版本文件（如 v1.1 的 [v1.1 - 视觉-LiquidGlass.md](../v1.1 - 视觉-LiquidGlass.md)）

### 0.2 本文档不是什么

- ❌ 不是 V1.2（或任何版本）的 todo list——那在演进计划里
- ❌ 不是 Liquid Glass 的视觉规范——那在视觉规范文档里

### 0.3 核心心智模型

**先奠基，再盖楼**。

任何前端工作（新功能、新主题、重构、优化）都从这三个问题开始：

1. **它属于哪一层？**（L1-L7）
2. **它是主题无关的（L1）还是主题相关的（L2）？**
3. **它是否遵守了该层的基线？**

只有回答完这三个问题，才能开始写代码。

## 1. 前端哲学（永远不变的基调）

> 这一节定义前端的"世界观"。所有技术选型、组件设计、交互选择，都从这些原则推导出来。

### 1.1 核心设计原则

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| **本地优先** | 前端不依赖云端即可工作；网络是增强不是前提 | 页面白屏等待云端返回才渲染 |
| **离线可用** | 断网时已有功能不降级，新操作进入队列稍后同步 | 断网就弹"网络错误"完全不可用 |
| **数据自主** | 用户数据在用户手里；前端不偷偷上传；本地存储格式透明可读 | 数据存在加密的私有格式用户无法导出 |
| **即时反馈** | 用户操作 100ms 内必须有视觉反馈；不允许"点了没反应" | 点击按钮后静默等待2秒才跳转 |
| **不丢数据** | 任何情况下用户输入不丢失；路由切换/关闭/崩溃都有兜底 | 切换页面时未保存的文字消失 |
| **尊重用户** | 不打断用户；不弹不必要的确认；动画服务于功能而非炫技 | 每步操作都弹 Modal 确认 |
| **一致可预测** | 相同的交互模式产生相同的结果；组件行为一致 | 同一个关闭按钮在不同弹窗行为不同 |
| **无障碍包容** | 键盘可操作；屏幕阅读器可用；动画可关闭；高对比度支持 | 只能鼠标点击，Tab 切不到按钮 |
| **渐进增强** | 核心功能在最低配置下可用；高级配置下体验更好 | 没有 GPU 加速就卡成 PPT |
| **性能即体验** | 快就是好；慢就是差。LCP < 1.5s，交互响应 < 100ms | 首屏 5 秒才能交互 |

### 1.2 精致感的来源

精致不是"花哨"，而是**所有"用户能感觉到但说不清"的细节都做对了**：

- **焦点有去处**：打开弹窗焦点自动进去，关闭弹窗焦点回原位
- **状态有反馈**：保存中/已保存/失败，用户始终知道发生了什么
- **动画有意义**：每个动画都在解释"发生了什么变化"，不是装饰
- **错误有出路**：出错时告诉用户"出了什么问题 + 你可以做什么"，不是一堆技术栈信息
- **空态有引导**：空页面不是空白，而是告诉用户"这里可以做什么 + 怎么开始"
- **键盘能走完**：不用鼠标也能完成所有核心操作
- **文字不溢出**：长文本、长名称、小屏幕下不出现遮挡和溢出
- **加载不白屏**：任何等待时间都有骨架屏或进度指示，不出现空白

### 1.3 技术选型原则

- **少即是多**：能不用第三方库就不用；能用原生 API 就不用库
- **可替换性**：所有第三方库通过封装层隔离，未来可替换
- **渐进式**：不一次性引入完整框架（如不直接上 Nuxt/Next），按需引入
- **构建最小化**：V1.x 保持无构建/极简构建，V2.0 Tauri 时再考虑 Vite 化
- **依赖审计**：任何新依赖必须评估：包大小、维护状态、安全记录、是否真的需要

## 2. 前端分层架构（7 层金字塔）

> 前端从地基到视觉分为 7 层。**上层依赖下层，下层不感知上层**。
> 新功能开发从底层往上层做：先确认 L1-L3 满足，再做 L4-L5，最后做 L6-L7。

```
         ┌─────────────┐
         │ L7 视觉呈现  │  ← 用户第一眼看到的
         ├─────────────┤
         │ L6 交互细节  │  ← 用户操作时感受到的
         ├─────────────┤
         │ L5 组件库    │  ← 组装 UI 的乐高积木
         ├─────────────┤
         │ L4 布局系统  │  ← UI 的骨架和空间分配
         ├─────────────┤
         │ L3 状态数据流│  ← 数据怎么流动和管理
         ├─────────────┤
         │ L2 基础设施  │  ← 工具函数、封装、抽象
         ├─────────────┤
         │ L1 工程规范  │  ← 代码怎么写、质量怎么保证
         └─────────────┘
```

### 2.1 L1 · 工程规范层

**职责**：定义代码怎么写、质量怎么保证、团队怎么协作。这一层是"开发体验"和"代码一致性"的基础。

**核心内容**：
- 代码规范（ESLint/Prettier/命名约定）
- Git 工作流（分支策略/commit 规范/PR 流程）
- 目录结构约定
- 测试策略（单元/组件/E2E 的测试金字塔）
- 构建与打包规范
- 文档要求（新组件必须写什么）

**基线要求**（任何版本都必须满足）：
- 所有代码通过 Lint，无 error，warning 逐条确认
- 所有工具函数有单元测试
- 提交信息符合 `type: description` 格式
- 新文件放在正确的目录，不乱放

**演进规则**：L1 随版本演进不断完善规范，但**不允许已确立的规范被回退**。

---

### 2.2 L2 · 基础设施层

**职责**：提供前端运行的"水电煤"——工具函数、封装、抽象，让业务代码写得简洁可靠。

**核心内容**：
- HTTP 客户端封装（请求/响应拦截、错误处理、重试、超时）
- 错误边界（ErrorBoundary，防止白屏）
- 日志系统（logger，分级日志，本地存储）
- 国际化框架（i18n 文案集中管理）
- 存储封装（localStorage/sessionStorage 的命名空间、版本化、过期）
- 通用工具函数（日期格式化、防抖节流、深拷贝、class 合并等）
- 通用 Composables（useDebounce/useThrottle/useResize/useInterval 等）
- 功能开关（Feature Flags，灰度发布）
- 环境配置（开发/生产/测试环境变量）

**基线要求**：
- 所有 HTTP 请求通过统一封装发出，禁止直接 fetch
- 所有面向用户的文案通过 i18n，禁止硬编码中文长字符串
- 所有 localStorage 操作通过存储封装，禁止直接读写
- 未捕获错误有 ErrorBoundary 兜底，不白屏

**演进规则**：基础设施**持续积累、可复用、与业务解耦**。新业务发现重复模式时，抽到 L2。

---

### 2.3 L3 · 状态与数据流层

**职责**：定义数据在前端怎么存、怎么流、怎么同步。

**核心内容**：
- 全局状态管理（Pinia stores，按领域拆分）
- 服务端状态缓存（SWR/stale-while-revalidate 策略）
- URL 状态（路由参数作为可分享、可刷新的状态）
- 本地持久化（草稿、用户偏好、缓存的版本化管理）
- 实时通信（SSE/WebSocket 的统一封装，Observable 事件总线）
- 跨 Tab/窗口同步（BroadcastChannel）
- 表单状态（受控/非受控、验证、提交）
- 乐观更新（先更新 UI 再等响应，失败回滚）
- 草稿状态机（pending/saving/saved/failed 五态）

**基线要求**：
- 状态分类清晰：组件本地 state / Pinia 全局 / URL 状态 / 服务端缓存，不混用
- 实时事件通过统一事件总线分发，组件不直接解析 SSE
- 用户输入的持久化走草稿状态机，保证不丢字
- URL 驱动主要视图状态，刷新可恢复

**演进规则**：L3 随业务复杂度增长而增强。简单版本可以先简化实现，但**状态分层的思路必须从第一天就遵守**。

---

### 2.4 L4 · 布局系统层

**职责**：定义页面的骨架、空间分配、响应式行为。布局是视觉的"骨架"。

**核心内容**：
- App Shell（侧栏 + 顶栏 + 主内容区的经典布局）
- 响应式断点系统（CSS 变量定义的断点，而非硬编码媒体查询）
- 间距系统（统一的间距尺度，不随便写 `10px`/`14px`）
- 滚动行为（主内容区滚动、侧栏固定、虚拟滚动长列表）
- 焦点轮廓（`:focus-visible` 键盘焦点样式）
- 路由切换过渡（页面间的平滑过渡）
- 窗口 resize 处理（防抖的 resize observable）
- 侧栏/面板的可折叠与尺寸记忆

**基线要求**：
- 最小可用宽度明确（V1.x 为 1280px，小于时有明确提示）
- 间距使用统一尺度（4 的倍数），不出现 `10px`/`13px`/`17px` 等随意值
- 键盘焦点有清晰可见的轮廓
- 侧栏折叠状态记住用户偏好（localStorage）

**演进规则**：V1.x 桌面优先，V1.4 跨平台时扩展响应式，V2.0 移动端时重新设计布局。

---

### 2.5 L5 · 组件库层

**职责**：提供可复用的 UI 组件，是组装页面的"乐高积木"。

**组件分类**：

| 分类 | 说明 | 例子 |
| --- | --- | --- |
| **基础组件 (Base)** | 原子级、无业务含义、纯 UI | Button/Input/Select/Checkbox/Radio/Switch |
| **反馈组件 (Feedback)** | 给用户反馈的组件 | Modal/Drawer/Toast/Tooltip/Popover/ConfirmDialog |
| **展示组件 (Display)** | 展示数据和状态的组件 | Card/Badge/Tag/Avatar/Progress/Skeleton/StatusDot/Empty |
| **导航组件 (Navigation)** | 导航相关 | Tabs(Tablist)/Breadcrumb/Pagination/Dropdown/Menu |
| **输入组件 (Input)** | 复杂输入 | Form/Textarea/DatePicker/Upload/Search/CommandPalette |
| **编辑器组件 (Editor)** | 富文本/草稿编辑 | DraftEditor/MarkdownEditor |
| **业务组件 (Business)** | 有业务含义的组件 | ProjectCard/CredentialItem/ReviewEditor |

**组件设计硬规则**：

1. **受控优先**：组件通过 props/v-model 接收状态，通过 emit 通知变更；组件不偷偷改内部状态
2. **单一职责**：一个组件只做一件事；超过 300 行考虑拆分
3. **可组合**：小组件通过 slot/children 组合成大组件，不用 props 堆砌配置
4. **无障碍内置**：每个交互组件默认带正确的 ARIA 属性、键盘支持
5. **主题无关样式**：组件 CSS 只引用 CSS 变量（设计令牌），不写死颜色/圆角/阴影值
6. **三态完整**：需要数据的组件必须处理 Loading/Error/Empty 三态
7. **Props 显式**：所有 props 有类型、有默认值、有注释；Boolean props 命名用 `is/has/should` 前缀

**基线要求**：
- 基础组件从业务中提取，不是一开始就造大而全的组件库
- 组件文件放在 `frontend/src/components/<category>/` 下，按分类组织
- 每个组件有 JSDoc 注释说明用途、props、emits、slots
- 业务组件不放在 base/ 下，避免业务逻辑污染基础组件

**演进规则**：V1.2 先提取高频基础组件（Modal/Drawer/Toast/Skeleton/Empty/StatusDot）；后续版本逐步丰富。**不追求大而全，业务中发现重复 3 次再提取**。

### 2.6 L6 · 交互细节层

**职责**：定义用户操作时的微交互、反馈、动效、键盘行为等"体验细节"。

**核心内容**：
- 悬停/激活/焦点反馈（hover/active/focus 态的视觉反馈）
- 点击/提交反馈（按钮 loading 态防重复提交、操作成功/失败提示）
- 加载策略（骨架屏/进度条/Spinner 的使用场景）
- 错误反馈（错误提示位置、文案、重试入口）
- 空态引导（空页面的场景化文案+下一步操作）
- 键盘导航（Tab 顺序、快捷键、Esc 关闭、Enter 确认）
- 焦点管理（焦点陷阱、焦点还原、Tabindex 策略）
- 动效使用（什么该动、什么不该动、动效时长、动效曲线、reduced-motion 降级）
- 手势/右键（右键菜单、拖拽、长按等高级交互）
- 引导与发现（Onboarding、新功能提示、快捷键提示、帮助入口）
- 长任务反馈（进度条、轮询退避、取消能力）
- 撤销/重做（危险操作的撤销能力）

**交互硬规则**：

1. **100ms 反馈律**：任何用户操作 100ms 内必须有视觉反馈（loading 态/按下态/过渡动画）
2. **焦点闭环**：弹窗/抽屉打开 → 焦点移入；关闭 → 焦点还原；Tab 不跑到弹窗外面
3. **Esc 统一**：所有浮层（Modal/Drawer/Dropdown/Tooltip/CommandPalette）统一用 Esc 关闭
4. **保存不打断**：自动保存是静默的（后台跑），不弹"保存成功"；只有失败才提示
5. **危险操作确认**：删除/覆盖/清空等不可逆操作必须二次确认
6. **动效三档**：full（完整动效）/ reduced（减弱动效）/ off（无动效），跟随系统设置
7. **reduced-motion 遵守**：系统开启"减少动态效果"时，所有装饰性动画关闭
8. **按钮防重复**：提交按钮进入 loading 态，防止双击重复提交
9. **错误不阻断**：非致命错误不阻塞用户继续操作，用 Toast 提示
10. **快捷键可查**：所有快捷键在命令面板或帮助入口可查

**基线要求**：
- 所有交互组件支持键盘操作
- 浮层组件有焦点管理
- 动效使用统一的时长和缓动曲线（从设计令牌取）
- 遵守系统 reduced-motion 设置

### 2.7 L7 · 视觉呈现层

**职责**：定义用户最终看到的颜色、字体、阴影、圆角、材质、装饰等视觉表达。

**核心内容**：
- 设计令牌（Design Tokens：色板/字号/间距/圆角/阴影/动效时长）
- 主题系统（多主题架构、theme.json 描述文件、切换机制）
- 色彩系统（主色/语义色/中性色梯度、暗色/亮色模式、对比度）
- 排印系统（字体栈/字号梯度/行高/字重）
- 材质与装饰（玻璃质感/阴影/边框/噪点/光斑等主题特化装饰）
- 图标系统（图标尺寸、颜色、使用规范）
- 动效视觉（动效曲线、时长、入场/出场模式）
- 暗色/亮色适配
- 高对比度模式适配

**视觉硬规则**：

1. **令牌驱动**：所有视觉值通过 CSS 变量引用，禁止写死 `#ff6b6b`/`14px` 等字面量
2. **L1/L2 分离**：行为（怎么动）和视觉（长什么样）分离；装饰元素必须可被主题切换器关掉
3. **对比度合规**：文本-背景对比度 ≥ WCAG AA（4.5:1）
4. **双主题一致**：暗/亮两套主题的信息层级一致，不是简单反色
5. **动效有目的**：动效解释状态变化，不是纯装饰；装饰性动效在 reduced-motion 下关闭
6. **图标统一**：使用 Lucide 图标库，统一尺寸（16/20/24px）和 stroke-width
7. **字体回退**：字体栈包含系统字体回退链，不依赖网络字体

**基线要求**：
- Liquid Glass 作为 V1.x 默认主题完整可用
- 暗/亮双主题可用
- 所有页面在两种主题下正常显示，无不可读文本

**演进规则**：V1.x 保持 Liquid Glass 一套主题；V1.4 加 Notion/Neo 等多主题；主题通过 `theme.json` 描述文件扩展。

### 2.8 层间依赖规则

```
L7 视觉  ──依赖──→ L6 交互 ──依赖──→ L5 组件 ──依赖──→ L4 布局
                                                      │
                                                      ▼
L3 状态  ──被上层消费，不感知上层──→ L2 基建 ──依赖──→ L1 规范
```

- **上层依赖下层**：L7 可以引用 L6-L1 的所有东西，L1 不能引用任何上层
- **同层可互引用**：同一层内的模块可以互相依赖（如组件之间可以组合）
- **跨层不跳级**：业务代码尽量只直接接触 L3-L7，L1-L2 是通过框架/工具间接使用的
- **主题相关 vs 主题无关**：
  - **L1-L3**：完全主题无关（代码逻辑不随主题变化）
  - **L4**：主要主题无关（布局骨架不变），细节（间距/圆角）随主题
  - **L5**：组件逻辑主题无关，组件样式主题相关
  - **L6**：交互行为主题无关，交互反馈的视觉主题相关
  - **L7**：完全主题相关

## 3. 设计系统（Design System）

> 设计系统是"视觉和交互的语言"，确保整个产品看起来像一个人做的。

### 3.1 设计令牌三层架构

令牌分三层，**上层引用下层，不直接用原始值**：

```
基础令牌 (primitive tokens)    语义令牌 (semantic tokens)      组件令牌 (component tokens)
─────────────────────────    ─────────────────────────     ─────────────────────────
--color-blue-500             --color-accent                --btn-bg-primary
--space-4 (16px)             --space-card-padding          --card-padding
--radius-md (12px)           --radius-card                 --modal-radius
--duration-in-fast (80ms)    --motion-duration-enter       --toast-enter-duration
```

- **基础令牌**：最底层的原始值（色阶里的某个蓝色、某个间距数值）。主题变了，基础令牌变
- **语义令牌**：有语义的命名（主色、危险色、卡片内边距）。组件引用语义令牌
- **组件令牌**：特定组件的具体值。只在组件内部使用，不跨组件复用

**命名规范**：`--<category>-<element>-<modifier>-<state>`，如 `--color-btn-primary-bg-hover`

### 3.2 主题系统架构

**主题 = 一套设计令牌值 + 可选的组件样式覆盖 + 可选的装饰元素**。

每个主题是一个独立目录：

```
frontend/src/themes/<theme-id>/
├── theme.json          # 主题描述文件（元信息 + 令牌值 + 装饰开关）
├── tokens.css          # CSS 变量定义（从 theme.json 生成或手写）
├── components.css      # 组件样式覆盖（可选，大部分组件不需要）
└── README.md           # 主题说明
```

**theme.json 必填字段**：

```json
{
  "id": "liquid-glass",
  "name": "Liquid Glass",
  "version": "1.1.0",
  "dark": {
    "colorPalette": { "bgBase": "...", "fgPrimary": "...", "accent": "...", "danger": "..." },
    "borderRadius": { "sm": 8, "md": 12, "lg": 18, "xl": 24 },
    "shadows": { "glass": "...", "hover": "..." },
    "typography": { "fontFamily": "...", "fontSizeBase": 14, "lineHeightBase": 1.5 },
    "motion": { "easing": "cubic-bezier(0.2, 0.8, 0.2, 1)", "durations": { "in_fast": 80, "in_slow": 200, "out_fast": 60, "out_slow": 180 } },
    "decorations": { "decryptedText": true, "lightSpots": true, "noiseTexture": true }
  },
  "light": { /* 同结构 */ }
}
```

**主题切换机制**：
1. 用户在设置中选择主题
2. 加载对应主题目录的 CSS（移除旧主题 CSS 引用）
3. 在 `<html>` 上设置 `data-theme="liquid-glass"` 属性
4. CSS 变量自动更新，所有组件视觉自动切换（因为引用的是语义令牌）

**主题扩展规则**：
- 新主题必须实现完整的 dark 和 light 两套
- 新主题必须通过 `scripts/validate-theme.js` 校验（必填字段、对比度、时长范围）
- 新主题必须通过 8 个核心页面的视觉一致性审计（截图比对）
- 主题之间**不共享**组件样式覆盖（每个主题独立）
- 装饰元素（如光斑/DecryptedText）在 theme.json 的 `decorations` 中开关控制，**关闭时组件不渲染对应 DOM**

### 3.3 排印系统（Typography）

- **字体栈**：`-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif`
- **字号梯度**（使用 CSS 变量）：`--font-size-xs(12) / sm(13) / base(14) / lg(16) / xl(18) / 2xl(20) / 3xl(24)`
- **行高**：正文 1.5，标题 1.3，紧凑 1.2
- **字重**：regular(400) / medium(500) / semibold(600) / bold(700)
- **不随便用字体大小**：所有字号从梯度中选，不写 `15px`/`17px`

### 3.4 间距系统（Spacing）

- **基准单位**：4px
- **间距梯度**：`--space-1(4) / 2(8) / 3(12) / 4(16) / 5(20) / 6(24) / 8(32) / 10(40) / 12(48) / 16(64)`
- **使用规则**：
  - 组件内间距用 `--space-2` 到 `--space-4`
  - 组件间间距用 `--space-4` 到 `--space-6`
  - 区块间间距用 `--space-6` 到 `--space-10`
  - 页面级间距用 `--space-8` 到 `--space-16`
- **禁止**：出现 `10px`/`13px`/`14px`/`17px`/`18px`/`22px` 等非 4 倍数间距

### 3.5 色彩系统（Color）

- **色板结构**：每个色相有 10 级梯度（50-900），500 为基准色
- **颜色分类**：
  - 中性色（neutral）：灰阶，用于文本/边框/背景
  - 主色（accent）：品牌色，用于主要操作和强调
  - 语义色：success/warning/danger/info
- **暗色模式**：不是简单反色，而是重新映射信息层级
- **对比度**：所有正常文本与背景对比度 ≥ 4.5:1（WCAG AA）
- **色彩用途**：颜色承载信息（红=危险/绿=成功/蓝=链接），不仅是装饰

### 3.6 动效系统（Motion）

- **时长梯度**：
  - `--duration-in-fast: 80ms`（小元素出现：tooltip/badge）
  - `--duration-in: 150ms`（标准入场：按钮悬停反馈）
  - `--duration-in-slow: 200ms`（大元素入场：抽屉/模态）
  - `--duration-out-fast: 60ms`（小元素消失）
  - `--duration-out: 120ms`（标准退场）
  - `--duration-out-slow: 180ms`（大元素退场/页面切换）
- **缓动曲线**：
  - `--ease-standard: cubic-bezier(0.2, 0.8, 0.2, 1)`（标准）
  - `--ease-enter: cubic-bezier(0, 0, 0, 1)`（入场减速）
  - `--ease-exit: cubic-bezier(0.4, 0, 1, 1)`（退场加速）
  - `--ease-spring: cubic-bezier(0.2, 0.8, 0.2, 1)`（弹性，谨慎使用）
- **动效属性白名单**：只动画 `transform` 和 `opacity`，不动画 `width`/`height`/`top`/`left`（性能差）
- **三档支持**：
  - full：完整动效
  - reduced：只保留必要的状态变化动效，装饰性动效关闭
  - off：全部 snap，无过渡（跟随 `prefers-reduced-motion: reduce`）

### 3.7 图标系统

- **图标库**：Lucide（统一使用）
- **尺寸梯度**：16px（内联）/ 20px（按钮/菜单项）/ 24px（卡片图标/空态图标）
- **stroke-width**：1.5px（小）/ 2px（标准）
- **颜色**：使用 `currentColor`，跟随父元素文本颜色
- **使用规则**：
  - 图标纯装饰 → `aria-hidden="true"`
  - 图标承载含义 → 配合可见文本或 `aria-label`

## 4. 组件设计基线

> 详见 § 2.5 组件库层，此处补充具体的设计要求。

### 4.1 三态组件契约

**任何需要异步数据的组件/页面必须处理三态**：

| 状态 | 视觉 | 交互 |
| --- | --- | --- |
| **Loading** | 骨架屏（Skeleton）或 Spinner，不要空白 | 可取消（长任务时） |
| **Error** | 错误说明（用户可读文案）+ 重试按钮 | 可重试，不阻断其他功能 |
| **Empty** | 场景化图标/插画 + 说明文案 + 下一步 CTA 按钮 | 引导用户创建第一个 |
| **Success** | 实际内容 | 正常交互 |

**骨架屏规范**：
- 形状与实际内容相似（卡片骨架、列表骨架、表单骨架）
- 使用 shimmer 动画（或 reduced-motion 下静态灰块）
- 不使用转圈 Spinner 作为骨架屏（Spinner 用在按钮/小区域）

### 4.2 反馈组件规范

**Toast（轻量提示）**：
- 用于：操作成功/失败提示、非阻断性通知
- 位置：顶部居中或右上角
- 时长：成功 2s 自动消失，错误不自动消失需手动关闭
- 最多同时显示 3 条，超出入队

**Modal（模态对话框）**：
- 用于：需要用户专注处理的任务（新建/编辑/确认）
- 必须：遮罩、焦点陷阱、Esc 关闭、点击遮罩关闭（配置项）
- 不用于：展示大量信息（用 Drawer）、非阻断操作（用 Popover）

**Drawer（抽屉）**：
- 用于：浏览详情、补充内容、不离开主上下文的操作
- 从右侧滑入，宽度 360-480px
- 打开时主内容不销毁（保持滚动位置和状态）

**ConfirmDialog（确认对话框）**：
- 用于：危险操作二次确认
- 明确告知：你在做什么 + 后果是什么 + 是否可撤销
- 危险操作用危险色按钮，取消是默认焦点（防止误操作）

### 4.3 表单组件规范

- **即时校验**：失焦时校验，不等到提交
- **错误就近显示**：错误信息在对应输入框下方，不在顶部集中
- **保存按钮状态**：表单无变更时禁用/或不显示保存按钮
- **输入防抖**：搜索类输入 300ms 防抖
- **Enter 提交**：表单内按 Enter 提交（多行文本除外）

## 5. 交互设计基线（UX Baseline）

> 详见 § 2.6 交互细节层，此处补充具体行为规范。

### 5.1 导航与路由

- **URL 即状态**：主要视图状态（当前 Tab/选中项目/搜索词/筛选条件）通过 URL 参数体现，刷新可恢复
- **路由切换不丢数据**：离开页面前 flush 所有未保存的草稿
- **侧栏高亮**：当前页面对应的侧栏项高亮
- **面包屑**：深层页面（三级及以上）显示面包屑导航（V1.3+）
- **浏览器后退可用**：所有内部导航使用 router，不做"禁用后退"的操作

### 5.2 键盘导航完整基线

| 键 | 行为 |
| --- | --- |
| `Tab` | 向前移动焦点到下一个可交互元素 |
| `Shift+Tab` | 向后移动焦点 |
| `Enter` / `Space` | 激活当前焦点元素 |
| `Esc` | 关闭最上层的浮层（Modal/Drawer/Dropdown/CommandPalette） |
| `Arrow Keys` | 在 Tablist/Menu/Dropdown 内移动选项 |
| `Home` / `End` | 在列表/Tablist 内跳到首/尾 |
| `Cmd/Ctrl+K` | 打开命令面板 |
| `Cmd/Ctrl+S` | 手动保存（当前上下文） |
| `Cmd/Ctrl+B` | 折叠/展开侧栏 |

**焦点管理规则**：
1. Modal/Drawer 打开 → 焦点移到第一个可交互元素或关闭按钮
2. Modal/Drawer 关闭 → 焦点还原到触发它们的元素
3. Tab 循环：在 Modal 内 Tab 不会跑到外面（焦点陷阱）
4. `:focus-visible`：键盘操作时显示焦点轮廓，鼠标操作时不显示

### 5.3 错误处理基线

- **用户可读文案**：错误信息不用技术术语（不说"404 Not Found"，说"页面不存在"）
- **错误码映射**：后端错误码 → 前端 i18n 文案表，集中管理
- **分级处理**：
  - 表单校验错误 → 字段级别红色提示
  - 操作失败 → Toast 错误
  - 页面级错误 → ErrorBoundary 降级 UI（重试按钮）
  - 致命错误 → 错误页面 + 报告按钮
- **不吞错误**：所有 catch 必须 log，不能空 catch

### 5.4 数据加载基线

- **首屏**：骨架屏，不白屏，不转圈
- **局部加载**：按钮内 Spinner（提交中），不全局遮罩
- **懒加载**：非首屏组件/路由懒加载（动态 import）
- **预加载**：hover 到链接时预加载目标路由（V1.3+）
- **缓存策略**：不常变的数据缓存到 Pinia + localStorage，不每次重新请求

### 5.5 无障碍（A11y）最低标准

- **ARIA**：交互元素有正确的 role/aria-label/aria-expanded/aria-selected 等
- **键盘**：所有交互可键盘完成
- **焦点**：焦点始终可见、不丢失、不跳到意想不到的地方
- **颜色**：不仅靠颜色区分信息（加图标/文字辅助）
- **动画**：支持 prefers-reduced-motion
- **对比度**：文本对比度 ≥ 4.5:1
- **图片**：有意义的图片有 alt，装饰图片 alt=""
- **表单**：label 与 input 关联（for/id 或包裹）

## 6. 状态与数据流基线

> 详见 § 2.3 状态与数据流层，此处补充具体架构约束。

### 6.1 状态分类与存放

| 状态类型 | 存放在哪里 | 例子 |
| --- | --- | --- |
| 组件本地状态 | 组件内 `ref/reactive` | 弹窗开关、输入框值、hover 状态 |
| 跨组件共享状态 | Pinia store | 用户信息、当前项目、全局设置 |
| URL 状态 | 路由 query/params | 当前 Tab、搜索词、选中 ID |
| 服务端缓存 | Pinia + SWR 策略 | 项目列表、凭据列表、备份历史 |
| 持久化本地状态 | localStorage（通过存储封装） | 主题偏好、侧栏状态、草稿 |
| 实时状态 | Observable 事件总线 | 备份进度、同步状态、AI 任务进度 |

**不允许**：把应该放在 URL 的状态放到 Pinia；把应该本地的状态放到全局。

### 6.2 草稿与持久化

所有"用户长文本输入 + 持久化"场景统一使用草稿状态机：

```
     用户输入
        │
        ▼
    ┌─────────┐  防抖650ms   ┌─────────┐   请求成功   ┌─────────┐
    │ pending │ ───────────→ │ saving  │ ──────────→ │ saved   │
    └─────────┘              └─────────┘              └─────────┘
        ↑                        │ 请求失败
        │                        ▼
        │                   ┌─────────┐
        └───────────────────│ failed  │（自动重试或提示手动重试）
                            └─────────┘
```

- `_revision`：用户每次本地修改 +1（单调递增）
- `_savedRevision`：服务器已确认保存的版本
- 当 `_revision > _savedRevision` → 需要保存
- 失焦/路由切换/关闭标签页前调用 `flush()` 确保保存
- 双层 timer：防抖 timer + inFlight 请求队列（同一时间只跑一个保存请求）

### 6.3 实时通信架构

- 服务端推送 → SSE 连接 → Observable 事件总线 → 组件订阅
- 组件不直接解析 SSE 消息，只订阅 typed 事件
- 跨 Tab 同步通过 BroadcastChannel 中继事件
- 长任务进度通过 Polling 轮询（指数退避，800ms→1600ms→3200ms→4800ms 封顶）

## 8. 版本演进规则（三条线并行）

### 8.1 三条迭代线

前端版本迭代不是只有"加功能"一条线，而是三条线并行：

```
┌─────────────────────────────────────────────────────────────┐
│  功能迭代线（Feature Line）                                   │
│  做什么功能（命令面板/回收站/会议纪要/习惯打卡...）             │
│  主要影响层：L3-L7（功能特化）                                 │
│  规划位置：产品迭代演进计划.md                                │
├─────────────────────────────────────────────────────────────┤
```

**三条线的关系**：
- 功能线驱动产品能力增长
- 视觉线驱动体验提升
- 基建线驱动代码质量和开发效率
- **每条线都必须遵守本总纲的基线**，不允许因为赶功能就降低 L1-L3 的质量

### 8.2 每个版本的前端必检清单

任何版本发布前，前端必须通过以下检查（**版本无关，所有版本适用**）：

#### 功能检查
- [ ] 所有新功能在暗/亮双主题下正常显示
- [ ] 所有新功能可通过键盘完成核心操作
- [ ] 新功能的 Loading/Error/Empty 三态完整
- [ ] 新功能的错误提示是用户可读文案
- [ ] 用户输入不丢失（草稿状态机或等效机制）
- [ ] 浏览器后退/前进正常工作
- [ ] URL 状态可分享、可刷新恢复（如适用）

#### 视觉检查
- [ ] 8 个核心页面截图审计（总览/今日/项目/复盘/凭据/数据/设置/新功能页面）
- [ ] 无文本溢出/遮挡/对齐问题
- [ ] 所有视觉值通过 CSS 变量引用（无硬编码颜色/字号/间距）
- [ ] 动效在 reduced-motion 下正确降级
- [ ] 焦点轮廓清晰可见

#### 工程检查
- [ ] ESLint 0 error
- [ ] 新增工具函数有单元测试
- [ ] 无 `console.log` 残留（用 logger 替代）
- [ ] 无 `alert()` 调用（用 Toast/Modal 替代）
- [ ] 无直接 `fetch`（通过 request.js 封装）
- [ ] 无硬编码中文长字符串（走 i18n）
- [ ] commit message 符合规范

#### 性能检查
- [ ] 首屏无明显白屏
- [ ] 命令面板/弹窗打开无明显延迟
- [ ] 无内存泄漏（长时间使用不卡死）
- [ ] 网络请求无瀑布（关键请求串行化问题）

### 8.3 向后兼容规则

- **数据兼容**：新版本必须能读取旧版本的数据（Prisma migration + 前端数据版本检测）
- **URL 兼容**：旧版本的 URL（书签）在新版本能正确解析
- **localStorage 兼容**：本地存储数据带版本号，升级时自动迁移
- **主题兼容**：旧主题配置在新版本有效（或自动迁移到新主题）

### 8.4 废弃与迁移策略

当需要废弃某个 API/组件/规范时：

1. **标记废弃**：在代码中加 `@deprecated` JSDoc 注释，console warning
2. **提供替代**：必须在废弃的同时提供新方式
3. **保留至少一个版本**：废弃的 API 至少保留一个完整版本周期
4. **文档更新**：本总纲和相关文档同步更新
5. **迁移指南**：在版本更新记录中说明如何迁移

### 8.5 本总纲的修订流程

本总纲不是一成不变的。修订流程：

1. 发现本总纲有不足/需要新增原则
2. 在 [产品迭代演进计划.md](./产品迭代演进计划.md) 的"决策记录"中记录修订提案
3. 与用户确认后更新本总纲
4. 在本文件附录 B 记录变更内容
5. 如果修订影响已实现代码，在下一版本中统一修正

## 9. 拿到新版本任务后的前端实操指南

> 给新 AI：当你拿到一个新版本的开发任务后，按以下步骤思考前端。

### 9.1 新版本前端思考流程

```
Step 1：读本总纲 § 1 前端哲学
        → 确认理解产品的体验基调

Step 2：读本总纲 § 2 分层架构
        → 理解 7 层结构

Step 3：读 [产品迭代演进计划.md](./产品迭代演进计划.md) 的当前版本章节
        → 知道这个版本要做什么功能

Step 4：对每个新功能，从底向上思考：
        ① L1 工程规范：是否需要新的 Lint 规则/测试/文档？
        ② L2 基础设施：是否需要新的工具函数/封装/composable？
        ③ L3 状态数据流：数据怎么存、怎么流、怎么同步？
        ④ L4 布局系统：页面/组件的骨架怎么搭？
        ⑤ L5 组件库：需要新组件还是复用现有组件？
        ⑥ L6 交互细节：键盘/焦点/动效/反馈怎么处理？
        ⑦ L7 视觉呈现：令牌怎么映射、主题怎么适配？
        ⑧ L1/L2 分离：哪些是主题无关逻辑，哪些是主题相关装饰？

Step 5：读本总纲 § 8.2 版本必检清单
        → 开发过程中和发布前逐项检查

Step 6：如果发现新功能需要新的基础设施/组件/规范，
        先补 L1-L3，再做 L4-L7（先奠基，再盖楼）
```

### 9.2 新功能开发前端 Checklist

每个新功能开发前，问自己这些问题：

- [ ] 这个功能的数据模型是什么？需要新的 Pinia store 吗？
- [ ] 数据从哪来？API？本地？实时推送？缓存策略？
- [ ] URL 需要反映状态吗？用户能通过 URL 分享/刷新吗？
- [ ] 有用户输入吗？需要草稿保存吗？怎么保证不丢字？
- [ ] 加载态/错误态/空态长什么样？
- [ ] 键盘能完成核心操作吗？焦点管理怎么处理？
- [ ] 用什么组件？现有组件能满足吗？需要新组件吗？
- [ ] 动效怎么设计？遵守动效系统吗？reduced-motion 下怎么退化？
- [ ] 暗/亮主题都适配了吗？有没有硬编码颜色？
- [ ] 需要新的工具函数/Hook 吗？应该放到 L2 吗？
- [ ] 对其他模块有影响吗？跨 Tab 同步怎么办？
- [ ] 测试怎么写？单元测试覆盖哪些？
- [ ] 装饰元素是否在 theme.json 中有开关？（L2 分离）

### 9.3 新主题添加流程（V1.4+）

1. 在 `frontend/src/themes/` 下新建 `<theme-id>/` 目录
2. 按 § 3.2 规范填写 `theme.json`（dark + light 两套令牌）
3. 编写 `tokens.css`（CSS 变量）
4. 如需组件样式覆盖，写 `components.css`
5. 运行 `scripts/validate-theme.js` 校验
6. 在系统设置中注册新主题选项
7. 跑 8 个核心页面截图审计
8. 在视觉规范文档中记录新主题
9. 更新本总纲附录 B

## 附录 A · 术语表

| 术语 | 含义 |
| --- | --- |
| **L1/L2 分离** | 主题无关的行为（L1）和主题相关的视觉（L2）分层设计 |
| **三态** | Loading/Error/Empty，异步内容的三种非成功状态 |
| **草稿 5 态机** | pending/saving/saved/failed/null，用户输入持久化的状态管理 |
| **设计令牌 (Design Tokens)** | 通过 CSS 变量定义的视觉值（颜色/间距/字号等） |
| **语义令牌** | 有语义命名的令牌（如 `--color-danger`），组件引用它 |
| **焦点陷阱** | Modal 打开时 Tab 键不跳出 Modal 的机制 |
| **焦点还原** | 关闭浮层后焦点回到触发元素的机制 |
| **τ 阻尼** | 用时间常数（而非帧数）控制动效，跨刷新率一致 |
| **Observable 事件总线** | 发布-订阅模式的事件系统，解耦事件生产者和消费者 |
| **SWR** | Stale-While-Revalidate，先显示缓存再后台更新 |
| **乐观更新** | 先更新 UI 再等服务器响应，失败回滚 |
| **ARIA** | Accessible Rich Internet Applications，无障碍网页属性 |
| **reduced-motion** | 系统级"减少动态效果"设置 |
| **BEM** | Block-Element-Modifier CSS 命名方法论 |
| **Feature Flag** | 功能开关，运行时控制功能开启/关闭 |
