# 阅读模块设计（V1.5）

> **适用范围**：V1.5 新增的「阅读 / 资料」模块——收藏文章、公众号推文、CVE 情报与论文，跟踪阅读进度，并把读到的东西一键沉淀进 Vault。
> **定位**：本文件描述阅读模块的数据模型、接口契约、状态机、沉淀通路与前端交互，是修改本模块前必读的规范。
> **唯一事实来源**：`backend/prisma/schema.prisma` 的 `ReadingMaterial` 模型、`backend/src/modules/reading/` 六个文件、`frontend/js/modules/ReadingPage.js`。
>
> 相关文档：`docs/状态机与字段规范.md`（状态机工厂与既有三套状态机）、`docs/沉淀模块设计.md`（Vault 侧设计）、`docs/搜索与索引规范.md`（阅读已接入跨模块搜索）、`docs/模块挂载点规范.md`（四触点挂载）。

---

## 1. 定位与范围

### 1.1 解决的问题

安全从业者的日常输入分散在四类载体：技术文章、公众号推文、CVE 情报、学术论文。此前工作台没有统一的登记入口，读过的东西散落在浏览器书签里，读完之后也没有通路变成自己的沉淀。

V1.5 的阅读模块解决两件事：

1. **登记与跟踪**：四类资料统一入库，用「未读 → 在读 → 已沉淀 → 已归档」四态跟踪进度。
2. **沉淀通路**：读完的资料一键转化为 Vault 沉淀条目，保留来源可追溯（`sourceType` + `sourceId`），与 `docs/沉淀模块设计.md` 的「引用不复制」原则一致。

### 1.2 在设计上的三个取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 资料正文是否入库 | **否**，只存 `sourceUrl` 链接与 `notes` 笔记 | 本地优先单机应用，存正文意味着爬虫/解析/版权问题；链接 + 笔记已满足个人知识管理需求 |
| 状态变更是否走独立端点 | **是**，`PATCH /:id/status` 与 `PUT /:id` 分离 | 状态变更需过状态机校验，与字段编辑是不同的权限与校验语义 |
| 自定义字段是否建列 | **否**，存 `customFields` JSON 字符串 | 字段由用户在设置页自定义，无法预建列；SQLite 无原生 JSON 类型，用 TEXT 存 JSON 串是既有惯例（与 `tags` 一致） |

### 1.3 明确不属于本版范围

| 能力 | 说明 |
| --- | --- |
| 正文抓取 / 离线阅读 | 只存链接，不抓取正文 |
| 全文检索阅读笔记 | 走全局搜索（`/api/v1/search`，见 §8），模块内只有 `title` / `notes` / `sourceUrl` 的 `contains` 匹配 |
| 附件 / PDF 管理 | 无文件上传 |
| 阅读进度百分比 | 四态是粗粒度状态，无「读到第几页」 |
| 标签自动补全 | 标签为自由输入，逗号分隔，无历史标签下拉 |
| 批量操作 | 无批量删除 / 批量沉淀 / 批量改状态 |

## 2. 数据模型

### 2.1 `ReadingMaterial`

定义于 `backend/prisma/schema.prisma:539`：

```prisma
model ReadingMaterial {
  id            String   @id @default(cuid())
  title         String // 资料标题（必填）
  sourceUrl     String? // 来源 URL
  type          String   @default("文章") // 文章 / 公众号 / CVE / 论文
  tags          String   @default("[]") // 标签 JSON 数组
  readingStatus String   @default("unread") // unread / reading / precipitated / archived
  notes         String? // 阅读笔记（Markdown）
  customFields  String   @default("{}") // 扩展文本字段 JSON 对象（系统设置定义，详见自定义字段规范）
  sortOrder     Int      @default(0)
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  deletedAt     DateTime?

  @@index([type])
  @@index([readingStatus])
  @@map("reading_materials")
}
```

| 字段 | 类型 | 默认 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | String (cuid) | `cuid()` | 否 | 主键 |
| `title` | String | — | 否 | 资料标题。Zod 限长 1~200 字符 |
| `sourceUrl` | String | `null` | 是 | 来源 URL，Zod 限长 500。空串会被 service 层 `_nullify()` 归一为 `null` |
| `type` | String | `'文章'` | 否 | 四种类型之一，见 §3。受「字段 / 状态机配置平台」的 `reading.type` 下拉项约束 |
| `tags` | String | `'[]'` | 否 | **JSON 数组字符串**，如 `'["AI安全","零信任"]'`。空数组时存 `'[]'` 而非 `null` |
| `readingStatus` | String | `'unread'` | 否 | 四态之一，见 §4 |
| `notes` | String | `null` | 是 | 阅读笔记，Markdown 文本，Zod 限长 20000 |
| `customFields` | String | `'{}'` | 否 | **JSON 对象字符串**，见 §6。空对象时存 `'{}'` |
| `sortOrder` | Int | `0` | 否 | 排序权重，列表默认排序的第一优先级 |
| `createdAt` | DateTime | `now()` | 否 | — |
| `updatedAt` | DateTime | 自动 | 否 | — |
| `deletedAt` | DateTime | `null` | 是 | 软删除标记，非 null 即已删除 |

**索引**：`type` 与 `readingStatus` 各一个单列索引，对应列表页最常用的两个筛选维度。表名映射为 `reading_materials`。

### 2.2 关于 JSON 列的两个约定

`tags` 与 `customFields` 都是 TEXT 列存 JSON 串，遵循全站既有惯例（与 `project.securityDomains`、`vault.tags` 等一致）：

- **写入**：service 层 `JSON.stringify()`；空值写 `'[]'` / `'{}'`，**不写 `null`**（避免读取侧每次判空）。
- **读取**：`toPublic()` 里 `parseJsonArray()` / `parseJsonObject()` 反序列化；`try/catch` 失败时回落 `[]` / `{}`，**脏数据不会导致接口报错**。

这个约定的副作用是：查询标签只能做子串匹配（`where.tags = { contains: tags }`），无法做「精确包含某个标签」的数组语义查询。搜 `AI` 会命中 `AI安全` 也会命中 `AntiAI` 之类含该子串的标签。已知限制，见 §10。

## 3. 四种资料类型（READING_TYPE）

定义于 `backend/src/common/constants/enums.js:310`：

```js
export const READING_TYPE = {
  ARTICLE: '文章',
  WECHAT: '公众号',
  CVE: 'CVE',
  PAPER: '论文',
};
```

| 常量 | 值 | 用途 | 前端标签配色 |
| --- | --- | --- | --- |
| `ARTICLE` | `文章` | 技术博客、官方文档、资讯 | `default` |
| `WECHAT` | `公众号` | 微信公众号推文 | `info` |
| `CVE` | `CVE` | 漏洞情报、安全公告 | `danger` |
| `PAPER` | `论文` | 学术论文、技术白皮书 | `warning` |

**取值是中文字符串，不是英文 key。** 这一点很重要：数据库里存的就是 `文章` / `公众号` / `CVE` / `论文`，查询参数也传中文（需 URL 编码）。这是与 `READING_STATUS`（英文值）的显著差异，改造时不要混淆。

配色映射定义在 `frontend/js/modules/ReadingPage.js:11` 的 `READING_TYPE_TAG_TYPES`，是前端硬编码，后端不参与。

### 3.1 类型可扩展

类型的合法取值**不再硬编码为 `z.enum`**，改为运行期从「字段 / 状态机配置平台」读取：

```js
// reading.schema.js
const typeValue = () => dropdownValue('reading.type', '非法的阅读资料类型');
```

`dropdownValue(scope, msg)` 来自 `backend/src/lib/configSchema.js`，内部调用 `getDropdownSync(scope)` 读取同步缓存。缓存未装载时回落到 `Object.values(READING_TYPE)` 默认值。

配置平台的默认种子（`fieldConfig.service.js#defaultConfig()`）：

```js
dropdowns: {
  'reading.type': Object.values(READING_TYPE),   // ['文章','公众号','CVE','论文']
  ...
}
```

因此**用户在设置页新增一个类型（如「播客」）后，后端校验与前端下拉会同时接受新值**，无需改代码。详见 §6.3。

## 4. 四态状态机（READING_STATUS）

### 4.1 状态定义

定义于 `backend/src/common/constants/enums.js:318`：

```js
export const READING_STATUS = {
  UNREAD: 'unread',
  READING: 'reading',
  PRECIPITATED: 'precipitated',
  ARCHIVED: 'archived',
};
```

| 状态值 | 中文标签 | 语义 | 前端标签配色 |
| --- | --- | --- | --- |
| `unread` | 未读 | 刚登记，还没开始看 | `default` |
| `reading` | 在读 | 正在阅读中 | `info` |
| `precipitated` | 已沉淀 | 已转化为 Vault 沉淀 | `success` |
| `archived` | 已归档 | 已完结或放弃，不再跟踪 | `warning` |

与 `type` 相反，**状态值是英文字符串**。

### 4.2 迁移表

定义于 `backend/src/common/constants/enums.js:326`：

```js
export const READING_STATUS_TRANSITIONS = {
  unread: ['reading', 'archived'],
  reading: ['precipitated', 'archived', 'unread'],
  precipitated: ['archived', 'reading'],
  archived: ['unread'],
};
```

### 4.3 完整迁移矩阵（4×4 = 16）

| from ↓ \ to → | `unread` | `reading` | `precipitated` | `archived` |
| --- | --- | --- | --- | --- |
| **`unread`** | 合法(自环) | 合法 | 非法 | 合法 |
| **`reading`** | 合法 | 合法(自环) | 合法 | 合法 |
| **`precipitated`** | 非法 | 合法 | 合法(自环) | 合法 |
| **`archived`** | 合法 | 非法 | 非法 | 合法(自环) |

统计：**合法 12（含 4 个自环）/ 非法 4**。

非法迁移清单：

| 迁移 | 为何禁止 |
| --- | --- |
| `unread → precipitated` | 不允许跳过「在读」直接标记已沉淀 |
| `precipitated → unread` | 已沉淀的资料不能退回未读 |
| `archived → reading` | 归档后必须先回到 `unread` 重开，不能直接进入在读 |
| `archived → precipitated` | 归档后必须先回到 `unread` |

### 4.4 自环语义

与全站其他状态机一致（详见 `docs/状态机与字段规范.md` §1.1）：`from === to` 时工厂层恒判合法，即使 `READING_STATUS_TRANSITIONS[from]` 数组里没有写自身——表中四个数组**都没有包含自身**，但自环仍合法。这是 `createStateMachine` 的实现约定，穷举测试时合法数比数组元素之和多 4，属正常现象。

### 4.5 与其他状态机的横向对比

| 状态机 | 状态数 | 终态是否可重开 | 迁移表常量 |
| --- | --- | --- | --- |
| 任务 5 态 | 5 | 是（`completed → pending`） | `TODO_STATUS_TRANSITIONS` |
| 项目 6 阶段 | 6 | 是（`项目结项 → 需求沟通`） | `PROJECT_PHASE_TRANSITIONS` |
| 复盘 3 态 | 3 | — | — |
| **阅读 4 态** | **4** | **是（`archived → unread`）** | `READING_STATUS_TRANSITIONS` |

阅读状态机的特点是**双向可回流**：`reading ↔ unread`、`precipitated ↔ reading`、`archived ↔ unread` 都成对出现，比项目阶段那种单向推进的机器更宽松。原因是阅读行为本身会反复（读一半放下、沉淀后再补充阅读、归档后又想起来重看）。

### 4.6 状态机的可配置化

与类型同理，状态值校验走配置平台：

```js
// reading.schema.js
const statusValue = () => stateValue('reading.status', '非法的阅读状态');

export const changeReadingStatusSchema = z.object({ status: statusValue() });
```

`changeStatus()` 的迁移表也优先取配置：

```js
await ensureFieldConfigCache();
const smConfig = getStateMachineSync('reading.status');
const states = smConfig?.states || Object.values(READING_STATUS);
const transitions = smConfig?.transitions || READING_STATUS_TRANSITIONS;
if (!states.includes(toStatus)) {
  throw new BusinessError(ErrorCodes.PARAM_ERROR, `非法的阅读状态「${toStatus}」`);
}
const exists = await readingRepository.findById(id);
if (!exists) {
  throw new BusinessError(ErrorCodes.DB_NOT_FOUND, '阅读项不存在');
}
const sm = createStateMachine({ name: 'ReadingStatus', ALLOWED_TRANSITIONS: transitions });
await sm.transition(exists.readingStatus, toStatus);
const updated = await readingRepository.updateById(id, { readingStatus: toStatus });
```

执行顺序值得注意：**先校验目标状态是否在 `states` 白名单 → 再查记录是否存在 → 最后过状态机迁移校验**。因此对一条不存在的 id 传一个非法状态，抛的是 `PARAM_ERROR` 而非 `DB_NOT_FOUND`。

配置平台的默认种子：

```js
stateMachines: {
  'reading.status': {
    states: Object.values(READING_STATUS),
    transitions: READING_STATUS_TRANSITIONS,
    initial: READING_STATUS.UNREAD,
  },
  ...
}
```

### 5.3 新增：`POST /api/v1/readings`

请求体（`createReadingSchema`）：

| 字段 | 类型 | 必填 | 默认 | 校验规则 |
| --- | --- | --- | --- | --- |
| `title` | string | **是** | — | `z.string().min(1, '标题不能为空').max(200, '标题长度不能超过 200 字符')` |
| `sourceUrl` | string \| null | 否 | `null` | `z.string().max(500).nullable().optional().or(z.literal(''))` |
| `type` | string | 否 | `'文章'` | `dropdownValue('reading.type', …).default(READING_TYPE.ARTICLE)` |
| `tags` | `string[]` | 否 | `[]` | `z.array(z.string()).optional()` |
| `readingStatus` | string | 否 | `'unread'` | `stateValue('reading.status', …).default(READING_STATUS.UNREAD)` |
| `notes` | string \| null | 否 | `null` | `z.string().max(20000).nullable().optional().or(z.literal(''))` |
| `customFields` | `Record<string, any>` | 否 | `{}` | `z.record(z.string(), z.any()).optional()` |
| `sortOrder` | number（非负整数） | 否 | `0` | `z.number().int().nonnegative().default(0)` |

两个细节：

- `sourceUrl` 与 `notes` 的 schema 都带 `.or(z.literal(''))`，**显式接受空串**。service 层的 `_nullify()` 会把 `''` / `undefined` / `null` 统一转成 `null` 再入库，因此前端传空串与不传该字段效果一致。
- `tags` 与 `customFields` 入库前序列化：`tags.length ? JSON.stringify(tags) : '[]'`、`customFields ? JSON.stringify(customFields) : '{}'`。

响应：`toPublic(created)`，即 §5.8 的 11 字段结构。

### 5.4 编辑：`PUT /api/v1/readings/:id`

`updateReadingSchema` 在 `id` 之外全部字段均为 `optional()`，是部分更新语义。service 实现用 `'x' in fields` 判断字段是否被显式传入，因此**传 `null` 与不传字段是不同的**：传 `notes: null` 会清空笔记，不传则不改动。

> 例外：`type` 与 `readingStatus` 虽然也在 `updateReadingSchema` 里，但语义上**不建议通过 `PUT` 修改状态**——`PUT` 不过状态机校验（`if ('readingStatus' in fields) updateData.readingStatus = fields.readingStatus;`，直接赋值）。改状态应走 `PATCH /:id/status`。这是一个需要注意的绕过口子，见 §10 限制 L4。

### 5.5 列表：`GET /api/v1/readings`

查询参数（`listReadingSchema`）：

| 参数 | 类型 | 校验 | 说明 |
| --- | --- | --- | --- |
| `q` | string | `z.string().optional()` | 关键词，对 `title` / `notes` / `sourceUrl` 三列做 `contains` 匹配（OR） |
| `type` | string | `dropdownValue('reading.type').optional()` | 按类型精确过滤 |
| `readingStatus` | string | `stateValue('reading.status').optional()` | 按状态精确过滤 |
| `tags` | string | `z.string().optional()` | 标签子串匹配（`where.tags = { contains: tags }`），传单个标签 |
| `fields` | string | `z.string().optional()` | **V1.5 字段裁剪**，逗号分隔，见 §7 |
| `page` | number | `z.coerce.number().int().positive().optional()` | 页码 |
| `limit` | number | `z.coerce.number().int().positive().optional()` | 每页条数 |
| `sort` | enum | `z.enum(['createdAt','updatedAt','sortOrder','readingStatus','type']).optional()` | 排序字段白名单 |
| `order` | enum | `z.enum(['asc','desc']).optional()` | 排序方向 |

**默认排序**：未传 `sort` 时为 `[{ sortOrder: 'asc' }, { createdAt: 'desc' }]`——先按 `sortOrder` 升序（数值小的在前），同序时按创建时间倒序（新建在前）。

传 `sort` 时 `orderBy` 退化为单字段：`[{ [sort]: order === 'asc' ? 'asc' : 'desc' }]`，即 `order` 缺省为 `desc`。

**响应形态**：`BaseRepository#findMany` 在传 `page` 时返回 `{ list, total, page, pageSize }`，不传时返回数组。service 层两种形态都做了兜底：

```js
if (Array.isArray(result)) {
  const list = result.map((r) => this.toPublic(r));
  return fields ? pickFields(list, fields) : list;
}
const list = result.list.map((r) => this.toPublic(r));
return { ...result, list: fields ? pickFields(list, fields) : list };
```

前端 `ReadingPage` 同样做了双形态兼容：`list.value = Array.isArray(raw) ? raw : (raw.list || [])`。

### 5.6 状态切换：`PATCH /api/v1/readings/:id/status`

请求体：`{ "status": "reading" }`，走 `changeReadingStatusSchema = z.object({ status: statusValue() })`。

| 错误场景 | 错误码 | 文案 |
| --- | --- | --- |
| `status` 不在配置平台 `states` 内 | `PARAM_ERROR` | `非法的阅读状态「xxx」` |
| `id` 对应的记录不存在 | `DB_NOT_FOUND` | `阅读项不存在` |
| 迁移不在 `transitions` 白名单内 | `PARAM_ERROR` | 由状态机工厂生成（详见 `docs/状态机与字段规范.md` §1.1） |

响应：`toPublic(updated)`。

## 6. 自定义扩展字段

### 6.1 存储方式

`customFields` 是 **TEXT 列存 JSON 对象字符串**，键与值都是字符串：

```json
{ "author": "张三", "score": "9", "CVE编号": "CVE-2026-1234" }
```

数据库里就是这一串字符（`customFields String @default("{}")`）。

设计意图：不同资料类型需要记录的属性不同（论文要记「作者 / 会议」，CVE 要记「CVSS 评分 / 影响版本」），预建列既无法穷举又会造成大量空列。因此由用户在设置页定义字段名，值以 key-value 形式自由填写。

### 6.2 service 层的读写

**写入**（`create` / `update`）：

```js
if ('customFields' in fields) {
  updateData.customFields = fields.customFields ? JSON.stringify(fields.customFields) : '{}';
}
```

**读取**（`toPublic`）：

```js
customFields: parseJsonObject(r.customFields)
```

```js
function parseJsonObject(str, fallback = {}) {
  if (!str) return fallback;
  try {
    const v = JSON.parse(str);
    return v && typeof v === 'object' ? v : fallback;
  } catch {
    return fallback;
  }
}
```

三点保证：

1. 列值为空串 / null 时回落 `{}`，接口不会返回 `null`。
2. JSON 解析失败（手工改库导致的脏数据）时回落 `{}`，**不抛错、不影响其他字段**。
3. 解析出非对象（如 `'123'` 或 `'"str"'`）时同样回落 `{}`。

Zod 侧约束是 `z.record(z.string(), z.any())`——键必须是字符串，值任意类型。但**前端只产生字符串值**（`htp-input` 的 `v-model` 绑定的是 string），所以实际入库的都是 `string → string` 映射。若通过 API 直接传数字或嵌套对象，能存进去，但前端编辑时会用 `String(cf[k])` 强转展示。

### 6.3 与「字段 / 状态机配置平台」的关系

V1.5 的配置平台（`backend/src/modules/system/fieldConfig.service.js`，§8.3）为阅读模块预置了两个 scope：

```js
customFields: {
  reading: [],   // 默认空数组，即「未定义任何扩展字段」
  project: [],
},
```

即：**`reading` 这个 scope 存在，但默认没有任何字段定义**。

这个设计下，`customFields` 与配置平台的关系是**松耦合**的：

- 配置平台的 `customFields.reading` 用于描述「这个模块有哪些字段定义」（供前端渲染带类型提示的表单）。默认数组为空时，`ReadingPage` **不使用它**，而是直接渲染一个自由的 key-value 编辑器（见 §7.4）。
- 无论配置平台里有没有定义，用户都能在编辑弹窗里自行「+ 添加字段」，填任意键值对，`customFields` 都会照单全收。

也就是说，**当前 `ReadingPage` 的扩展字段编辑器是自由模式，没有消费 `customFields.reading` 的定义**。这是一个已具备能力但尚未接线的点，见 §10 限制 L5。

与 `type` / `readingStatus` 不同——那两个是**紧耦合**：值必须落在配置平台的下拉项 / 状态集内，否则 Zod 直接拒绝。

### 6.4 前端编辑器的数据流

`ReadingPage.js` 中 `form.customFields` 是 **行数组** `[{key, value}]` 而非对象——因为 key-value 编辑器的行需要稳定的遍历与删除语义，对象无法表达「空 key 的临时行」。

**打开编辑弹窗时**（对象 → 行数组）：

```js
const cf = item.customFields && typeof item.customFields === 'object' ? item.customFields : {};
const cfRows = Object.keys(cf).map((k) => ({ key: k, value: cf[k] == null ? '' : String(cf[k]) }));
```

**提交时**（行数组 → 对象，跳过空 key）：

```js
function buildCustomFields() {
  const obj = {};
  form.customFields.forEach((row) => {
    const k = (row.key || '').trim();
    if (k) obj[k] = row.value;
  });
  return obj;
}
```

三点行为：

1. **空 key 的行被静默丢弃**——用户点了「+ 添加字段」但没填名字，保存时该行消失，不报错。
2. **重复 key 时后者覆盖前者**——`obj[k] = row.value` 直接赋值，无去重校验。
3. **value 不 trim**——只有 key 做了 `trim()`，值保留原始空格。

列表页展示扩展字段时只显示数量：`扩展字段 {{ Object.keys(item.customFields).length }} 项`，不展开具体键值。

## 7. 与 Vault 的沉淀通路

### 7.1 转化实现

`reading.service.js#convertToVault()`：

```js
async convertToVault(id) {
  readingIdSchema.parse({ id });
  const r = await readingRepository.findById(id);
  if (!r) {
    throw new BusinessError(ErrorCodes.DB_NOT_FOUND, '阅读项不存在');
  }
  const vaultItem = await vaultService.upsertFromSource({
    sourceType: 'READING_NOTE',
    sourceId: id,
    title: r.title,
    content: r.notes || '',
    tags: parseJsonArray(r.tags),
  });
  return {
    id: vaultItem.id,
    topic: vaultItem.topic,
    sourceType: vaultItem.sourceType,
    sourceId: vaultItem.sourceId,
  };
}
```

字段映射：

| 源（ReadingMaterial） | 目标（VaultItem） | 说明 |
| --- | --- | --- |
| `title` | `topic` | 沉淀标题 |
| `notes` | `content` | 阅读笔记直接作为沉淀正文 |
| `tags`（JSON 串） | `tags`（数组） | 经 `parseJsonArray()` 反序列化后传入 |
| `id` | `sourceId` | 来源追溯键 |
| — | `sourceType` | 固定 `'READING_NOTE'` |
| — | `status` | 由 `vaultService.create()` 内部设为 `'DRAFT'` |
| — | `sourceUrl` | **传 `null`**，见下 |

### 7.2 幂等性

幂等由 `vaultService.upsertFromSource()` 保证：

```js
async upsertFromSource({ sourceType, sourceId, title, content, tags = [] }) {
  const existed = await vaultRepository.findOne({ sourceType, sourceId });
  if (existed) return existed;
  return this.create({
    topic: title || '阅读沉淀',
    content: content || '',
    tags,
    status: 'DRAFT',
    sourceType,
    sourceId,
    sourceUrl: null,
  });
}
```

查找键是 `(sourceType, sourceId)` 二元组。同一条阅读资料重复点击「沉淀」，**不会创建第二个 Vault 条目，直接返回已存在的那个**。测试 `convertToVault 一键沉淀且幂等` 断言 `v2.id === v1.id`。

### 7.3 两个需要注意的语义

| 现象 | 说明 |
| --- | --- |
| **沉淀后不回写 `readingStatus`** | 点击「沉淀」只创建 Vault 条目，阅读资料的 `readingStatus` **不会自动变成 `precipitated`**。用户需要再手动切一次状态。这是当前实现与「已沉淀」语义之间的缝隙 |
| **`sourceUrl` 传 null** | `upsertFromSource` 硬编码 `sourceUrl: null`，阅读资料的 `sourceUrl` **不会带进 Vault 条目**。沉淀里想回溯原文链接需要从 Vault 反查 `sourceId` 再查阅读表 |

另外，`upsertFromSource` 的 `existed` 分支**直接返回既有条目，不更新内容**。因此：先沉淀 → 再回阅读资料补充笔记 → 再次点击「沉淀」，Vault 里的 `content` **仍是第一次沉淀时的旧笔记**。这是「upsert」名不副实的地方——实际是「find-or-create」。见 §10 限制 L3。

`ReadingPage.js`：

## 9. `?fields=` 列表字段裁剪

V1.5 引入的列表响应裁剪能力，阅读模块是三个已接入模块之一（另两个是 `project` 与 `todo`）。

### 9.1 实现

`backend/src/lib/fieldSelector.js`：

```js
export function parseFieldsParam(fields) {
  if (!fields || typeof fields !== 'string') return null;
  const arr = fields.split(',').map((s) => s.trim()).filter(Boolean);
  return arr.length ? arr : null;
}

export function pickFields(rows, fields) {
  if (!Array.isArray(rows)) return rows;
  if (!Array.isArray(fields) || !fields.length) return rows;
  return rows.map((row) => {
    if (!row || typeof row !== 'object' || Array.isArray(row)) return row;
    const out = {};
    for (const f of fields) {
      if (Object.prototype.hasOwnProperty.call(row, f)) out[f] = row[f];
    }
    return out;
  });
}
```

### 9.2 裁剪时机

裁剪发生在 `toPublic()` **之后**：先完整序列化，再挑字段。因此裁剪只减少响应体量，**不减少数据库查询与序列化开销**——它优化的是网络传输（虽然本地单机应用下这个收益也有限）。

`hasOwnProperty` 判断意味着**传一个不存在的字段名不会产生 undefined 键**，只会被忽略。

### 9.3 阅读模块的接入点

`reading.schema.js` 的 `listReadingSchema` 含 `fields: z.string().optional()`（注释 `// V1.5 ?fields 字段裁剪`）；`reading.service.js#list()` 在返回前应用 `pickFields`。

示例：`GET /api/v1/readings?fields=id,title` 返回 `[{ id, title }]`，不含 `notes` / `type` / `customFields` 等。

测试 `list ?fields 裁剪仅返回指定字段` 断言：响应含 `id` / `title`，`notes` 与 `type` 为 `undefined`。

### 9.4 三个模块的接入现状

| 模块 | schema 是否声明 `fields` | service 是否调用 `pickFields` |
| --- | --- | --- |
| `reading` | 是（`reading.schema.js:40`） | 是（`reading.service.js:125-131`） |
| `project` | 是（`project.schema.js:52`） | 是（`project.service.js:177-178`） |
| `todo` | 是（`todo.schema.js:49`） | 是（`todo.service.js:167-172`） |

`todo.service.js` 的注释里额外记了一个坑（原文引用）：

> 否则 `pickFields` 遇到非数组会原样返回，导致裁剪静默失效。

即 `todo` 的列表返回形态需要先行归一为数组，否则裁剪会无声失败。新增接入模块时要注意这一点。

```js
}
```

判定式 `from === to || transitions[from].includes(to)` 显式体现了 §4.4 的自环语义。这 16 个用例与 §4.3 的矩阵表一一对应（合法 12 / 非法 4）。

### 10.3 测试约定

- 独立测试库：`process.env.HTD_TEST_DB_URL`。
- 数据前缀：`reading.test.js` 用 `TEST_`，`reading-statemachine.test.js` 用 `SM_`。
- 清理：`reading.test.js` 在 `beforeEach` / `afterEach` 双向清理 `readingMaterial`（按 title contains `TEST_`）与 `vaultItem`（`sourceType: 'READING_NOTE'`）；`reading-statemachine.test.js` 只在 `afterAll` 清理一次。
- **`reading-statemachine.test.js` 用的是 `prisma.readingMaterial.delete()`（硬删除）而非软删除**，以避免与 service 的 `deletedAt: null` 过滤纠缠。

### 10.4 覆盖缺口（诚实清单）

| 缺口 | 影响 |
| --- | --- |
| 无路由 / 控制器层测试 | 7 个端点的参数校验与响应包裹形态未验证 |
| 未测 `q` 关键词搜索 | `list` 的 `OR` 三列匹配无用例 |
| 未测 `tags` 子串过滤 | 标签筛选无用例 |
| 未测 `sort` / `order` / `page` / `limit` | 排序与分页无用例 |
| 未测自定义字段的脏数据回落 | `parseJsonObject` 的 try/catch 分支无用例 |
| 未测 `?fields` 传不存在的字段名 | 静默忽略的行为无用例守护 |
| 前端 `ReadingPage` 无自动化测试 | 配置回落、状态下拉过滤、key-value 编辑器均依赖人工验收 |

## 11. 已知限制与后续演进

### 11.1 已知限制

| 编号 | 限制 | 影响 |
| --- | --- | --- |
| L1 | **标签为子串匹配** | `tags` 存 JSON 串，只能 `contains` 匹配。搜 `AI` 会命中任何含该子串的标签，无法做精确的数组包含查询 |
| L2 | **`customFields` 不可查询** | 值埋在 JSON 串里，无法按扩展字段筛选或排序 |
| L3 | **`upsertFromSource` 不更新既有条目** | 沉淀后补充笔记再沉淀，Vault 内容不刷新。名为 upsert，实为 find-or-create |
| L4 | **`PUT /:id` 可绕过状态机改状态** | `updateReadingSchema` 含 `readingStatus` 且不过迁移校验。改状态应统一走 `PATCH /:id/status` |
| L5 | **扩展字段编辑器未消费配置平台定义** | `customFields.reading` 已预留 scope 但默认为空数组，`ReadingPage` 渲染的是自由 key-value 编辑器，不使用该定义 |
| L6 | **前端迁移表与配置平台不同步** | `ReadingPage` 硬编码 `READING_STATUS_TRANSITIONS`，不读配置平台的 `transitions`。用户改了迁移规则后，前端仍会展示后端将拒绝的选项 |
| L7 | **沉淀不联动改状态** | 点「沉淀」后 `readingStatus` 不变，需手动再切一次 |
| L8 | **`sourceUrl` 不进 Vault** | `upsertFromSource` 硬编码 `sourceUrl: null` |
| L9 | **删除文案与实际行为不符** | 提示「删除后不可恢复」，实际是软删除且可从回收站恢复 |
| L10 | **无批量操作** | 批量沉淀 / 批量归档 / 批量删除均未实现 |
| L11 | **列表统计作用于筛选结果** | 「未读 N / 已沉淀 N」跟随筛选变化，非全量统计 |
| L12 | **自定义字段值全为字符串** | 无数字 / 日期 / 布尔类型，也无值校验 |
| L13 | **扩展字段不参与全局搜索** | `MODULE_CONFIGS` 中 reading 的搜索字段只有 `title` / `notes` / `sourceUrl`，`customFields` 搜不到（见 `docs/搜索与索引规范.md` §4.2） |

### 11.2 后续演进建议

**低成本**

1. **修复 L9 文案**：把「删除后不可恢复」改为「已移入回收站，可在数据与部署页恢复」，与 `RecycleBinPage` 的实际能力对齐。
2. **修复 L4**：从 `updateReadingSchema` 中移除 `readingStatus`，或在该分支加上与 `changeStatus` 相同的状态机校验，堵住绕过口子。
3. **沉淀联动状态（L7）**：`convertToVault` 成功后，若当前状态为 `reading` 则自动切到 `precipitated`（`reading → precipitated` 是合法迁移，无需改迁移表）。若当前是 `unread` 则保持不动（因为 `unread → precipitated` 非法）。

**中成本**

4. **前端消费配置平台的 `transitions`（L6）**：把 `statusOptionsFor()` 改为读 `dataStore.fieldConfig.stateMachines['reading.status'].transitions`，回落链与 `cfgStatusValues` 保持一致。
5. **接线扩展字段定义（L5）**：在设置页提供 `customFields.reading` 的编辑 UI，`ReadingPage` 读该定义渲染带类型的表单项（可复用 `CUSTOM_FIELD_TYPE` 的 `single_line` / `multi_line`）。
6. **修复 L3 的 upsert 语义**：`upsertFromSource` 的 `existed` 分支改为更新 `topic` / `content` / `tags` 后再返回，或新增一个 `force` 参数区分「只创建」与「创建并更新」。需要评估：已有沉淀被手工编辑过的话，覆盖更新会丢失用户的修改。

**高成本（需重新论证）**

7. **扩展字段结构化（L1 / L2 / L12）**：把 `customFields` 拆成独立的 `ReadingFieldValue` 表（`readingId` + `fieldKey` + `fieldValue` + `fieldType`），换取可查询、可筛选、可排序、可类型化。代价是列表查询变成 JOIN 或 N+1，且需要数据迁移脚本。在扩展字段数量少、以展示为主的场景下，当前的 JSON 方案性价比更高，是否改造取决于用户是否真的产生了「按扩展字段筛选」的需求。

8. **正文抓取与离线阅读**：需要引入正文解析（Readability 类库）、本地存储目录、清理策略，与「本地优先」的边界需重新界定（是否要处理付费内容 / 版权）。当前只存链接的设计是刻意的保守选择，改动前应确认真实使用频率。
