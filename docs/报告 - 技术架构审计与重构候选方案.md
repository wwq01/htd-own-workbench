## 二、Top 技术债清单

> 排序依据：P0 = 已构成线上/发布可用性故障或 V2.0 硬阻塞；P1 = 显著抬高迭代成本或已产生不一致；P2 = 规范性欠账。

### P0-1｜端口顺延时全站写入 403（安全中间件与端口协商契约断裂）

**证据链**：

| 文件 | 行 | 内容 |
|------|-----|------|
| `backend/src/common/utils/port.js` | 9 | `FIXED_PORTS = [17388, 17389, 17390]` |
| `backend/src/server.js` | 55-58 | `findAvailablePort(...)` 返回值可能 ≠ `appConfig.port`，仅 `logger.warn` |
| `backend/src/server.js` | 61,64 | `createApp()` 后 `app.listen(port, ...)` —— 监听真实端口 |
| `backend/src/config/app.config.js` | 36 | `port: parseInt(process.env.HTD_PORT,10) \|\| 17388` —— **静态常量** |
| `backend/src/middleware/origin-guard.js` | 14-17 | `allowed` 写死 `http://127.0.0.1:${appConfig.port}` / `localhost:${appConfig.port}` |
| `backend/src/app.js` | 50-57 | CORS 白名单同样基于 `appConfig.port` |

**失效路径**：17388 被占用 → 服务实际监听 17389 → 用户浏览器访问 `http://127.0.0.1:17389` → 前端发起 POST，`Origin: http://127.0.0.1:17389` → `origin-guard.js:18` 判定不在 `allowed`（其中只有 17388）→ `next(BackendError(ORIGIN_FORBIDDEN, 403))`。

**影响**：**只读可用、所有写入操作全站失效**。这是最恶劣的故障形态——用户看到界面正常、数据正常渲染，只在保存时报 403，极难自诊断。且 `probeInstance`(`server.js:46`) 只探测 17388，17388 被**非本应用**进程占用时必然走到这条路径。

**为什么没被测出来**：`middleware/origin-guard.test.js:38,43` 硬编码 17388 构造 Origin，与 `appConfig.port` 默认值恰好一致，端口顺延场景零覆盖。

**旁证**：`app.js:54-56` 为 CORS 留了 `HTD_CORS_ORIGINS` 逃生阀，但 `origin-guard.js` **没有任何逃生阀**，即使运维知道问题也无法通过环境变量绕过。

### P0-2｜macOS 构建产物数据根目录必然错误

**证据链**：

| 文件 | 行 | 内容 |
|------|-----|------|
| `backend/src/config/app.config.js` | 15 | `const DEFAULT_DATA_ROOT = 'D:\\荒天帝工作台'` |
| `backend/src/config/app.config.js` | 16-28 | `resolveDataRoot()`：`HTD_DATA_ROOT` 未设 → 读 `D:\荒天帝工作台\settings.json` → catch 静默 → **return DEFAULT_DATA_ROOT** |
| `backend/src/config/app.config.js` | 40-46 | `dbDir/logDir/backupDir/dbPath` 全部 `path.join(DATA_ROOT, ...)` |
| `backend/src/bootstrap.js` | 20-23 | `ensureDir(appConfig.dataRoot)` 等 4 次无条件创建 |
| `backend/package.json` | 23 | `build:mac` 产出 `荒天帝工作台-macos` |

**失效路径**：macOS 上 `HTD_DATA_ROOT` 无人注入（全库 `grep HTD_DATA_ROOT` 仅 `app.config.js:17` 一处**读取**，无任何写入/注入点），`D:\...` 读取失败 → `DATA_ROOT = 'D:\荒天帝工作台'` → 在 POSIX 下这是一个**合法相对路径名**（反斜杠是普通字符）→ `bootstrap.js:20` 在当前工作目录下创建一个名为 `D:\荒天帝工作台` 的目录，数据库落在 `./D:\荒天帝工作台/data/workbench.db`。

**关联**：`app.config.js:4` `import os from 'os'` 已引入但全文未使用——说明"用 `os.homedir()` 做跨平台默认值"是曾经的设计意图，实现时被遗漏。

### P0-4｜Tauri sidecar 契约缺失（V2.0 "0 改动"承诺当前不成立）

`server.js` 作为未来 Tauri sidecar，存在三处硬阻塞：

| # | 问题 | 证据 | 后果 |
|---|------|------|------|
| a | **实际端口无法回传** | `server.js:55` 端口动态确定，`server.js:64-72` 仅写入 logger；无 stdout 结构化输出、无端口文件 | Tauri 前端不知道该连哪个端口。Tauri sidecar 标准做法是解析 stdout 约定行 |
| b | **无条件唤起系统浏览器** | `server.js:75-77` `setTimeout(() => openBrowser(url), 500)` 无任何环境开关；`browser.js:10-38` 无 guard | Tauri 窗口 + 系统浏览器**双开**，同一 SQLite 两个前端 |
| c | **实例复用逻辑与 sidecar 生命周期冲突** | `server.js:46-52` 探测到已有实例即 `openBrowser` + `process.exit(0)` | Tauri 拉起 sidecar，sidecar 立即 exit(0) → Tauri 判定 sidecar 异常退出 |

**补充**：`app.config.js:49-54` 用 `process.pkg` 三元判定 `frontendDir` / `templateDbPath`。Tauri 场景下 sidecar 若仍是 pkg 产物则可工作，但若改为 Node 直跑或换打包器，这两个路径**静默失效**（`bootstrap.js:33-34` 仅 `logger.warn`，不阻断启动）——即前端 404 而服务显示"启动成功"。

**结论**：V2.0 "业务代码 0 改动"对 controller/service/repository 成立，但**启动层（server.js / app.config.js）必须改动**。这一点应写入 ADR，避免决策层误判迁移成本。

项目已有状态机工厂 `lib/stateMachine.js:createStateMachine`（39行，`transition()` 越迁抛 `BusinessError(PARAM_ERROR)`），但落地方式分裂为三档：

|------|------|------|------|

**叠加问题——配置纳管范围与枚举回落不对称**：

## 三、三个重构候选方向

### 方向 A：保持零构建，注册点自动化（`meta.js` 约定）

**做什么**

1. **修复全部 P0**（前置，不属于方向差异）：
   - `appConfig.port` 改为可写运行时值，`server.js:55` 拿到真实端口后回写；`origin-guard.js` / `app.js` CORS 读运行时值。附带为 `origin-guard` 增加与 CORS 对称的环境变量逃生阀。
   - `app.config.js:15` 按 `process.platform` 分流默认数据根（Windows 保持 `D:\荒天帝工作台`，POSIX 用 `os.homedir()` —— `os` 已 import 待用）。
   - 生成 launcher 或删除 `ci.yml:116` 的 job（二选一，不留红灯）。
   - `server.js` 增加 `HTD_NO_BROWSER` / `HTD_SIDECAR` 开关，并在 stdout 打印 `HTD_PORT=<port>` 约定行供 Tauri 解析。
2. **每个前端页面增加 `meta.js` 同级描述文件**（路由路径、导航标题、SVG 图标 key、组件名），由一个 `frontend/js/registry.js` 在运行时遍历静态清单完成路由/导航/组件注册 —— 将 4 处手动改动收敛为 1 处（`meta` 声明）+ 1 个自动生成的清单文件（由 `scripts` 生成并纳入 CI 校验，仍不引入构建器）。
3. **新增 CI 门禁**：`check-registry.mjs` 校验"页面文件 ↔ meta ↔ index.html script ↔ 路由"四者一致；扩展 `visual-audit.js` 扫描 `**/*.js` 中的裸 hex 色值（P1-4）。
4. **状态机统一**：`project.service.js:107-113` / `reading.service.js:144` 收归 `createStateMachine`；`fieldConfig.defaultConfig()` 补齐 6 个未纳管状态机域，或在设置页显式标注"暂不可配"。
5. **service 越层治理**：跨模块写入统一走对方 repository；`search`/`backup`/`data` 三处标注架构例外并加注释。

**不做什么**

- 不引入 Vite / 任何前端构建器
- 不拆 `dataStore.js`（仅在新增模块时要求新 action 落在新分片 store，存量不动）
- 不动 CSS 文件拆分（`pages.css` 1910 行保留）
- 不做 Tauri 实际接入，只把 sidecar 契约（端口回传 + 无浏览器模式）预埋好

**风险**

| 风险 | 等级 | 说明 |
|------|------|------|
| `meta.js` 方案仍需手动维护 index.html script 清单 | 中 | 零构建无法做模块解析，只能靠 CI 校验兜住，无法根治 |
| 端口运行时化触及全局配置对象可变性 | 中 | `appConfig` 从"冻结常量"变为"启动后可写一次"，需明确注释与测试 |
| 状态机收归可能改变错误文案 | 低 | 需回归 6 个模块的状态流转测试 |

**收益**：P0 全清；P1-4/P1-5/P1-6/P1-7 大部分解决；新增页面成本从 5 处降至 2 处；**总投入最小，不引入新技术栈风险**。

**与 V2.0 关系**：完全兼容。sidecar 契约预埋后，Tauri 接入时后端改动量趋近于 0，前端因仍是纯静态资源，Tauri WebView 可直接加载或经 Express 托管，二选一皆可。

### 方向 B：前端引入 Vite

**做什么**

1. 同样先修 P0（不可省）。
2. 引入 Vite + ESM `import`，删除 `index.html:71-91` 的 21 条 script；路由/导航/组件用 `import.meta.glob` **真正自动注册**（根治 P1-5，无需 CI 校验）。
3. 拆分 `dataStore.js` 855 行为 22 个模块 store（P1-8）；拆分 `pages.css` 为页面级 CSS 模块（P2-2）。
4. 引入 TypeScript 类型（可选）与前端单测（Vitest 已在后端使用，工具链复用）。
5. pkg 打包链改为 `vite build` → `dist/` → 作为 pkg asset（`package.json:46` 的 `../frontend/**/*` 改为 `../frontend/dist/**/*`）。

**不做什么**

- 不改后端分层（P1-2/P1-3 另案处理）
- 不引入 SSR、不引入组件库（本地优先 + 现有 BEM/令牌体系已成型，引组件库会与 `visual-audit.js` 类名契约正面冲突）

**风险**

| 风险 | 等级 | 说明 |
|------|------|------|
| **类名契约门禁失效** | **高** | `visual-audit.js` 依赖"类名不可删除"审计；Vite + CSS 模块化会引入 hash 类名，现有 212 行门禁脚本需同步重写，否则视觉规范失去强制力 |
| 21 个 Page 全量改写为 ESM 模块 | 高 | 885 行的 `ProjectPage.js` 等大文件在迁移中极易引入回归，而前端**当前无自动化测试** |
| 构建产物与 pkg asset 路径耦合 | 中 | `app.config.js:49-51` `frontendDir` 需同步调整，P0-4 的静默失效风险放大 |
| 违背"前端零构建"既有决策 | 中 | 属决策反转，需新 ADR 记录并说明触发条件 |
| 调试链路变长 | 低 | 从"改 js 刷新"变为"dev server / build"，个人项目的即时性优势丧失 |

**收益**：P1-5 根治（而非缓解）、P1-8 可解、P2-2 可解；为知识图谱等复杂交互提供依赖管理能力；引入 tree-shaking 后 P1-6 类死代码可被工具检出。

**关键判断**：**当前触发条件尚未满足。** 触发 Vite 的合理信号是"依赖图复杂到手动 script 顺序无法维护"或"需要第三方 npm 库（如图谱布局引擎 d3-force / cytoscape）"。前者当前靠 21 条有序 script 尚能承受；后者才是真正的分水岭 —— `charts.js` 目前是**手写 SVG**（P1-4 上下文），若知识图谱确定要做力导向布局，手写不现实，那一刻 Vite 从"可选"变为"必需"。

### 方向 C：面向 Tauri 的端到端重构

**做什么**

1. 修 P0 并将 `server.js` 正式重构为**双模入口**：`--sidecar` 模式（无浏览器、stdout 端口协议、不做实例复用退出）与 `--standalone` 模式（现有行为）。
2. 数据根目录改为平台标准 app-data 路径，提供从 `D:\荒天帝工作台` 的一次性迁移逻辑。
3. 前端资源改由 Tauri 打包分发（不再走 `express.static`，`app.js:109-128` 静态托管降级为 standalone 模式专用）。
4. 引入 Tauri 侧能力：原生菜单、系统托盘、自动更新、文件对话框（替换现有 Web 文件选择）。
5. 同步执行方向 B 的前端构建化（Tauri 生态默认 Vite，二者天然绑定）。

**不做什么**

- 不放弃 HTTP API 通信模式（不改用 Tauri IPC/`invoke` —— 否则 26 个模块的 controller 层全部要重写，"0 改动"承诺彻底作废）

**风险**

| 风险 | 等级 | 说明 |
|------|------|------|
| **同时承担 B 的全部风险 + Rust 工具链** | **极高** | 一次性引入构建器 + Rust + 跨平台签名/公证，个人项目失控概率高 |
| 数据迁移不可逆 | 高 | `D:\荒天帝工作台` 现有用户数据迁移到 app-data，需备份/回滚方案，与 `backup.service.js`(361行) 联动 |
| Prisma engine 在 Tauri sidecar 下的分发 | 高 | 现依赖 `package.json:49-51` 将 `@prisma/engines` 作为 pkg asset；Tauri sidecar 打包方式不同，需重新验证原生二进制随包分发 |
| macOS 公证 | 中 | `build:mac` 目前只产 unsigned 二进制，Tauri 分发要求更严 |

**收益**：真正的桌面应用体验（托盘、原生菜单、自动更新）；根治 P0-2 的路径问题；`launcher-test`(P0-3) 这类脆弱的 shell 启动器彻底消失。

**关键判断**：**这是终局形态，但不应是下一步。** 当前 P0 尚未修复、前端无测试覆盖、`dataStore`/`ProjectPage` 均在 850+ 行 —— 在这个地基上叠加 Rust 与构建链，等于把 4 类风险耦合进同一个变更批次。

## 四、给总监的架构建议

### 4.1 结论：采用 **A → (触发式) B → C** 的分阶段推进，当前立即执行 A

三个方向并非互斥选项，而是**同一条演进路径上的三段**。真正需要决策的只有一件事：**何时从 A 切到 B**。我的建议是设置明确的触发条件，而不是排期。

### 4.2 分阶段方案

#### 阶段 0：P0 止血（建议立即，独立于方向选择）

| 项 | 内容 | 验收 |
|----|------|------|
| P0-1 | `appConfig.port` 运行时化；`origin-guard.js` / `app.js` CORS 读真实端口；补充 `origin-guard.test.js` 端口顺延用例 | 占用 17388 后启动，写入操作正常 |
| P0-2 | `app.config.js:15` 按 `process.platform` 分流默认数据根 | mac 产物数据落在 `~/` 下正确位置 |
| P0-3 | 生成 launcher 或删除 `ci.yml:116` job | CI 全绿 |
| P0-4a/b | `server.js` 增加 `HTD_SIDECAR`/`HTD_NO_BROWSER`；stdout 输出端口约定行 | sidecar 模式不弹浏览器、端口可被外部解析 |

**这一阶段不含任何架构选择，是纯缺陷修复，不应被方向讨论阻塞。** P0-1 与 P0-2 各自都能导致产品在特定环境下不可用，优先级高于一切重构议题。

#### 阶段 1：方向 A 全量落地（V1.6）

顺序建议按"证据密度 / 改动风险"比排列：

1. **P1-4 色值统一 + 门禁扩容**（改动小、立刻消除多主题缺陷、且门禁一旦到位后续不再回退）
2. **P1-1 状态机收归 + fieldConfig 纳管范围对齐**（消除"配置平台不可信"，这是产品可解释性问题）
3. **P1-7 ReadingPage 改造**（照抄 `ProjectPage.js:73-84` 范本，顺手补 `convertToVault` 状态联动）
4. **P1-6 lineChart 挂载**（40 行死代码转化为可见价值，成本最低）
5. **P1-5 meta.js 注册自动化 + check-registry 门禁**（本阶段最大项，放在门禁体系完备后做更安全）
6. **P1-2 service 越层治理 + 架构例外显式标注**
7. **P1-3 system 模块按职责拆为 dashboard / chart / setting / backup / data 五个 service**

`P2-1`(错误码) 与 `P2-2`(超长文件) 建议随手改，不单独排期。

#### 阶段 2：方向 B 触发条件（不排期，条件驱动）

满足**任意一条**即启动 Vite 迁移：

- 需要引入任何第三方 npm 运行时库（**知识图谱力导向布局是最可能的触发点**）
- `index.html` script 数超过 30 条，或出现过 2 次以上因加载顺序导致的线上问题
- 单个 Page 文件超过 1200 行且无法通过组件抽取解决

迁移时**必须先做的前置工作**（否则不批准启动）：
1. 重写 `visual-audit.js` 使其兼容构建产物 —— 类名契约门禁不能有断档期
2. 为 `ProjectPage` / `FinancePage` / `dataStore` 三个高危文件补齐前端测试
3. 出 ADR 记录"零构建"决策反转的触发依据

#### 阶段 3：方向 C（V2.0）

**准入条件**：阶段 1 完成 + 阶段 2 完成 + 前端测试覆盖建立。届时 Tauri 接入的实际工作量将只剩：sidecar 打包验证、Prisma engine 分发验证、数据迁移、签名公证 —— 四项都是**可独立验证的工程问题**，而不是与架构重构纠缠的复合风险。

### 4.3 需要总监拍板的三个决策点

| # | 决策 | 我的建议 | 需记录 |
|---|------|----------|--------|
| D1 | `V2.0 业务代码 0 改动` 的边界如何定义？ | 明确为"controller / service / repository / schema 零改动"，**启动层（server.js、app.config.js）与静态资源托管必然改动**（P0-4） | 新增 ADR，修正决策层对迁移成本的预期 |
| D2 | Windows 数据根 `D:\荒天帝工作台` 是否保留为硬约束？ | Windows 保留（用户已有数据），POSIX 用 `os.homedir()`；Tauri 阶段统一迁移到 app-data 并提供迁移器 | 补入 `OPEN-DECISIONS.md` |
| D3 | 知识图谱是否确定进入 V2.0 范围？ | 这是方向 B 的**唯一强触发条件**。若确定要做力导向布局，则 Vite 应提前到阶段 1 之后立即启动，而非等触发；若只做静态关系图，`charts.js` 手写 SVG 可继续支撑 | 影响阶段 2 的启动时点 |

### 4.4 一句话总结

这套代码库的**分层纪律与门禁体系明显优于同规模项目**（router/controller 零越层、类名契约门禁、测试库隔离），真正的问题不是"架构错了"，而是**三处契约在演进中脱钩**：端口协商与安全中间件脱钩（P0-1）、平台默认值与跨平台目标脱钩（P0-2）、配置平台的承诺范围与实际纳管范围脱钩（P1-1/P1-7）。这三类问题的共性是"局部都对，接缝处错"，因此修复手段应当是**把接缝变成门禁**，而不是推倒重来 —— 这正是方向 A 的核心逻辑，也是我不建议现在上 Vite 或 Tauri 的原因。
