# 沉淀模块设计（Vault · V1.3 起步）

> **适用范围**：知识组「沉淀 Vault」模块的最小可用设计与跨模块联动约定。
> **定位**：V1.3 是「第二大脑」的起点（V2.0 再扩双向链接 / 知识图谱）。本文件锁定**最小字段、来源类型、引用不复制原则、自动生成触发、首页推荐算法、联动接口签名**六大契约，避免后续版本改字段时破坏关联链路。

---

## 1. 最小字段表

落地于 `backend/prisma/schema.prisma` 的 `VaultItem` 模型 + `backend/src/modules/vault/vault.schema.js`（Zod，前后端共用校验）。

| 字段 | 类型 | 必填 | 说明 | 备注 |
| --- | --- | --- | --- | --- |
| `id` | Int | PK | 主键 | 自增 |
| `topic` | String(200) | ✅ | 主题（标题） | service 层额外校验非空，空 → `PARAM_ERROR`「沉淀主题不能为空」 |
| `content` | Text | ✅ | 笔记正文（Markdown 纯文本） | V1.3 前端离线手写 parser；V1.5 再引 markdown-it |
| `tags` | String[] | ✅ | 标签数组 | **以 JSON 字符串存库**（入库 `JSON.stringify`、出库 `JSON.parse`）；列表筛选用 `contains` 子串匹配 |
| `status` | Enum | ✅ | `DRAFT` / `PRECIPITATED` / `ARCHIVED` | 默认 `DRAFT` |
| `sourceType` | Enum | ✅ | 来源类型（见 §2） | 默认 `MANUAL` |
| `sourceId` | Int? | ❌ | 来源记录 ID | `sourceType != MANUAL` 时由调用方必填；空字符串入库归一为 `NULL` |
| `sourceUrl` | String(200)? | ❌ | 来源 URL Hash | 点击跳回原记录用；空字符串归一为 `NULL` |
| `createdAt` / `updatedAt` / `deletedAt` | DateTime | 标准 | 时间戳 | `deletedAt` 软删除（进回收站） |

> 模型**无 `remark` 字段**（V1.3 早期设计曾考虑，落地时移除）。所有「备注类」信息请放进 `content`。

### 1.1 枚举（`enums.js`）

```js
export const VAULT_STATUS = { DRAFT:'DRAFT', PRECIPITATED:'PRECIPITATED', ARCHIVED:'ARCHIVED' };
export const VAULT_SOURCE_TYPE = {
  MANUAL:'MANUAL', WEEKLY_REVIEW:'WEEKLY_REVIEW', PROJECT_REVIEW:'PROJECT_REVIEW',
  MEETING_REVIEW:'MEETING_REVIEW', CREDENTIAL_NOTE:'CREDENTIAL_NOTE', DEPLOY_NOTE:'DEPLOY_NOTE',
};
```

## 2. sourceType 六种类型

| 值 | 含义 | 生成方式 | sourceId 指向 |
| --- | --- | --- | --- |
| `MANUAL` | 手动新建 | 用户在沉淀页直接写 | NULL |
| `WEEKLY_REVIEW` | 周复盘沉淀 | 周复盘 `submit` 钩子自动生成 | `review.id` |
| `PROJECT_REVIEW` | 项目复盘沉淀 | 项目复盘 `submit` 钩子自动生成 | `review.id` |
| `MEETING_REVIEW` | 会议复盘沉淀 | 会议纪要生成复盘并提交后触发 | `review.id` |
| `CREDENTIAL_NOTE` | 凭据转沉淀 | 凭据保险箱「💡转沉淀」按钮手动触发 | `secret.id` |
| `DEPLOY_NOTE` | 部署转沉淀 | 部署档案「💡转沉淀」按钮手动触发 | `deployment.id` |

> 前四种本质是「复盘/会议」的派生；后两种是「凭据/部署」的一键引用。除 `MANUAL` 外，所有来源都必须带 `sourceId` + `sourceUrl`，否则跳回原记录会断链。

---

## 3. 引用不复制的三大原则（§6.8.4）

沉淀内容**永远不复制**原复盘 / 原凭据的完整正文到 `VaultItem.content`，只存三类东西：

1. **摘要**：用户提炼的 3–5 条要点（自动生成草稿时预填 Action Items 前 3 条占位）。
2. **引用指针**：`sourceType` + `sourceId` + `sourceUrl` 三元组，唯一指向原记录。
3. **延伸思考**：用户在沉淀页自行补充的延伸内容（≠ 原文复制）。

### 3.1 为什么必须引用不复制

| 风险 | 复制正文 | 引用不复制 |
| --- | --- | --- |
| **双写不一致** | 复盘正文改了，沉淀副本不同步 → 数据矛盾 | 永远读原记录，单一事实来源 |
| **存储浪费** | 复盘 5000 字 ×N 条沉淀 | 只存 300 字摘要 |
| **图谱断链** | V2.0 知识图谱无法基于副本建立关系 | 引用关系天然成网 |

### 3.2 反例（禁止）

> ❌ 用户把一份 5000 字的周复盘全文粘贴进沉淀 `content`。

后端软约束：非 `MANUAL` 来源的 `content` 超过「同来源 MANUAL 平均字数 ×2」时，更新接口返回 `BackendError`（码 `RESULT.VAULT.CONTENT_TOO_LONG_FOR_SOURCE`）**软告警**——不阻断保存，但记录日志并提示「引用模式不建议粘贴完整原文，建议提炼摘要，原文请跳回来源查看」。

## 4. 草稿自动生成触发条件

通用幂等方法（已落地）：`VaultService.autoCreateFromReview({ sourceType, reviewId, sourceUrl, title, content })`
- **幂等**：同一 `(sourceType, sourceId)` 已存在则直接返回旧记录，不重复创建（防止重复提交复盘多次生成）。
- 仅生成「摘要 + 引用指针」，不复制原文。

### 4.1 触发链路（4 种）

```
周复盘 submit (draft→submitted)
   └─ onTransition → VaultService.autoCreateFromReview({sourceType:'WEEKLY_REVIEW', reviewId})   → Vault DRAFT

项目复盘 submit (draft→submitted)
   └─ onTransition → autoCreateFromReview({sourceType:'PROJECT_REVIEW', reviewId})               → Vault DRAFT

会议纪要「生成复盘」→ ReviewService 创建 review(draft) 并回写 meeting.reviewId
   └─ 该 review submit → autoCreateFromReview({sourceType:'MEETING_REVIEW', reviewId})           → Vault DRAFT

凭据/部署「💡转沉淀」按钮（手动）
   └─ VaultService.create({sourceType:'CREDENTIAL_NOTE'|'DEPLOY_NOTE', sourceId, sourceUrl, topic, tags})
                                                                                              → Vault DRAFT
```

### 4.2 沉淀态推进

- 复盘 `submit → precipitate`（生成沉淀）：`VaultService.markPrecipitatedBySource(sourceType, reviewId)` 将关联 Vault 置 `PRECIPITATED`。
- 归档：`update(id, { status:'ARCHIVED' })`。

> ✅ 已落地并集成测试覆盖：周/项目复盘 `submit` 自动生成 Vault DRAFT（见 `review-statemachine.test.js`）。会议复盘、凭据/部署转沉淀的前端入口与首页推荐卡片为 V1.3 规划项，后端接口已就绪，前端页面按实际接入为准。

## 5. 首页推荐算法（规则权重 · §6.8.5）

> V1.3 为规则式（V2.0 再做 Agent 推荐）。候选来自 `dataStore.homeSummary`（后端 `/system/home-summary` 一次聚合）。

### 5.1 候选池

本周（周一 0 点 ~ 今）：
- 状态变为 `COMPLETED` 的今日任务；
- 阶段变为 `CLOSED` / `ACCEPTANCE` 的项目；
- 本周 `SUBMITTED` 但未生成沉淀（`PRECIPITATED`）的复盘。

### 5.2 打分表

| 信号 | 权重 | 说明 |
| --- | --- | --- |
| 项目阶段变化 | +4 | 本周有阶段推进的项目 |
| 任务含标签「重点」 | +2 | 已完成任务 `tags` 含「重点」 |
| 复盘待沉淀 | +3 | 本周提交但未沉淀的复盘 |
| 本周今日计划完成率 > 80% | +1 | 整体执行力加成 |

取**前 3 条**展示在首页知识组卡片「推荐待写沉淀」，每条带「一键生成草稿」按钮（前端 `dataStore.autoRecommendVault(candidate)` 调 `autoCreateFromReview`）。

### 5.3 空态

本周无完成事项 → 卡片显示空态：`title='本周还没有值得沉淀的产出'`，`actionText='去今日计划看看有没有已完成的？'`。

## 6. 联动接口签名

后端 service 方法（已落地，详见对应 `*.service.js`）：

```js
// ReviewService（backend/src/modules/review/review.service.js）
async submit(id)            // draft→submitted，钩子调 VaultService.autoCreateFromReview
async precipitate(id)       // submitted→precipitated，钩子调 VaultService.markPrecipitatedBySource

// VaultService（backend/src/modules/vault/vault.service.js）
async create({ topic, content, tags, status, sourceType, sourceId, sourceUrl })
async autoCreateFromReview({ sourceType, reviewId, sourceUrl, title, content })  // 幂等
async markPrecipitatedBySource(sourceType, reviewId)
async update(id, payload)   // tags 重新序列化；空 sourceId/sourceUrl 归一 NULL；含软约束告警
async list({ status, sourceType, tag })   // tag 走 contains 子串
async getById(id)
async delete(id)            // 软删除

// MeetingService（backend/src/modules/meeting/meeting.service.js）
async generateReview(id)    // 创建 review(draft) 并回写 meeting.reviewId
```

前端（`frontend/js/store/dataStore.js`）：
```js
async createVaultItem(payload)
async updateVaultItem(id, payload)
async deleteVaultItem(id)
async autoRecommendVault(candidate)   // 首页推荐「一键生成草稿」
```

### 6.1 跳回来源（对账要点）

沉淀详情页「来源信息」区渲染可点击链接：`window.location.hash = sourceUrl` 跳回原模块记录，并临时高亮原记录 3s（`prefers-reduced-motion` 关闭时去过渡）。**对账规则**：沉淀 `sourceId` 必须能原样定位到对应 `review / secret / deployment` 记录，否则视为断链 bug。

## 7. 验收清单（沉淀相关）

- [ ] 周/项目复盘 `submit` 后 Vault 自动 +1（`sourceType` 正确、`sourceId` 正确，`sourceUrl` 非空）。
- [ ] 同一复盘重复 `submit` 不重复生成 Vault（幂等）。
- [ ] `precipitate` 后关联 Vault 置 `PRECIPITATED`。
- [ ] 凭据/部署「转沉淀」生成 `CREDENTIAL_NOTE` / `DEPLOY_NOTE`，`sourceId` 指向原记录。
- [ ] 非 MANUAL 来源粘贴超长原文 → 更新接口返回软告警且不阻断。
- [ ] 沉淀详情点「来源」→ URL hash 定位原记录 + 高亮 3s + 摘要与原记录一致。
